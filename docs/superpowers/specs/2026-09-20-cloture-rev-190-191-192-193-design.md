## 1. REV-192 — durcissements de `core/app/pipelines/exchange.py`

Seam posé par le chantier « IPC d'échange DuckDB↔Arrow » (2026-09-16), sans
appelant réel à ce jour (préparé pour un futur premier moteur natif). 4
correctifs, tous vérifiés contre le code actuel :

1. **`srid` non coercé avant interpolation SQL** (`to_arrow_stream`,
   `f"ST_SetCRS({_qi(geom_col)}, 'EPSG:{srid}')"`) — inoffensif aujourd'hui
   (type `int` annoté, seuls des tests l'appellent) mais un futur appelant
   piloté par une config externe pourrait y passer une valeur non contrôlée.
   Correctif : `int(srid)` avant interpolation.
2. **`srid=0` incohérent entre les deux chemins** — `crs=None` côté
   GeoParquet (`f"EPSG:{srid}" if srid else None"` dans
   `app/cdc/parquet_writer.py::build_geodataframe`/
   `build_geodataframe_from_relation`), mais un CRS bogué `EPSG:0` côté Arrow
   (`ST_SetCRS` ne valide rien). Correctif : rejeter `srid <= 0` de façon
   identique sur les deux chemins (lever une erreur explicite plutôt que
   produire un CRS silencieusement faux ou nul).
3. **Collision de `view_name`** — un second appel `from_arrow_stream` avec le
   même `view_name` (créé comme `TEMP TABLE`, jamais documenté comme tel dans
   le nom du paramètre) lève un `duckdb.CatalogException` brut (« Table with
   name … already exists! »), pas `PipelineRuntimeError` — incohérent avec le
   contrat d'erreur du reste du module. Correctif : convertir cette exception
   en `PipelineRuntimeError`. Le `finally: conn.unregister(...)` tient déjà
   correctement dans ce cas (vérifié) — pas de fuite de ressource à corriger,
   seulement le type d'erreur.
4. **Colonnes géométrie ignorées en cas de pluralité** — `_geometry_column`
   ne détecte que la première colonne `GEOMETRY` (déjà documenté), mais les
   colonnes géométrie non sélectionnées traversent sans `ST_SetCRS` (chemin
   Arrow) et atterrissent comme valeurs opaques non-géométrie dans le
   GeoParquet (chemin fichier) — cette conséquence n'est pas documentée.
   Correctif : compléter la docstring pour couvrir ce cas ; pas de
   changement de comportement (aucun appelant réel, cf. ci-dessus).

Test : falsification explicite pour chacun des 4 points (injecter le défaut
visé, confirmer que le test échoue, corriger, confirmer le succès) — cf.
piège n°10 du CLAUDE.md, qui s'applique à tout correctif dont la preuve
repose sur un test.

## 2. REV-193 — garde `TYPE_CHECKING` sur `core/app/cdc/parquet_writer.py`

`duckdb` est importé au niveau module uniquement pour l'annotation de type de
`build_geodataframe_from_relation`/`write_geoparquet_from_relation`
(`relation: duckdb.DuckDBPyRelation`). Ce fichier est aussi importé par le
process `cdc-worker`, qui ne chargeait jusqu'ici jamais `duckdb` — coût
mesuré : 67 ms / 11 MiB au chargement du module.

Correctif : `if TYPE_CHECKING: import duckdb`, annotations concernées en
chaîne (`"duckdb.DuckDBPyRelation"`). Test : import isolé du module,
vérifier que `duckdb` n'apparaît pas dans `sys.modules` après import (et
qu'il y apparaît toujours quand le module qui construit réellement une
relation DuckDB l'importe, pour ne pas casser l'usage réel).

## 3. REV-190 — extraction de `useOpenItem` hors de `routes.tsx`

`catalogue-mes-vues-signets` (« Mes vues (signets) ») est mesurée à 82.576 de
santé dans le bilan de fonctionnalités — la logique propre aux signets
(`getBookmarkConfig`, reconstruction d'URL `timeRange`/`extent`/
`crossFilter`, les branches de `useOpenItem`) est intégralement couverte par
`shell/src/shell/routes.test.tsx` (vérifié : ce fichier rend `<AppRoutes/>`

stub). Le déficit est un problème de **rattachement de preuve** :
l'inventaire de fonctionnalités cite `routes.tsx` entier (442 lignes au
19-09-2026, partagées par 20+ routes sans rapport avec les signets), jamais
des numéros de ligne — cf. CLAUDE.md : « les numéros de ligne dérivent en

Correctif : extraire `useOpenItem` (aujourd'hui lignes 102-173 de

`routes.tsx` importe le hook à ses 3 sites d'appel (`CatalogRoute`,
`BookmarksRoute`, `ReportsRoute`) sans changement de comportement.
`routes.test.tsx` n'a besoin d'aucune modification (il teste déjà via
`<AppRoutes/>`, indépendant de l'endroit où vit le hook).

Clôture : mettre à jour `docs/revue/inventaire-fonctionnalites.jsonl` pour
que `catalogue-mes-vues-signets` cite `shell/src/shell/useOpenItem.ts` comme
preuve (plus `routes.tsx` entier) ; régénérer le bilan
(`feature_health_cli.py --write`) ; vérifier empiriquement la santé obtenue.
Si elle dépasse 90, retirer l'entrée de `exceptions_priorite_moyenne` dans
`core/scripts/feature_health_thresholds.json`. Si elle reste sous 90 (le
fichier extrait n'est peut-être pas mécaniquement couvert à 83,3 %+ de

backlog — ne pas forcer un résultat par des tests qui n'exercent rien de
nouveau sur la fonctionnalité (piège déjà identifié dans l'entrée REV-190

## 4. REV-191 — variante liste/array sur `FieldType`

### 4.1 Constat vérifié

`app/collections/introspection.py::FieldType` n'a aucune variante
liste/array. Le gap est déjà atteignable aujourd'hui : `transform.derive`/
`transform.aggregate.metrics` acceptent une expression SQL DuckDB dont seul
`FROM`/nom de table est filtré (`app/pipelines/expr_validation.py`), donc
`string_split(...)`/`list_value(...)` produisent déjà une colonne DuckDB
`LIST` sans code nouveau. `writer.collection` (`validate_feature`,
`app/features/validation.py:49-64`) rejette proprement toute propriété
`LIST` — `unknown_property` si la colonne cible n'existe pas,
`invalid_type` si elle existe avec un autre type — parce qu'**aucune
collection ne peut jamais déclarer de colonne liste**. Le rejet actuel est
sûr (pas de crash, pas de corruption) ; le vrai manque est l'absence de
`FieldType` correspondant.

### 4.2 Décisions de portée (tranchées en amont de ce document)

- **Déclencheur** : à la fois `writer.collection` (pipelines produisant une
  colonne `LIST`) et la déclaration d'une colonne liste via
  `POST /collections/empty` (le seul point d'entrée DDL réel du dépôt pour
  une collection créée avec un schéma explicite).
- **Types d'éléments acceptés** : tous les `FieldType` scalaires existants —
  `string`, `integer`, `number`, `boolean`, `date`, `datetime`. Jamais
  `list` imbriqué, jamais `enum`/`unsupported`/`attachment` en élément.
- **Stockage** : `ARRAY` natif Postgres (`text[]`, `integer[]`,
  `double precision[]`, `boolean[]`, `date[]`, `timestamptz[]`) — mapping
  direct avec les colonnes `LIST` en sortie de pipeline DuckDB, typage fort,
  opérateurs array natifs.
- **Encodage MVT** : sérialisation JSON en chaîne (`ST_AsMVT` n'accepte que
  des propriétés scalaires).

### 4.3 Côté cœur

**Modèle** (`core/app/collections/introspection.py`) :
- `FieldType` gagne `"list"`.
- `ColumnInfo` gagne `list_item_type: FieldType | None = None`.

**Introspection Postgres** (`introspection_pg.py`) :
`information_schema.columns.data_type == "ARRAY"` détecte un array ;
`udt_name` (`_text`, `_int4`, `_int8`, `_numeric`, `_float8`, `_float4`,
`_bool`, `_date`, `_timestamptz`, `_timestamp`…) débarrassé de son `_`
préfixe donne le type d'élément via une table de correspondance dédiée (les
noms internes Postgres diffèrent des clés de `_TYPE_MAP`, ex. `int4` vs
`integer`). `ftype = "list"` si l'élément est reconnu par cette table, sinon
`"unsupported"` (même repli que pour tout type non mappé aujourd'hui). **À
vérifier contre un `postgis-test` réel** au moment de l'exécution (piège
n°3) — les noms `udt_name` exacts n'ont pas été confirmés contre une
instance qui tourne dans le cadrage de ce document.

**Validation** (`app/features/validation.py`) : `_type_ok` gagne une branche
`list` — une valeur `list` Python dont chaque élément satisfait `_type_ok`
pour `col.list_item_type` (réutilise `_type_ok`, récursion d'un seul
niveau, jamais plus car `list_item_type` n'est jamais lui-même `"list"`).
`None` reste valide (absence de valeur, comme pour tout autre type).

**Écriture** (`app/features/repository.py::insert_feature`/
`replace_feature`) : aucun changement de code — une colonne `list` n'est pas
dans le chemin `unsupported`, donc déjà écrite comme toute autre propriété.
Le binding SQLAlchemy `:pN` d'une valeur `list` Python vers une colonne
Postgres `ARRAY` via `text()` est **à vérifier empiriquement** par un test
d'écriture réelle contre Postgres (pas supposé fonctionner par lecture du
code psycopg/SQLAlchemy).

**Lecture** (`_row_to_feature`) : aucun changement — psycopg renvoie déjà une
colonne Postgres `ARRAY` comme `list` Python.

**Filtrage** (`repository.py::_where`) : une colonne `list` rejoint le même
rejet que `unsupported` (ligne ~77-78) → `FilterError(name, "property not
filterable")`, un 422 propre plutôt qu'un `col = :val` cassé contre un
array.

**Tuiles vectorielles** (`app/features/tiles.py::build_mvt_sql`) : pour une
colonne `list`, la projection dans `props_clause` devient
`to_jsonb(t.{col})::text AS {col}` au lieu de la colonne brute.

**Schéma JSON exposé** (`app/collections/schema_json.py::
table_info_to_schema`) : une entrée de champ `list` gagne
`"itemType": col.list_item_type`, même patron que `"values"` pour `enum`.

**DDL de création** (`app/collections/schemas.py::EmptyCollectionColumn.
sqlType`, `provisioning.py::create_empty_collection`) : le `Literal` de
`sqlType` gagne `"text[]", "integer[]", "bigint[]", "double precision[]",
"boolean[]", "date[]", "timestamptz[]"` — la génération DDL
(`f"{ident} {c.sqlType}"`) accepte déjà cette syntaxe Postgres sans
changement de code, seul l'allowlist Pydantic s'ouvre.

**Hors périmètre, documenté au lieu d'être corrigé** : agrégation DuckDB
analytique (`app/analytics`) sur une colonne liste.

### 4.4 Côté shell

**Types** (`shell/src/api/types.ts`) : `CollectionFieldType` gagne `"list"` ;
`CollectionSchemaField` gagne `itemType?: CollectionFieldType`.

**Formulaire généré** (`shell/src/builder/widgets/form.tsx`, SP-4) : un champ
`list` suit le même traitement que `unsupported` — exclu du rendu et de la
validation (mêmes filtres `f.type !== "unsupported"`, lignes ~103, ~456,
~459 au 19-09-2026, à revérifier à l'exécution). Un éditeur de valeur liste
générique est une question de design à part entière, non tranchée ici : la
colonne reste lisible via l'API mais pas éditable depuis le formulaire
auto-généré.

**Wizard de requête visuelle** (`shell/src/pages/VisualQueryWizardPage.tsx`,
`shell/src/builder/visualQuery/inferSchema.ts`) : risque de régression
identifié en lisant le code, pas une extension mécanique. Le wizard a déjà un
point de passage unique pour exclure les pseudo-champs non filtrables/
joignables/résumables (`withoutAttachmentFields`, ligne ~207, aujourd'hui
limité à `attachment`) — étendu pour exclure aussi `list`, avec un
renommage reflétant les deux cas couverts (ex. `withoutUnrepresentableFields`).
Sans cet ajout, un champ `list` resterait sélectionnable dans les pickers
Filtrer/Joindre/Résumer et tomberait dans un cas déjà bogué aujourd'hui pour
`unsupported` (`inferSchema.ts::sqlTypeOf` retombe silencieusement sur
`"double precision"` quand `FIELD_TYPE_TO_SQL[type]` vaut `null`) — bug
préexistant, hors périmètre de correction ici, mais à ne pas étendre à un
nouveau type en l'ignorant.

`inferSchema.ts::FIELD_TYPE_TO_SQL` gagne `list: null` (même traitement
qu'`attachment`/`unsupported`) — le type reste complet pour la vérification
TypeScript (`Record<CollectionFieldType, ...>` exige une entrée par membre),
et `list` n'atteint jamais la génération de schéma de sortie du wizard
aujourd'hui grâce à l'exclusion amont.

**Ce que ça ouvre concrètement** : `POST /collections/empty` (donc tout
appelant API, y compris un futur outillage) peut déclarer une colonne liste
— c'est la fermeture réelle de REV-191. Le wizard de requête visuelle, seul
appelant UI actuel de cette route, n'exerce pas ce chemin (ses pickers
l'excluent, cf. ci-dessus) — limitation assumée et documentée, pas un
chantier UI supplémentaire.

**Hors périmètre** : `compileFilter.ts` (switch avec `default:`, pas de
vérification d'exhaustivité — `list` y tomberait dans le même branch
générique que `string`, mais inatteignable puisque le picker de filtre
l'exclut déjà en amont, pas de changement nécessaire) ; popups/symbologie
carte (un champ liste affiché en popup montre la chaîne JSON brute produite
par le MVT — pas de nouveau helper CEL de décodage).

### 4.5 Tests

  `text[]`/`integer[]`).
