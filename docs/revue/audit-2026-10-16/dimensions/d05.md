# d05 — Dashboards, widgets, cross-filter, analytics

Audit en lecture seule, sans exécution de suite de tests. Preuves = lecture directe du code (fichier:ligne).

## Synthèse

Le SQL Lab est bien confiné : `enable_external_access=false` et `lock_configuration=true` sont posés après la matérialisation, les colonnes sensibles sont masquées, les limites géographiques sont refusées. Aucune faille d'autorisation trouvée sur `/aggregate`, MCP ou alertes.

Les problèmes se concentrent sur trois points :

1. Des résultats silencieusement faux : plafond de 100 enregistrements sur la source par défaut, totaux de pivot additionnés sur des agrégats non additifs, fenêtres de comparaison qui se chevauchent, cross-filter temporel qui ne ramène aucune ligne.
2. Un contexte analytique non restauré de bout en bout (bookmark, widget de dates).
3. Un modèle sémantique trop pauvre pour viser mieux qu'ArcGIS et FME : pas de mesure calculée, pas de top-N, pas de jointure spatiale no-code, un SQL Lab sans issue.

Total : 12 constats (1 Critical, 9 Important, 1 Minor regroupant 5 finitions ; les 11 premiers vérifiés, le Minor non vérifié). Un test DuckDB ponctuel a invalidé une hypothèse (comparaison numérique contre paramètre texte : OK) ; elle n'est pas remontée.

## Critical

### 1. Source « features » par défaut : indicateur, graphique et tableau calculés sur les 100 premières entités, sans alerte
Tag : **bug** — vérifié

**Preuve**
- Une nouvelle DataSource est créée avec `type:"features"` (`shell/src/builder/DataSourcePanel.tsx:144`).
- `queryPage` appelle `fetchGeoJsonPage(buildFeaturesUrl(...))` sans paramètre `limit` (`shell/src/api/domains/datasets.ts:210` ; `_queryParams` n'en ajoute jamais). Le cœur applique `limit=Query(100)` par défaut (`core/app/features/routes.py:320`).
- `indicator.tsx` (`resolveFlatValue`, l.163-188) renvoie `data.records.length` pour tout agg autre que sum (l.188) : un « Nombre » plafonne à 100. La somme porte sur les mêmes 100 lignes.
- `chart.tsx:420-433` applique `buildOption` à ces records.
- Le tableau (`data.tsx:294-334`) trie et pagine côté client sur les 100 lignes ; seul un `<p>` « tronqué » apparaît (l.377). Indicateur et graphique n'ont aucun avertissement alors que `data.total` est disponible.

**Reproduction** : collection de 5000 entités, nouvelle app, source par défaut (features), widget Indicateur agg=count : affiche 100. Widget Tableau trié par population décroissante : classement des 100 premières lignes seulement.

**Correctif**
1. Indicateur/Graphique/Pivot : forcer ou proposer en priorité le type `statistics` (agrégat serveur) ; sur source features, afficher `data.total` et un badge « échantillon de N sur M » quand total > records.length.
2. Tableau : pagination et tri serveur (offset/limit/sortby déjà disponibles côté OGC).
3. Créer la source par défaut en `statistics` quand le widget cible est un indicateur ou un graphique.

## Important

### 2. Pivot : totaux de ligne, colonne et général additionnent des agrégats non additifs
Tag : **bug** — vérifié

**Preuve** : `buildPivotGrid` ne connaît pas l'agrégat de chaque mesure ; `rowTotal`, `colTotal` et `grandTotal` font `reduce((sum,…)=>sum+cell(...))` (`shell/src/builder/widgets/pivotTable.ts:64-72`). Pour avg, min, max, median, percentile ou countDistinct, le « Total » est une somme de moyennes : mathématiquement faux. Les null deviennent 0 (`Number(x ?? 0)`, l.47), une cellule absente s'affiche 0 au lieu de vide, et les nombres sont rendus bruts, sans `formatNumber` ni format de métrique (`pivot.tsx:100-199`).

**Reproduction** : source statistics groupBy [region, annee], measures [{agg:"avg", field:"prix"}] : les « Total » ligne et colonne affichent la somme des moyennes.

**Correctif** : passer l'agrégat de chaque mesure (`resolvedSource.query.measures`) à `buildPivotGrid`. Pour les non additifs, demander les totaux au cœur (requêtes groupBy partielles, ou ROLLUP/GROUPING SETS dans `aggregate.py`) ou masquer le total. Cellule vide plutôt que 0, formatage via `DatasetMetric.format`.

### 3. Comparaison de périodes : fenêtre de référence qui chevauche la période courante, et comparaison qui ignore filtres et mesure de la source
Tag : **bug** — vérifié

**Preuve** : `referenceWindow` (mode previous) pose `refTo = current.from` (`shell/src/lib/comparisonWindow.ts:45`). Les deux bornes sont inclusives côté cœur (`__lte` sur une date seule devient `< jour+1`, `aggregate.py _build_where`) : le jour `from` est compté dans les deux fenêtres (courant 2026-01-08..01-14, référence 2026-01-02..01-08). Ensuite `windowedStatisticsSource` part de `query:{}` (l.60-82, notamment l.68-75) : filtres statiques de `DataSource.query`, mesure/metric et groupBy de la source d'origine sont perdus. `chart.tsx:348` force `agg = valueField ? "sum" : "count"` et passe `valueField` (souvent le libellé d'une mesure) comme champ brut au cœur : 422 ou somme différente du graphique non comparé (`chart.tsx:348-405`, `indicator.tsx:51-125`).

**Reproduction** : indicateur avec filtre statut=ouvert sur la source, comparaison « période précédente », plage 8-14 janvier : delta calculé sans le filtre, le 8 janvier compté deux fois.

**Correctif** : `refTo = from − 1 jour`, durée = `to − from + 1 jour`. Construire la source fenêtrée depuis la source réelle (`{...resolvedSource, query:{...resolvedSource.query, ...patch, groupBy, bucket}}`) en réutilisant l'agg et le champ de la mesure choisie.

### 4. Cross-filter : une seule entrée par dataset, clic sur un bucket temporel = filtre à zéro ligne, patch qui écrase les filtres de l'auteur et du contexte
Tag : **bug** — vérifié

**Preuve**
- (a) `crossFilter` est `Record<datasetId, entrée unique>` (`shell/src/builder/AnalyticsContext.tsx:15,114-128`) : un second widget sur le même dataset remplace le filtre du premier au lieu de l'intersecter. Select multi-champs, slider et clic graphique s'annulent mutuellement.
- (b) `resolveClickFilter` renvoie `{field: categoryField, value: params.name}` (`chartOption.ts:326-328`). Pour un graphique groupé avec bucket, `name` vaut le début de bucket tronqué (ex. `2026-03-01T00:00:00`) et le filtre devient une égalité exacte sur des horodatages (`_build_where`, branche else, `aggregate.py:306-345`) : zéro ligne. Une catégorie NULL envoie `""` ou `"null"`, ignoré ou sans correspondance.
- (c) `mergedQueryFor` fait `{...s.query, ...contextPatch, ...filters}` (`DataContext.tsx:87-90`) : un filtre d'auteur sur la même clé est remplacé silencieusement, et `applyCrossFilterValue` (`analyticsPatch.ts:20-59`) réécrit `field__gte/__lte`, ce qui écrase la plage du contexte temps global si `timeField` est le même champ.

**Reproduction** : graphique en barres par mois, clic sur « mars » : les autres widgets passent à 0 ligne. Source statut=ouvert plus select-filter statut=[ferme] : on voit des fermés.

**Correctif** : liste de prédicats par dataset (clé = widgetId ou champ) combinés en AND, avec fusion d'intervalles. Un clic sur bucket émet `{from,to} = [début, début+grain[`. Une catégorie NULL émet un prédicat `isnull` (cf. constat 9). Les filtres du contexte s'ajoutent à ceux de l'auteur (tableau de clauses) au lieu de les remplacer.

### 5. Widget Période : état local non resynchronisé avec le contexte (bookmark, ?ctx=), sans validation ni préréglages
Tag : **bug** — vérifié

**Preuve** : `from`/`to` sont des `useState("")` locaux (`shell/src/builder/widgets/dateRangeFilter.tsx:33-47`). Le contexte restauré depuis un bookmark ou `?ctx=` (`AppRuntimePage.tsx:100-135`, `AnalyticsContext.tsx:77-79`) applique le `timeRange` aux requêtes, mais les deux `<input type=date>` s'affichent vides. Au premier changement d'un seul champ, `update(e.target.value, to)` avec `to=""` appelle `setTimeRange(null)` : la plage restaurée est effacée. Rien n'empêche from > to. Aucun préréglage (7 j, 30 j, mois, YTD, relatif), aucune granularité, aucune exclusion par widget.

**Reproduction** : ouvrir un bookmark avec `timeRange` : champs vides alors que le filtre est actif. Modifier la date de fin : la plage disparaît.

**Correctif** : dériver la valeur affichée de `useAnalyticsContext().timeRange` (comme `sliderFilter` le fait déjà) ; valider from ≤ to ; ajouter préréglages et plages relatives (« 30 derniers jours ») résolues à l'exécution.

### 6. Bookmark : la géométrie du cross-filter spatial est perdue à l'enregistrement ; variables et page de carte non capturées ; les rapports PDF planifiés héritent du défaut
Tag : **parite** — vérifié

**Preuve** : un clic carte pose `setCrossFilter(..., record.geometry)` (`mapWidget.tsx:392-398`) et `DatasetCrossFilterLink` mode « spatial » s'appuie sur `entry.geometry` (`analyticsPatch.ts:51-57`). `BookmarkCrossFilterEntry` (`core/app/configs/schemas.py:288-295`) ne déclare que field/value/originSourceId ; c'est un `BaseModel` pydantic sans `StrictModel`, donc la clé `geometry` envoyée par `createBookmarkItem` (`shell/src/api/domains/items.ts:305-313`) est supprimée silencieusement. Le signet restauré, et le PDF planifié via `encode_analytics_context` (`core/app/reports/ctx.py:23-31`), perdent le filtre spatial. `BookmarkPayload` (l.298-309) ne contient ni les variables d'app, ni l'onglet actif, ni la caméra de la carte, ni la visibilité des couches. À l'inverse `?ctx=` (`analyticsContextUrl.ts:7-12`) encode toute la géométrie dans l'URL (risque de dépassement de longueur sur un polygone détaillé).

**Reproduction** : dataset A avec lien spatial vers B ; clic sur un polygone de A ; « Enregistrer la vue » ; rouvrir : B n'est plus filtré.

**Correctif** : ajouter `geometry: dict|None` (borné en taille) à `BookmarkCrossFilterEntry`, ou une référence `{datasetId, pk}` résolue à la lecture. Capturer variables, pageId et vue carte dans `BookmarkPayload`. Ne pas mettre de géométrie dans l'URL (référence par pk).

### 7. Widgets statistiques : le retard du lac (asOf/pending) est calculé par le cœur mais jamais montré ; un lac vide donne des zéros silencieux
Tag : **bug** — vérifié

**Preuve** : `POST /aggregate` renvoie `asOf`, `pending` et `lagBytes` (`core/app/features/routes.py:443-494`). `queryPage` ne garde que `data.rows` (`datasets.ts:150-185`) ; `asOf`/`pending` ne sont lus par aucun widget. Tant que la réplication CDC n'a rien écrit (`pending=true`), `_run_collection_aggregate` renvoie des lignes vides ou une ligne de zéros (`aggregate.py:659-680, 737-752`). Le tableau features lit la base en direct et affiche les données alors que graphiques et indicateurs sur la même collection montrent « Aucune donnée » ou 0. Le lac a jusqu'à ~30 s de retard (docstring de `lake_as_of`).

**Reproduction** : importer ou créer une collection, ouvrir tout de suite l'app : tableau rempli, indicateur count = 0.

**Correctif** : remonter `{rows, asOf, pending}` jusqu'à `DataSourceState` et afficher un badge « mis à jour à hh:mm / réplication en cours » sur les widgets statistics. Option : repli sur l'agrégat PostGIS quand `pending`.

### 8. SQL Lab : impasse fonctionnelle, matérialise toute la collection à chaque requête
Tag : **differenciateur** — vérifié

**Preuve** : `SqlLabPage.tsx:81-340` ne contient aucun export CSV/XLSX, aucune sauvegarde de requête (l'historique est un stockage local au navigateur, `readSqlHistory`), aucun lien « créer un dataset/graphique/alerte depuis cette requête ». Côté cœur, `_materialize` fait `CREATE TEMP TABLE … AS <dedup CTE>` sur toutes les colonnes de chaque collection référencée (`sql_sandbox.py:94-115`) avant d'exécuter la requête, sans pushdown de prédicat, sous `MEMORY_LIMIT` 512 Mo et `STATEMENT_TIMEOUT_S` 10 s (`sql_sandbox.py:28-29`) : une collection de plusieurs millions de lignes échoue ou expire quel que soit le WHERE. `SqlQueryBody.sql: str` n'a pas de `max_length` (`routes.py:83-84`) et `parse_ast` (`sql_sandbox.py:165-188`) s'exécute avant le démarrage du timer.

**Reproduction** : SQL Lab sur ~5 M de lignes : `SELECT count(*)` dépasse 10 s ou 512 Mo. Aucun bouton pour exporter le résultat.

**Correctif** : remplacer la matérialisation par des vues sur `read_parquet` avec projection et filtre poussés, borner `sql` à ~100 Ko, démarrer le timer avant le parse. UI : requêtes enregistrées partageables (kind query), export CSV/GeoJSON du résultat, « Enregistrer comme dataset » (pipeline `writer.dataset`, comme la requête visuelle), « Ajouter à une app ».

### 9. Modèle sémantique trop pauvre : métriques field+agg seulement, filtres =/in/>=/<= uniquement, pas de tri ni de top-N, plafond de 10 000 groupes
Tag : **differenciateur** — vérifié

**Preuve** : `DatasetMetric = {field, agg, p, format, unit}` (`core/app/configs/schemas.py:198-220`) : pas de mesure calculée (ratio, différence), pas de mesure filtrée, pas de comparaison de période ni de cumul côté serveur, pas de colonnes calculées de dataset. `AggregateRequestBody.filters: dict[str,str]` (`aggregate.py:46-62`) et `_build_where` (l.306-345) ne connaissent que égalité, `__in`, `__gte`, `__lte` : pas de !=, NOT, IS NULL, contains, OR ni groupes de conditions. Tri figé sur `ORDER BY __cat` (l.796-808) : pas de tri par mesure, pas de limit ni top-N, et au-delà de `MAX_GROUPS=10 000` (l.82) la requête est rejetée en 400. Les widgets de comparaison recomposent côté client ce que Power BI, Superset ou ArcGIS Dashboards fournissent comme mesures.

**Reproduction** : « top 10 régions par somme » impossible ; taux a/b impossible sans pipeline ; filtre statut ≠ clos impossible.

**Correctif** : étendre `AggregateRequestBody` : `orderBy` (clé ou mesure), `limit`, opérateurs (neq, isnull, contains, nin) et arbre AND/OR. Étendre `DatasetMetric` : `filter` (arbre de conditions) et `expr` (arithmétique entre métriques, validée, pas de CEL libre). Couvre aussi le cross-filter sur NULL (constat 4).

### 10. Requête visuelle no-code : jointure inner/left sur clé de même nom uniquement, pas de jointure ni résumé spatial
Tag : **differenciateur** — vérifié

**Preuve** : `JoinConfig = {collectionId, on: string, how: "inner"|"left"}` (`shell/src/builder/visualQuery/inferSchema.ts:4`) : une seule colonne, même nom des deux côtés (`transform.join{on, how}`, `compilePipeline.ts:96-117` ; UI `QueryJoinPicker.tsx:66-67`), sans right/full ni clés multiples ou de noms différents. Aucune option « Jointure spatiale » ni « Résumer à l'intérieur de » alors que le moteur expose déjà `transform.spatialRelator` (`core/app/pipelines/ops/attrs.py:384`). La requête est matérialisée en collection (`writer.dataset` mode replace) plutôt que virtuelle. C'est le « Join Features / Summarize Within » d'ArcGIS que la plateforme peut offrir en no-code.

**Reproduction** : compter les points d'intérêt par commune dans l'assistant : impossible, il faut passer par l'éditeur de pipeline.

**Correctif** : mode spatial dans `JoinConfig` (`predicate: intersects|within|nearest`, option distance) compilé vers `transform.spatialRelator` ou la jointure spatiale DuckDB ; clés multiples et de noms différents ; right/full. Option : mode « vue » (dataset adossé à une requête, sans copie).

### 11. Coût par widget : toutes les sources de toutes les pages interrogées d'emblée, aller-retours S3 de métadonnées sans cache
Tag : **dette** — vérifié

**Preuve** : `AppRenderer.tsx:224-247` monte `<DataProvider sources={config.dataSources}>` une seule fois, hors page, et `DataContext.tsx:92-101` crée un `useQueries` pour chaque source sans tenir compte des widgets de la page active : 5 pages × 4 widgets = 20 agrégats au chargement, y compris pour des pages jamais visitées. Côté cœur, chaque appel ouvre une connexion DuckDB neuve (`duckdb_conn.py:25-50` : connect, LOAD de 3 extensions, CREATE SECRET) puis, via `_run_collection_aggregate` : `_has_any_file` (glob S3, `aggregate.py:479-486`), `latest_snapshot` (listage), `_has_seq_column` ×2, `_lake_column_names` ×2 (`read_parquet LIMIT 0`, l.510-587) avant la vraie requête, puis `lake_as_of` (`read_parquet max(_ts)`). Aucun cache des schémas ni des résultats ; le reducer `row_number()` sur toute la collection est recalculé pour chaque widget.

**Reproduction** : dashboard de 12 widgets sur une même collection de 1 M de lignes : 12 connexions, ~80 requêtes de métadonnées S3, 12 réductions complètes.

**Correctif** : shell : ne passer à `DataProvider` que les sources référencées par les widgets de la page active (ou activées par visibilité). Cœur : mémoïser (collection_id, snapshot, jeu de colonnes) quelques secondes, fusionner `_has_seq_column`/`_lake_column_names` en une lecture de schéma, réutiliser une connexion/pool par worker, cacher les agrégats par (collection, requête, asOf).

### 12. Finitions analytics
Tag : **polish** — **non vérifié** (lecture non recoupée indépendamment)

**Preuve (déclarée)**
1. Le sélecteur d'agrégat de l'indicateur ne propose que count et sum (`indicator.tsx:280-282`) alors que le cœur supporte 9 agrégats (`ANALYTICS_AGGREGATES`) ; avg/min/max sur source features retombent sur count (l.188). Le champ valeur du graphique et de l'indicateur est un `<input>` libre (`chart.tsx:160-175`), sans sélecteur de champs du schéma.
2. `_pivot_split` remplit les combinaisons absentes avec 0 (`row.setdefault(sv, 0)`, `aggregate.py:362-382`, l.380), faux pour avg/min/max.
3. `sliderFilter` : `<input type=range>` sans `step` (défaut 1) : impossible de choisir 0,3 sur 0..1 ; chaque tick appelle `setCrossFilter` sans debounce (`sliderFilter.tsx:130-149`).
4. `selectFilter` charge toutes les valeurs distinctes (plafond 10 000, erreur 400), une case par valeur, sans recherche ni virtualisation ; une valeur NULL donne un id vide (`selectFilter.tsx:54-70`).
5. `_render_message` passe `datasetName=payload.datasetItemId` (`core/app/alerts/jobs.py:263-271`) : le message d'alerte contient l'identifiant, pas le titre.

**Reproduction** : indicateur « moyenne » sur source features : affiche le nombre de lignes. Slider sur champ décimal 0..1 : seules 0 et 1 atteignables.

**Correctif** : `ANALYTICS_AGGREGATES` dans l'indicateur et sélecteur de champs typé ; `null` dans `_pivot_split` ; `step` dérivé de min/max + debounce 300 ms ; recherche + limite top N dans le select et prédicat IS NULL ; résoudre le titre du dataset pour `{datasetName}`.

## Avantages et différenciateurs

- SQL Lab réellement confiné : accès externe coupé et configuration verrouillée après matérialisation, colonnes sensibles masquées, limites géographiques refusées.
- Aucune faille d'autorisation relevée sur `/aggregate`, MCP et alertes : la porte `can()` et le masquage de colonnes tiennent sur ces surfaces.
- Le cœur calcule déjà `asOf`/`pending`/`lagBytes` : la transparence de fraîcheur du lac est à un câblage UI d'être un atout face à ArcGIS Dashboards.
- Le moteur de pipeline expose déjà `transform.spatialRelator` : la jointure/résumé spatial no-code (constat 10) est un différenciateur à faible coût face à ArcGIS « Join Features / Summarize Within » et FME.
- Le cross-filter spatial inter-datasets existe déjà (SP-14n), rare dans les outils BI génériques ; une fois rendu persistant (constat 6) il devient un avantage net.
- Un modèle sémantique enrichi (constat 9 : mesures calculées, top-N, arbre de conditions) servirait en une fois dashboards, MCP, alertes et rapports.
