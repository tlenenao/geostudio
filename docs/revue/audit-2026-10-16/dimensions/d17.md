# Audit 2026-10-16 — Dimension d17 « Multi-tenant »

Lecture seule du code, aucun test lancé. Tags : bug, parite, differenciateur, securite, dette.

## Synthèse

L'isolation par `tenant_id` est bien faite au niveau des données : les 45 tables portant `tenant_id` sont couvertes par `purge_tenant`, et aucune requête par id sans garde tenant n'a pu être exploitée depuis une route. L'audit est écrit dans les services. Le problème de fond est ailleurs : la plateforme n'est pas réellement multi-tenant. Le tenant est codé en dur à `default` sur toutes les surfaces, sans provisioning, sans quota par tenant et sans isolation de charge. Trois défauts concrets s'y ajoutent : tables PostGIS jamais supprimées, quotas aveugles aux lignes PostGIS et aux utilisateurs, `audit_log` non immuable.

Décompte : 2 Critical, 3 Important, 3 Minor (5 constats vérifiés par lecture de code, 3 Minor non vérifiés).

## Critical

### C1 — Multi-tenance non opérante : le tenant est toujours « default » [differenciateur]

- Preuve : `core/app/auth/dependency.py:205` résout `get_or_create_default_tenant(session)` pour toute requête (mock, clé d'API, jeton d'export, OIDC) ; le tenant n'est jamais lu depuis un claim, un host ou un realm. Même schéma : `core/app/mcp/tools/identity.py:66`, `core/app/dcat/routes.py:60`, `core/app/configs/guest_access.py:151`, `core/app/stac/routes.py:72`, `core/app/ows/routes.py:175`, `core/app/ows/wms_routes.py:174`, `core/app/extensions/routes.py:127`, `core/app/collections/routes.py:387` et `:558`. `core/app/public/routes.py:116/140/216/233/270` codent `DEFAULT_TENANT_SLUG` en dur. `Tenant(...)` n'est instancié qu'en `core/app/tenants/repository.py:23` (id « default »). Le modèle (`core/app/tenants/models.py:14-20`) n'a que id/slug/name/created_at : ni statut, ni domaine, ni branding, ni limites, ni flags. Aucune route de création/listage de tenants. Tout porteur d'un jeton valide de l'issuer OIDC est auto-créé « creator » dans `default` (`core/app/users/repository.py:23+`). Un second tenant créé à la main serait invisible de ses propres visiteurs publics.
- Reproduction : `grep -rn 'get_or_create_default_tenant\|DEFAULT_TENANT_SLUG' core/app` ; aucune autre source de `tenant_id` côté requête. Insérer à la main un 2e tenant et un utilisateur : aucun jeton ne peut s'y résoudre.
- Correctif : résolveur de tenant unique (claim OIDC `tenant`/`org`, ou sous-domaine/header de confiance posé par Traefik) utilisé par `get_current_user`, MCP, routes publiques/STAC/DCAT/OWS. Étendre `Tenant` (status, custom_domain, branding, settings JSON, limites). API `POST/GET /v1/platform/tenants` réservée à un rôle opérateur, avec bootstrap de l'admin du tenant.

### C2 — Supprimer une collection ne supprime jamais sa table PostGIS [bug]

- Preuve : `repo.delete_collection` (`core/app/collections/repository.py:173-175`) fait seulement `session.delete(col)`. La route `unregister_collection` (`core/app/collections/routes.py:970-1032`) retire publication CDC, pièces jointes, lac, puis la ligne catalogue, sans DROP. Le seul `DROP TABLE` du dépôt est `core/app/compliance/purge.py:261` (purge de tenant entier). Les tables `ingest_*`/`query_*` (`core/app/ingestion/importer.py:332`, `core/app/collections/provisioning.py:72`) survivent avec leurs lignes et leur `tenant_id`. `core/app/compliance/orphans.py` ne balaie que S3. Effets : (1) effacement RGPD non tenu ; (2) contournement du quota de stockage (lignes PostGIS non mesurées, `core/app/quotas/service.py:139-143`) ; (3) `GET /collections/candidates` (`core/app/collections/routes.py:604-641`) liste ces tables orphelines (geometryType/srid/columnCount) à tout admin de collections de n'importe quel tenant. `_reject_preexisting_mismatched_tenant_column` (`ddl.py:208-237`) ne bloque le réenregistrement inter-tenant que si des lignes d'un autre tenant existent.
- Reproduction : `POST /v1/uploads` (GeoJSON) puis `DELETE /v1/collections/ingest_xxx` -> 204 ; `SELECT count(*) FROM public.ingest_xxx` renvoie toujours les lignes ; `GET /v1/collections/candidates` depuis un autre tenant liste `ingest_xxx`.
- Correctif : DROP de la table dans `unregister_collection` quand elle est créée par GeoStudio (`ingest_`/`query_` ou drapeau `managed=true`) ; pour une table préexistante, retirer RLS/colonne ajoutée. Balayage `sweep_orphan_tables` avec délai de grâce dans `compliance/orphans.py`. Filtrer `candidates` sur les tables sans `tenant_id` ou à `tenant_id` unique égal à celui de l'appelant.

## Important

### I1 — Quotas : une limite instance-wide, éteinte par défaut, qui ignore l'essentiel [parite]

- Preuve : `core/app/quotas/service.py:151-168` lit des variables d'environnement globales ; tout est inerte sans `CORE_QUOTAS_ENABLED=true` (défaut `false`, `:196-197`). `check_quota_or_raise` n'accepte que items/collections (`:222-229`). `user_count` (`:169`) n'est jamais plafonné. Stockage sans lignes PostGIS (`:139-143`). `create_feature` (`core/app/features/routes.py:905`) et writer.collection sans plafond de lignes. Pas de quota de clés d'API, pipelines/runs, exports, secondes DuckDB, requêtes. `enforce_storage_quota` (`:246-268`) s'exécute après l'upload et rescanne jusqu'à 9 buckets S3 (O(objets)).
- Reproduction : `CORE_QUOTAS_ENABLED=true`, plafond d'items bas ; `POST /v1/collections/{id}/items` en boucle n'est jamais refusé ; `GET /admin/usage` ne bouge pas.
- Correctif : table `tenant_limits` (tenant_id, kind, soft, hard) avec repli sur l'env ; kinds `features`, `storage_db`, `users`, `api_keys`, `pipeline_runs_per_day` ; compteur de stockage incrémental ; exposition dans l'UI admin.

### I2 — Pas d'isolation de charge entre tenants [differenciateur]

- Preuve : `core/app/ratelimit/limiter.py:90-110` clé sur l'en-tête Authorization brut ou l'IP ; `core/app/ratelimit/models.py:3-5` sans tenant. Files procrastinate globales (`etl`, `dataexport`, `search` : `core/app/compliance/jobs.py:66`, `core/app/geocoding/jobs.py:142`). Seul verrou : par pipeline (`create_run_unless_active`, `core/app/pipelines/service.py:102`) ; aucun plafond de runs simultanés par tenant.
- Reproduction : lancer 100 runs de pipelines distincts depuis un tenant ; tous dans la file `etl` unique, sans fairness.
- Correctif : budget de rate-limit (tenant, groupe) ; plafond de runs/exports actifs par tenant à l'enfilage (via `tenant_limits`) ; `priority`/`lock=tenant_id` procrastinate ; métriques OTel étiquetées `tenant_id`.

### I3 — `audit_log` non immuable, sans rétention ni export, supprimé avec le tenant [parite]

- Preuve : `core/app/audit/models.py:15-32`, `core/app/audit/writer.py:7-29` : simple INSERT ; le rôle applicatif garde UPDATE/DELETE (aucun TRIGGER/REVOKE dans `alembic/versions` pour `audit_log`). Pas de chaînage de hachage, de rétention, d'export ni de SIEM ; seul lecteur : `core/app/usage/service.py`. `core/app/compliance/purge.py:385-390` supprime l'audit du tenant ; la trace `tenant.purge_requested` (`core/app/compliance/routes.py:128`) disparaît avec lui, ne reste que le `PurgeReceipt`.
- Reproduction : avec le rôle applicatif, `UPDATE audit_log SET actor_id=NULL WHERE action='user.erase'` réussit ; après `purge_tenant`, `SELECT count(*) FROM audit_log WHERE tenant_id=...` vaut 0.
- Correctif : rôle INSERT seul ou trigger BEFORE UPDATE/DELETE ; chaîne `prev_hash`/`hash` avec vérification ; `GET /v1/audit` et sink OTLP/webhook/syslog ; rétention par tenant ; exporter/signer l'audit dans le reçu de purge.

### I4 — Aucune défense en profondeur sur les tables du cœur [securite]

- Preuve : la RLS n'existe que sur les tables dynamiques (`core/app/collections/ddl.py:253-262`). Les ~45 tables du cœur n'ont aucune politique. `core/app/configs/repository.py:90-99` `get_config(session, config_id)`, `:353-360` `delete_config`, `list_revisions`, et `get_config_by_item(session, item_id)` appelé sans tenant par ~35 sites (`core/app/export/jobs.py:253`, `core/app/alerts/jobs.py:121`, `core/app/pipelines/jobs.py:38`, `core/app/mcp/tools/analytics.py:50`). Les appelants relus vérifient l'accès (ex. `configs/routes.py:211-216`) : pas de fuite exploitable trouvée, mais un oubli futur n'a aucun filet.
- Reproduction : `grep -rn 'get_config_by_item(session, ' core/app` ; aucun appel ne passe de `tenant_id`, la signature ne le permet pas.
- Correctif : `tenant_id` obligatoire dans ces fonctions ; RLS + `FORCE ROW LEVEL SECURITY` avec `app.tenant_id` posé par `get_session`/jobs, au moins sur items/configs/connector_secrets/api_keys ; test de contrat « toute table `tenant_id` a une policy ».

## Minor (non vérifiés)

### M1 — Reçus de purge lisibles inter-tenants par id [securite] (non vérifié)
`core/app/compliance/routes.py:163-190` : `get_purge_status` fait `session.get(PurgeReceipt, purge_id)` sans filtre tenant (`PurgeReceipt` sans `tenant_id`, `core/app/compliance/models.py`). Tout détenteur de `compliance.manage` connaissant l'UUID lit tenantSlug, requestedByUserId et counts. Id inconnu et en cours renvoient le même 202 (`:176-181`). Repro : tenant B, `GET /v1/compliance/purges/<uuid du tenant A>` -> 200. Correctif : filtrer par `tenant_slug`, 404 pour id inconnu.

### M2 — Espace de noms de tables global [dette] (non vérifié)
`core/app/collections/routes.py:456-463` : 409 « already registered by another tenant » (oracle d'existence). `Collection.id` = nom de table dans `public` ; `_ensure_quarantine` (`core/app/pipelines/collection_writer.py:128-143`) échoue en DuplicateTable si un autre tenant possède le nom ; `core/app/compliance/purge.py:261` DROP aussi une table préexistante enregistrée par l'admin. Repro : A enregistre `communes`, B tente la même -> 409. Correctif : préfixe/schéma par tenant ou séparer `Collection.id` de `table_name` ; ne DROP en purge que les tables `managed`.

### M3 — Pas de cycle de vie de tenant [differenciateur] (non vérifié)
`core/app/tenants/models.py:14-20` sans statut ; seul cycle de vie : `purge_tenant` irréversible (`core/app/compliance/purge.py:177-358`). Ni suspension, ni export de portabilité (RGPD Art. 20), ni restauration par tenant (`deploy/backup/restore.sh` restaure la base entière). La purge de `default` est suivie de sa recréation (`core/app/tenants/repository.py:17-47`). Repro : chercher `suspend`/`export_tenant` dans `core/app` : rien. Correctif : `tenants.status` contrôlé dans `get_current_user`, job `export_tenant`.

## Avantages et différenciateurs

- Isolation données solide : `tenant_id` sur 45 tables, RLS sur les tables de collection, `purge_tenant` couvrant toutes les tables à `tenant_id`, reçu de purge.
- Aucune requête par id sans garde exploitable depuis une route ; l'audit est écrit dans les services.
- Différenciateur potentiel (C1, I2, M3) : multi-organisation sur une instance avec vitrines publiques par domaine, face à ArcGIS Online/Enterprise ; quotas/crédits par tenant (I1) comme brique de gouvernance et de monétisation face à ArcGIS et FME Flow ; portabilité d'un tenant en documents déclaratifs.
