# d06 — Builder no-code, gabarits, embedding

Audit du 2026-10-16. Lecture seule : aucun test lancé, rien exécuté sur stack réelle. Les points « à confirmer » sont déduits de la lecture du code.

Périmètre : builder, CEL, variables, gabarits, embed, export d'app.

Bilan : 12 constats (1 Critical, 7 Important, 1 Important de performance, 3 Minor non vérifiés). Les 9 premiers ont été vérifiés dans le code. Les 3 Minor ne l'ont pas été.

## Critical

### C1 — Export d'app impossible pour toute source liée à un dataset (layer vide) — tag : bug

- **Preuve** :
  - `shell/src/builder/DataSourceSelect.tsx:35-40` crée la source `{type:'features', layer:'', datasetId: pk}`.
  - `core/app/appexport/guard.py` boucle sur `config.dataSources` avec `collection_id = source.layer`. `collections_repo.get_collection(..., collection_id='')` renvoie None, d'où « collection '' introuvable ».
  - `core/app/appexport/freeze.py:41-44` : `get_collection(..., collection_id=source.layer)` puis `refuse_if_collection_has_limits(..., collection_id=source.layer)`.
  - Ni `guard.py`, `freeze.py`, `snapshot.py` ni `jobs.py` ne mentionnent `datasetId`.
  - Le chemin Datasets→Widgets, celui que le produit promeut, ne s'exporte dans aucun des 3 modes, connecté compris, car la garde est commune. Les datasets SQL ou pipeline n'ont de toute façon pas de collection directe.
- **Reproduction** : créer une app, ajouter une source « dataset: » dans `DataSourceSelect`, enregistrer, lancer Exporter (statique, connecté ou autoporté). Le job échoue avec « collection '' introuvable ».
- **Correctif** :
  - Résoudre `datasetId` vers sa collection (config dataset `source == 'collection'`) avant garde, gel et snapshot, comme le fait `guest_access.resolve_guest_scope`.
  - Pour les datasets SQL ou pipeline : soit les matérialiser dans le snapshot, soit refuser avec un message explicite.
  - Ajouter un test de bout en bout d'export avec source dataset.

## Important

### I1 — Widget Bouton : `window.open(href)` sans validation de schéma — tag : sécurité

- **Preuve** :
  - `shell/src/builder/widgets/index.tsx:190-191` : `if (href) window.open(href, "_blank", "noopener")`.
  - Le jumeau Hero valide via `isSafeHref` (`hero.tsx:14-19`, `:139`, schémas http/https/mailto), avec un commentaire sur la frontière de confiance auteur→visiteur anonyme.
  - Aucune validation serveur : `document_validation.py::_http_url_error` ne couvre que les couches de `MapConfig`.
  - `href` peut être un `$expr` (`resolveExprBindings`), donc piloté par des données de collection, y compris une saisie publique.
  - Une URL `javascript:` ou `data:` s'exécute dans un contexte hérité, et `/embed/` est servi sur la même origine que le shell authentifié.
  - Cas jumeau du piège n°14 : garde posée sur Hero, jamais reportée.
  - L'exécution réelle de `javascript:` sous `noopener` varie selon le navigateur (**à confirmer**).
- **Reproduction** : widget `button` avec `href` = `javascript:alert(document.domain)` ou `{ $expr: record.url }` sur une donnée contrôlée par un tiers. Ouvrir `/embed/:token` et cliquer.
- **Correctif** :
  - Exporter `isSafeHref` dans un module partagé et l'appliquer au Bouton, ainsi qu'aux autres sorties d'URL d'auteur (image `src`, hero `backgroundImageUrl`).
  - Ajouter une validation de schéma côté `document_validation` (clés `href`/`ctaHref` des widgets).

### I2 — Les exports statique et autoporté ignorent les filtres de DataSource — tag : bug

- **Preuve** :
  - `core/app/appexport/freeze.py` appelle `select_features(..., filters=None, bbox=None, geom_intersects=None)` puis garde `query={**source.query, 'records': ...}`.
  - `shell/src/staticExport/StaticItemClient.ts` renvoie `source.query.records` sans appliquer les clés de filtre restantes.
  - `core/app/appexport/miniserver/main.py::list_items` ne lit que limit/offset/bbox. Les paramètres de filtre envoyés par `shell/src/api/domains/datasets.ts::_queryParams` sont ignorés en silence.
  - L'app exportée montre donc plus de données que l'app live, sans avertissement, jusqu'à 50 000 lignes de plus en statique.
- **Reproduction** : source `features` avec query `{statut:'ouvert'}`. En statique, le tableau liste toutes les lignes. En autoporté, `/v1/collections/x/items?statut=ouvert` ignore le filtre.
- **Correctif** :
  - Passer `source.query` (hors clés `STAT_KEYS`) en `filters` à `select_features` dans `freeze_config`.
  - Supporter filtres, `sortby` et `datetime` dans `miniserver/items.select_features`.
  - À défaut, avertir à l'export quand une clé non supportée est présente.

### I3 — Validation CEL partielle (serveur et shell), échecs silencieux à l'exécution — tag : bug

- **Preuve** :
  - `core/app/configs/document_validation.py:112-122` (`_item_errors`) ne contrôle que `visibleWhen` des items de premier niveau, plus `message.when` (l.160).
  - Ne sont pas validés : les `{$expr}` des props (`exprBindings.ts`), `criticalWhen`/`warningWhen` de l'indicateur (`indicator.tsx:217-218`), `visibleWhen` des champs de formulaire (`form.tsx:288`), `visibleWhen` des widgets imbriqués (tabs/modal/drawer).
  - `shell/src/builder/configExpressionErrors.ts` ne parcourt que les items de page, les colonnes calculées et les messages.
  - À l'exécution, `expr.ts::evaluateExpression` avale toute erreur (`console.warn`) et renvoie `undefined`. `WidgetHost.tsx:70-78` masque alors le widget, et une colonne calculée devient une cellule vide (`data.tsx:55`).
  - Un auteur, ou le copilote, le MCP ou l'import XLSForm qui contournent l'éditeur, ne voit aucune erreur : seulement un widget absent en production.
  - Deux moteurs distincts (cel-js 0.8.2 côté shell, cel-python côté serveur). Le serveur ne vérifie que la syntaxe (docstring l.25-28).
- **Reproduction** : `PUT /v1/configs/by-item/{id}` avec un widget `tabs` dont un item imbriqué a `visibleWhen:'vars.x =='` est accepté (200). En runtime, le widget disparaît sans trace visible.
- **Correctif** :
  - Parcours générique de tous les nœuds widget (`widget_nodes` existe déjà) pour valider `visibleWhen`, `$expr`, `*When` et les colonnes `expr`.
  - Remonter les erreurs d'évaluation en mode edit/preview (badge sur le widget).
  - Test de parité cel-js/cel-python sur un corpus d'expressions.

### I4 — Évaluation CEL sans cache (reparse à chaque appel) — tag : bug (performance)

- **Preuve** :
  - `shell/src/builder/expr.ts:12-14` appelle `evaluate(expr, ctx)` avec une chaîne.
  - `node_modules/cel-js/dist/lib.js::evaluate` fait `parse(expression)` (lexer et parseur chevrotain) à chaque appel, sans cache.
  - Appelants chauds : `data.tsx:49` (une évaluation par ligne×colonne calculée à chaque rendu, `render: row => cellValue` l.50-69), `WidgetHost.tsx:70` (par widget et par rendu), `popupTemplate.ts:94` (par placeholder), `labelSource` (par entité).
  - Un tableau de 1000 lignes avec 3 colonnes calculées reparse 3000 expressions par rendu, et le moindre changement de variable relance tout.
- **Reproduction** : table de 5000 lignes avec 3 colonnes `expr`, changer une variable liée. Le profil du main thread est dominé par `CelParser`.
- **Correctif** :
  - Mémoïser `parse(expr).cst` dans une Map bornée (l'API `evaluate` accepte déjà un CST).
  - Mémoïser aussi les résultats de colonnes par (ligne, vars), ou passer à `useMemo`.

### I5 — Portée invité d'un embed incomplète (couches additionnelles du widget carte) — tag : bug

- **Preuve** :
  - `core/app/configs/guest_access.py::resolve_guest_scope` ne parcourt que `root.config.dataSources` (datasetId ou layer) pour remplir `allowed_collection_ids`.
  - Le widget carte accepte des couches additionnelles `props.layers` (`mapWidget.tsx:353`, MapLayer vector/feature avec `collectionId`, `types.ts:463-503`) hors `dataSources`.
  - `collections/routes.py:392` n'autorise le jeton invité que pour les ids de la portée. Une couche privée du créateur du lien, légitimement visible via `can(created_by)`, répond 404 dans l'embed. Le comportement exact hors portée est **à confirmer en stack réelle** (retombée sur lecture publique seulement).
  - Idem pour les datasets référencés uniquement par des widgets imbriqués.
- **Reproduction** : app avec un widget carte dont `props.layers` contient une couche vecteur `collectionId=X` non liée à une dataSource. X est privée mais partageable par le créateur du lien. Ouvrir `/embed/:token` : couche vide ou 404 sur les tuiles.
- **Correctif** :
  - Étendre `resolve_guest_scope` avec un parcours de `widget_nodes` pour collecter `collectionId`/`datasetId` des props de widgets, en gardant le recoupement `can(created_by)`.
  - Test sur couche additionnelle.

### I6 — Liens d'embed : 30 jours max, aucune restriction d'origine, aucun mot de passe — tag : différenciateur

- **Preuve** :
  - `core/app/sharing/schemas.py:8` `_MAX_SHARE_LINK_TTL_DAYS = 30` et `share_links.py` `_MAX_TTL_SECONDS = 30*86400`. Un dashboard intégré dans un site tiers casse tous les mois et exige un nouveau jeton.
  - Pas de renouvellement : le jeton HS256 porte un `exp` figé et aucune route de prolongation n'existe.
  - Pas de `frame-ancestors` (grep core/shell/deploy : seulement le realm Keycloak). Le routeur shell-embed (`docker-compose.yml` ~1039) retire `X-Frame-Options` sans le remplacer : n'importe quel site peut encadrer un lien volé.
  - La liste des liens (`items/routes.py:295-313`) n'expose ni compteur de vues ni dernière utilisation.
  - ArcGIS offre l'embed permanent, la restriction par domaine et le contrôle d'accès.
- **Reproduction** : créer un lien avec `ttlDays=31` : 422. Embarquer le lien dans une page d'un autre domaine : il charge sans restriction.
- **Correctif** : ajouter `allowed_origins` (colonne `share_link` + CSP `frame-ancestors` dynamique ou middleware sur `/embed`), TTL « permanent » révocable, renouvellement, compteur de vues et dernier accès, mot de passe optionnel.

### I7 — Aucun cycle brouillon/publié — tag : différenciateur

- **Preuve** :
  - `core/app/configs/repository.py:44-49` `_latest_revision` (`ORDER BY version DESC`) et `get_config_by_item:101-108` : le runtime (`mode=runtime`, `configs/routes.py:~430`) lit toujours la dernière révision.
  - grep `published_revision|draft` dans `core/app/configs` et `items/models.py` : 0 résultat. L'historique et le rollback existent, mais pas de pointeur « publiée ».
  - Un auteur qui édite une app diffusée en embed publie chaque enregistrement. Experience Builder d'ArcGIS sépare brouillon et publication.
- **Reproduction** : ouvrir un lien `/embed/` dans un onglet, modifier et enregistrer l'app dans le builder. Le rechargement de l'embed montre l'état intermédiaire.
- **Correctif** : colonne `published_version` sur Config, route de publication avec audit, runtime/guest/export lisent la version publiée et l'éditeur la dernière. Bouton « Publier » et diff dans `ConfigHistoryPanel`.

### I8 — Variables d'app non pilotables de l'extérieur — tag : différenciateur

- **Preuve** :
  - `shell/src/builder/VariablesContext.tsx` : état purement React (`useState` initialisé par `initialValue`), aucune lecture de `location`/`searchParams`.
  - grep `postMessage`/`searchParams` dans `shell/src/builder`, `AppRenderer`, `EmbedPage.tsx` : 0 résultat.
  - Un site hôte ne peut ni pré-filtrer l'app (ex. `?commune=19`), ni écouter une sélection, ni envoyer un filtre. Aucun lien profond vers un état de l'app.
  - ArcGIS fournit les paramètres d'URL (Instant Apps) et la JS API/Experience SDK.
- **Reproduction** : ouvrir `/embed/:token?commune=19` : aucun effet. Aucun message reçu par `window.parent` lors d'un clic sur une entité.
- **Correctif** : variables marquées `urlParam`/`public` dans la config, hydratation depuis l'URL à l'initialisation, protocole postMessage minimal (`setVariable`, `onSelect`) validé contre les `allowed_origins` du lien.

## Minor (non vérifiés)

Ces trois constats n'ont pas été vérifiés dans le code.

### M1 — Allowlist de widgets d'export tenue à la main : `featureReport` refusé comme « extension tierce » — tag : dette

- **Preuve** : `core/app/appexport/guard.py` `_SUPPORTED_WIDGET_TYPES` (commentaire « à tenir en phase manuellement ») ne contient pas `featureReport`. Ce widget est pourtant enregistré dans `shell/src/builder/widgets/featureReport.tsx` et absent aussi de `_AUTHENTICATED_ONLY_WIDGETS`. En statique et autoporté, il est signalé « widget 'featureReport' non supporté (extension tierce) ». Aucun test de parité TS↔Python, contrairement à `templates.test.ts`.
- **Reproduction** : ajouter un widget `featureReport` à une app et exporter en statique : refus.
- **Correctif** : générer la liste depuis le registre TS (JSON committé comme `templates.data.json`), ou ajouter un test comparant `registerBuiltinWidgets()` à `guard.py`. Classer `featureReport` explicitement.

### M2 — Contextes d'expression incohérents selon le point d'évaluation — tag : polish

- **Preuve** : `ExprContext` (`expr.ts:5-10`) expose `vars, record, user, ctx`. `WidgetHost.tsx:70-78` passe `ctx: analyticsCtx` et `record: data?.records[0]?.properties`. `data.tsx:49-53` (colonnes calculées) n'envoie pas `ctx`. `ActionBus.ts:15` initialise `{vars:{}, user:{name:''}}`. `query_generation.py:110` déclare `{vars,user}` pour `visibleWhen` au copilote. Une expression `ctx.timeRange` fonctionne dans un `visibleWhen` et donne une cellule vide dans une colonne, sans erreur (cf. I3). Pour `visibleWhen`, `record` = premier enregistrement de la source du widget : sémantique non documentée et fragile au tri.
- **Reproduction** : colonne calculée `ctx.timeRange != null ? 'oui':'non'` : cellule vide quel que soit le contexte temporel.
- **Correctif** : un seul constructeur `buildExprContext(...)` partagé par tous les appelants. Documenter les variables par contexte dans l'éditeur (autocomplétion CEL) et aligner la liste du copilote.

### M3 — Gabarits d'app codés en dur uniquement — tag : différenciateur

- **Preuve** : `shell/src/builder/templates.ts` : 13 gabarits issus de `templates.data.json`, noms via `NAME_KEYS`. `core/app/configs/builder_templates.json` en copie identique. `core/app/mcp/tools/configs.py:232-246` `create_item(template=...)` ne résout que ces ids. grep `saveAsTemplate|tenantTemplate|custom.?template` dans `shell/src` et `core/app` : 0 résultat. Une organisation ne peut ni capitaliser une app réussie en modèle, ni partager de modèles. Le coût serait faible, tout objet étant déjà un document déclaratif. ArcGIS propose des modèles partagés dans l'organisation.
- **Reproduction** : dans le catalogue ou le builder, aucune action pour transformer une app existante en gabarit.
- **Correctif** : flag `is_template` sur l'item (config déclarative, sources rebindables) listé par `GET /v1/templates` avec le jeu builtin. Action « Enregistrer comme gabarit », exposition MCP `create_item(template=<item_id>)`.

## Avantages et différenciateurs

Atouts déjà en place :

- Un seul runtime `AppRenderer(config, mode)` pour apps et dashboards, avec modes edit/preview/runtime.
- Tout objet est un document déclaratif schématisé, donc pilotable par MCP et copilote.
- Moteur CEL partagé : `visibleWhen`, colonnes calculées, bindings `$expr`, variables typées.
- 13 gabarits livrés, avec test de parité TS↔JSON.
- Partage par lien signé dont la portée est recoupée avec les droits réels du créateur (`resolve_guest_scope`).
- Trois modes d'export (statique, connecté, autoporté), avec garde et gel de données.
- Historique de versions et rollback sur les configs.

Pour battre ArcGIS Experience Builder, à construire :

1. Liens d'embed durables, restreignables par origine (I6).
2. Cycle brouillon/publié (I7).
3. État d'app pilotable par URL ou postMessage (I8).
4. Gabarits propres au tenant (M3).
5. Export des sources dataset, la promesse Datasets→Widgets (C1).
