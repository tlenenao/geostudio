# Dimension d34 — Données ouvertes françaises

Audit en lecture seule, 2026-10-16. Aucun test lancé ; deux constats ont été vérifiés par exécution (curl sur data.gouv.fr, pyproj en local), les autres par lecture du code.

Bilan : 7 constats vérifiés (2 Critical, 5 Important, 0 Minor). Les constats Minor non vérifiés sont au nombre de 0.

## Critical

### C1 — `transform.buffer` en mètres passe par EPSG:3857 : distances fausses d'environ 50 % en métropole

- Tag : bug
- Preuve : `core/app/pipelines/compiler.py:191-192` : `ST_Transform(ST_Buffer(ST_Transform(geometry, src, 'EPSG:3857', true), distance), 'EPSG:3857', src, true)`. Web Mercator dilate les distances de 1/cos(lat), soit x1,52 à 48,85 N. Un tampon « 100 m » mesure donc environ 66 m au sol à Paris et environ 72 m à Marseille. Le libellé du schéma (`core/app/pipelines/analysis.py:79`) annonce « en mètres (reprojection EPSG:3857 interne) » : le défaut est présenté comme une fonctionnalité. Lambert-93 (EPSG:2154) est pourtant géré partout ailleurs.
- Reproduction : pipeline reader -> `transform.buffer` `{unit: 'meters', distance: 100}` sur un point à Paris (EPSG:4326). Mesurer le rayon du résultat avec `ST_Distance` en EPSG:2154 : environ 66 m, pas 100 m.
- Correctif : choisir un CRS métrique local. 2154 si l'emprise est en métropole ; projection DOM adaptée (2972, 2975, 5490, 4471...) ou UTM ; ou aeqd centré sur le centroïde (déjà présent dans `core/app/pipelines/ops/reliquats.py:100`). À défaut, `ST_Buffer` sur geography. Ajouter un test de distance réelle. Auditer aussi les autres unités « meters ».

### C2 — Écriture OGC Features sur une collection stockée en EPSG:2154 : GeoJSON lon/lat estampillé 2154 sans `ST_Transform`, lecture par défaut en Lambert-93

- Tag : bug
- Preuve : `core/app/features/repository.py:425` (`_geometry_sql`), 449, 490, 517 et 565 : `ST_SetSRID(ST_GeomFromGeoJSON(:__geom), :__srid)` avec `__srid=info.srid`. GeoJSON est en lon/lat par contrat, et `SUPPORTED_EPSG` (`core/app/ogc_crs.py:7`) inclut 2154, qui est donc annoncé comme CRS de stockage possible. Symétriquement, `repository.py:263-264` : sans paramètre `crs`, `ST_AsGeoJSON(geom)` sort les coordonnées brutes du stockage (mètres Lambert) sans en-tête Content-Crs (`routes.py:403` ne l'émet que si `out_srid` est fourni). Une collection BD TOPO/PCI enregistrée en 2154 est donc corrompue en écriture (point à 2,3 m / 48,8 m de l'origine Lambert) et non conforme RFC 7946 en lecture. `ingestion/importer.py:558` refuse l'ajout sur 2154 (« reprojection à ajouter si besoin réel »).
- Reproduction : enregistrer une table PostGIS existante en SRID 2154 comme collection. `POST /v1/collections/{id}/items` avec `geometry {type: Point, coordinates: [2.35, 48.85]}`. Relire la géométrie en SQL : elle vaut `POINT(2.35 48.85)` dans le SRID 2154, donc au mauvais endroit. `GET` sans `crs` : coordonnées en mètres.
- Correctif : dans `_geometry_sql`, remplacer par `ST_Transform(ST_SetSRID(GeomFromGeoJSON, 4326), :__srid)` quand `srid != 4326`, avec option Content-Crs/`crs` en entrée (Part 2). Lecture par défaut : `ST_Transform` vers 4326. Reporter sur les jumelles : `straddle_gate` (l.507), `collection_writer.py:563`, cql2. Lever aussi la restriction d'ajout d'`importer.py:558`.

## Important

### I1 — NTF / Lambert zones (27571-27575, Lambert II étendu) sans grille IGN : repli silencieux à ~2 m

- Tag : bug
- Preuve : `core/app/ingestion/parsers.py:404-415` : `pyproj.Transformer.from_crs(src, WGS84, always_xy=True)` sans `area_of_interest`, sans `only_best`, sans `PROJ_NETWORK`. Exécuté en local (pyproj 3.7.2, réseau désactivé) : `Transformer.from_crs(27572, 4326)` -> « Lambert zone II + NTF (Paris) to NTF + NTF to WGS 84 (1) », accuracy = 2.0 m. La grille `fr_ign_ntf_r93.tif` (précision ~0,05 m) n'est installée ni dans `core/Dockerfile` ni dans `deploy/` (grep proj/grid vide). Le repli est choisi sans avertissement : un cadastre ou des fonds IGN anciens en NTF sont décalés de 1-2 m sans que l'utilisateur le sache. DuckDB `ST_Transform` (`pipelines/compiler.py:207`) et PostGIS ont les mêmes limites.
- Reproduction : `cd core && uv run python -c "from pyproj import Transformer; t=Transformer.from_crs(27572,4326,always_xy=True); print(t.description, t.accuracy)"` affiche accuracy 2.0.
- Correctif : embarquer proj-data (paquet fr_ign) ou `PROJ_DATA` avec les grilles françaises (`fr_ign_ntf_r93`, RAF18b/20 pour l'altimétrie) dans les images core/worker/postgis. Utiliser `only_best=True` ou journaliser `transformer.accuracy` et exposer un avertissement d'import au-delà de 0,5 m. Documenter.

### I2 — Connecteur « CKAN / data.gouv » inopérant sur data.gouv.fr

- Tag : parite
- Preuve : `core/app/harvest/connectors/ckan.py:64` : endpoint = `scheme://netloc/api/3/action/package_search`. Vérifié par curl le 2026-10-16 : `https://www.data.gouv.fr/api/3/action/package_search` -> 404 `application/json`, alors que `https://www.data.gouv.fr/api/1/datasets/` répond (API uData). data.gouv.fr n'est plus un CKAN. Le moissonnage échoue en `HarvestFetchError` à la racine (`ckan.py:113`). De plus, seules les ressources GeoJSON/GPKG/SHP sont copiables (l.29) : les CSV/Parquet/ZIP, majoritaires sur data.gouv, sont exclus, et `_extract_bbox` (l.178) retombe sur le monde entier.
- Reproduction : créer une source de moissonnage de type `ckan` avec l'URL `https://www.data.gouv.fr/` ; lancer le moissonnage : erreur de document racine illisible.
- Correctif : ajouter un connecteur « udata » (`/api/1/datasets/?page_size=&q=`, ressources avec format, url, schema, `spatial.geom`/zones, organisation, licence mappée DCAT) et le pré-déclarer dans un catalogue de sources françaises (data.gouv, geo.data.gouv, Géoplateforme). Gérer les CSV avec colonnes lat/lon ou adresse via `transform.geocode`.

### I3 — `reader.wfs` : une seule requête, sans pagination ni signal de troncature

- Tag : bug
- Preuve : `core/app/pipelines/ops/wfs.py:41` (`maxFeatures <= 100000`), 91-98 : un unique GetFeature avec count/maxFeatures, aucun `startIndex`, aucune lecture de `numberMatched`/`numberReturned`, aucune alerte si `len(features) == maxFeatures`. Les serveurs GeoServer (dont `data.geopf.fr/wfs`, plafond serveur typique de quelques milliers d'entités) coupent à leur limite propre : le pipeline réussit avec un jeu partiel (ex. 5 000 bâtiments sur 40 000 d'une commune). Le docstring (l.1-12) signale en outre un risque d'inversion lat/lon non traité.
- Reproduction : `reader.wfs` sur `https://data.geopf.fr/wfs/ows`, typeName `BDTOPO_V3:batiment`, maxFeatures 100000 : la réponse est coupée par le plafond serveur, le run est vert sans avertissement.
- Correctif : paginer (WFS 2.0 `startIndex` + `count`, tri stable) jusqu'à `numberMatched` ou au plafond ; échouer ou marquer `truncated` si `numberReturned < numberMatched`. Ajouter un paramètre bbox/`cql_filter` (code INSEE) pour borner la requête, et valider l'ordre des axes en normalisant selon la première coordonnée.

### I4 — Géocodage BAN : score, type, code INSEE et code postal jetés ; tout résultat est « trouvé »

- Tag : differenciateur
- Preuve : `core/app/geocoding/provider.py:36-39` : `GeocodeResult = {label, lon, lat}` uniquement. `BanGeocoder.search` (l.60-70) ne lit que `properties.label` : score, type (housenumber/street/municipality), citycode, postcode, context sont perdus. Aucun paramètre autocomplete, type, citycode, postcode, ni biais lat/lon. `geocoding/batch.py:80-86` : un résultat vaut « trouvé » dès qu'il existe, sans seuil. Un lot d'adresses incomplètes retourne des centroïdes de commune présentés comme des points d'adresse ; on ne peut ni filtrer ni mesurer la qualité. Le lot fait N requêtes GET (cadence 40/s) alors que la Géoplateforme propose `/geocodage/search/csv`.
- Reproduction : `transform.geocode` sur une colonne contenant seulement « Rue de la Paix » : statut « trouvé », point arbitraire, aucune colonne de score.
- Correctif : étendre `GeocodeResult` (score, type, citycode, postcode) ; `transform.geocode` émet `geocode_score`/`geocode_type`/`geocode_citycode` ; seuil `minScore` -> statut « incertain ». Ajouter les filtres citycode/postcode et le mode CSV de la Géoplateforme pour les gros lots.

### I5 — Aucune intégration native Cadastre / INSEE / BD TOPO / COG ni CRS DOM

- Tag : differenciateur
- Preuve : grep sur `core/app` et `shell/src` (hors tests) : aucun connecteur, catalogue ou référentiel pour PCI/EDIGEO/Etalab, INSEE (COG, IRIS, carreaux 200 m), BD TOPO ou RPG. `core/app/ogc_crs.py:7` : `SUPPORTED_EPSG = (4326, 3857, 2154)` ; `core/app/ows/wms.py:19-22` : `CRS_TABLE` à 4 entrées ; `ows/wms_routes.py:107` : domaine codé en dur pour 3 SRID. Les CRS DOM (2972 Guyane, 2975 Réunion, 4471 Mayotte, 5490 Antilles) et CC9 zones (3942-3950) ne sont pas servis par WMS/OGC Features ; WFS (`ows/wfs.py:93`) n'annonce que 2154. L'import (`ingestion/parsers.py:468-489`) accepte pourtant ces CRS.
- Reproduction : `GET /v1/collections/{id}/items?crs=EPSG:2975` -> 400 `invalid_crs`.
- Correctif : rendre `SUPPORTED_EPSG` et `CRS_TABLE` pilotés par la config de collection (CRS de stockage + liste française pré-déclarée), avec domaines de validité tirés de pyproj (`area_of_use`). Livrer un « pack France » : sources pré-déclarées (Géoplateforme WFS/WMTS, geo.api.gouv.fr communes/départements, API carto Cadastre, INSEE COG/IRIS), jointure COG -> contours, et `transform.geocode` mutualisé.

## Avantages et différenciateurs

- Le géocodeur BAN est déjà migré vers la Géoplateforme (`data.geopf.fr`), avec garde SSRF et épinglage DNS. Le lot et le reverse existent.
- Les constats « sécurité » du périmètre sont propres : la garde d'egress du géocodage est correcte.
- Lambert-93 (2154) est géré dans l'import, le WFS et les pipelines ; l'import accepte aussi les CRS DOM et CC9.
- Principal différenciateur à construire : un « pack France » natif (Cadastre, INSEE/COG, BD TOPO, connecteur udata, catalogue de sources françaises). Aucun concurrent généraliste ne l'offre et le socle (moissonnage, pipelines, géocodage) est en place.
