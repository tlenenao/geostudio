## Constats Important (vérifiés)

### 1. Chromium du worker d'export sans filtrage de sortie ni CSP : SSRF interne via configs de carte/app — Important — `securite`

**Fichiers** : `core/app/export/jobs.py:182`, `:188`, `:260` ; `core/app/configs/schemas.py:134-143` ; `docker-compose.yml:768` ; `martin-config.yaml`.

**Preuve** : `jobs.py:182` lance `chromium.launch(headless=True)` puis `page.goto(url)` ligne 188, sans `page.route`, sans allowlist, sans proxy sortant. La cible est `SHELL_BASE_URL` (`http://shell:8300`, `docker-compose.yml:768`), qui contourne Traefik : la CSP enforcing (img/connect-src) n'est donc jamais posée sur cette page. Le worker est sur `gis-net`. La page rend des configs écrites par des utilisateurs : `MapLayer.tilesUrl`, `url` et `dataUrl` sont des `str` libres (`schemas.py:134-143`). Un Créateur peut faire récupérer par le navigateur du worker n'importe quelle URL interne (core:8200, minio:9000, titiler, valhalla, keycloak, martin:3000) et obtenir le rendu dans le PDF/PNG exporté.

Aggravant potentiel : Martin tourne avec la chaîne `postgresql://gis:...` (propriétaire des tables, RLS activée mais pas FORCE, `ddl.py:253`) et `martin-config.yaml` ne désactive pas l'auto-publication. S'il auto-publie les tables, une couche `kind=vector` avec `tilesUrl=http://martin:3000/<table>/{z}/{x}/{y}` sortirait les données de n'importe quel tenant sans `can()` ni RLS. **L'auto-publication par défaut de Martin v0.18 n'a pas été vérifiée dans ce run** : ce volet est une hypothèse, le volet SSRF est lu au code.

**Reproduction** : avec `CORE_EXPORT_ENABLED=true` et le profil `export`, créer une carte avec une couche raster/vector pointant vers `http://martin:3000/<table_collection>/{z}/{x}/{y}` (ou un GeoJSON interne), lancer `POST /v1/export`, ouvrir le PNG/PDF. Vérifier aussi dans les logs de l'export-worker les requêtes sortantes vers `http://169.254.169.254/` ou `http://minio:9000/`.

**Correctif** : dans `_launch_and_navigate`, créer un contexte avec `page.route('**/*')` qui n'autorise que l'origine du shell, l'URL publique du cœur et une allowlist d'hôtes de tuiles/fonds de carte (calculée comme la CSP), et refuse les plages internes après résolution DNS. Faire naviguer le worker via l'entrée Traefik pour obtenir la même CSP, ou poser la même CSP côté nginx du shell. Dans `martin-config.yaml`, mettre `auto_publish: false` ou retirer Martin du réseau accessible au worker ; ajouter `FORCE ROW LEVEL SECURITY` ou un rôle Martin non propriétaire.

### 2. Génération de la CSP dynamique cassée par un hôte malformé : YAML invalide et plantage de la tâche toutes les 5 min — Important — `bug`

**Fichiers** : `core/app/security/csp_hosts.py:23`, `:29` ; `core/app/security/traefik_render.py:42`, `:58` ; `core/app/security/jobs.py:23` ; `core/app/mapicons/basemap_routes.py:41` ; `core/app/configs/schemas.py:139`.

**Preuve (reproduite en local avec les vraies fonctions)** :
1. `_origin()` renvoie `scheme://hostname` sans valider le hostname : `https://a"b.example/x` donne l'hôte `a"b.example`. `render_dynamic_conf` l'insère tel quel dans une chaîne YAML entre guillemets (`traefik_render.py:58-63`) et `yaml.safe_load` échoue (« expected ... block mapping »). Le docstring affirme que c'est impossible (lignes 5-11).
2. `https://x:abc/` passe le validateur de style de fond de carte (`basemap_routes.py:41-49`, qui ne lit que `hostname`) et les layers de MapConfig n'ont aucune validation d'URL. Or `_origin()` évalue `parsed.port`, qui lève `ValueError: Port could not be cast to integer value`. L'exception remonte dans `refresh_csp_dynamic_conf_task` (`jobs.py:23`, aucun try/except). Un seul enregistrement piégé empêche toute mise à jour de la CSP pour toute l'instance, tant qu'il existe.

**Reproduction** : `PUT` d'une MapConfig avec `layers=[{"id":"l","title":"t","kind":"raster","url":"https://x:abc/{z}/{x}/{y}.png"}]` (rôle Créateur), puis attendre le cron `*/5` : la tâche échoue en `ValueError` à chaque tick. Variante : un hôte contenant un guillemet rend le fichier YAML illisible pour Traefik. Le comportement exact de Traefik face à ce fichier n'est pas vérifié (il garde l'ancienne config, ou perd l'en-tête CSP).

**Correctif** : dans `_origin()`, valider l'hôte par regex `^[a-z0-9.-]+$` (ou IDNA) et le port par `int` borné, avec try/except et abandon silencieux de l'entrée. Dans `compute_csp_allowlist`, ignorer chaque entrée invalide au lieu de tout échouer. Émettre la valeur YAML via `json.dumps` (ou `yaml.safe_dump`) plutôt qu'un gabarit de chaîne. Ajouter une validation d'URL (http/https, hôte valide) sur `MapLayer.url/tilesUrl/dataUrl` et `MapTerrain.tilesUrl`.

### 3. CSP enforcing élargie par des données de n'importe quel Créateur, sans frame-ancestors/base-uri/form-action — Important — `securite`

**Fichiers** : `core/app/security/service.py:36`, `:54-66` ; `core/app/security/csp_hosts.py:44-65` ; `core/app/security/traefik_render.py:42-50`.

**Preuve** : `compute_csp_allowlist` (`service.py:54-66`) lit la dernière révision de TOUTES les cartes (`_latest_map_config_bodies`, toutes les configs `kind=map`, tous tenants, brouillons compris), les `HarvestSource` et les `TenantBasemap`, et injecte chaque origine dans `img-src` ET `connect-src` de la CSP servie à tous (`traefik_render.py:42-50`). Quiconque peut enregistrer une carte avec une couche raster `url=https://attaquant.tld/{z}/{x}/{y}.png` ouvre une destination d'exfiltration (fetch/img) pour tous les utilisateurs de l'instance, ce qui annule l'intérêt de la CSP comme confinement après une XSS. La CSP générée ne contient pas `base-uri`, `form-action` ni `frame-ancestors` (le clickjacking ne repose que sur `X-Frame-Options` de Traefik). `style-src` garde `'unsafe-inline'`.

**Reproduction** : compte Créateur, enregistrer une carte avec une couche raster `url=https://evil.example/{z}/{x}/{y}.png`. Après le cron suivant, le fichier `csp-dynamic-conf` contient `https://evil.example` dans `connect-src` et `img-src` pour toute l'instance.

**Correctif** : ne dériver `connect-src`/`img-src` que d'hôtes validés par un admin (sources de moissonnage approuvées, fonds de carte du tenant déclarés sous privilège admin), ou faire proxifier par le cœur les tuiles externes. Ajouter `base-uri 'self'; form-action 'self'; frame-ancestors 'self'` (ou la CSP embed dédiée). Ne plus lire les brouillons.

### 4. Soumission publique : corps multipart lu et écrit sur disque avant tout contrôle, sans plafond global — Important — `securite`

**Fichiers** : `core/app/public_submit/routes.py:62-74`, `:132-150` ; `core/app/public_submit/service.py:82` ; `core/app/main.py:311-318` ; `core/app/mapicons/routes.py:76-90`.

**Preuve** : `POST /v1/public/submit/{token}` est la seule route d'écriture sans authentification. Ses paramètres `Form(...)`/`File(None)` (`routes.py:65-68`) sont parsés par Starlette/python-multipart avant l'exécution du handler : la partie fichier est déversée dans un `SpooledTemporaryFile` (disque au-delà de 1 Mio). `ip_limiter.allow(ip)` (`routes.py:74`), `find_token` et le plafond de 25 Mo (`_store_attachment`, ligne 143) ne s'exécutent qu'après réception complète du corps, y compris pour un jeton invalide. Le seul plafond de corps du dépôt est `config_body_limit`, limité à `^/v1/configs` (`main.py:98` et `311-318`). Aucun `buffering`/`maxRequestBodyBytes` Traefik n'est configuré (grep négatif sur les yml/toml). `mapicons/routes.py:76-90` reconnaît cette limite et la renvoie au reverse-proxy. Un anonyme peut remplir `/tmp` du conteneur core avec des envois répétés ou concurrents de plusieurs Go.

**Reproduction** : `curl -F payload='{}' -F file=@<fichier de 5 Go> https://host/v1/public/submit/gss_bidon`, en parallèle depuis plusieurs connexions : l'espace disque du conteneur core augmente avant le 404.

**Correctif** : middleware ASGI de plafond de `Content-Length` (411 sans l'en-tête, 413 au-delà) sur toutes les routes multipart, avec un plafond serré (quelques Mo plus 25 Mo) pour `/v1/public/*`. Poser en plus Traefik `buffering.maxRequestBodyBytes`. Passer le rate-limit de `/v1/public/submit` dans le middleware (`route_group`) pour qu'il précède le parsing.

### 5. Jeton d'export : pleine identité pendant 2 min, dans l'URL, accepté par le shell comme n'importe quel bearer — Important — `securite`

**Fichiers** : `core/app/export/jobs.py:258-263` ; `core/app/auth/export_tokens.py:39-90` ; `core/app/auth/dependency.py:229-243` ; `shell/src/auth/exportAwareToken.ts:19-22` ; `shell/src/auth/RequireAuth.tsx:21-30`.

**Preuve** : `mint_export_token` émet un JWT HS256 `{tenant_id,user_id,job_id}`. `decode_export_token` ne vérifie jamais `job_id` ni une portée, et `get_current_user` (`dependency.py:229-243`) renvoie le `User` complet : toutes les routes, y compris admin/écriture, sont ouvertes avec ses privilèges pendant le TTL. Le jeton est passé en query string (`jobs.py:263`, `?exportToken=...`) : il apparaît dans l'historique de Chromium et dans les logs d'accès du shell/Traefik. Côté shell, `buildExportAwareToken` (`exportAwareToken.ts:19-22`) utilise TOUT `?exportToken=` présent dans l'URL comme jeton d'API et `RequireAuth` saute la redirection de connexion : un lien piégé `https://app/maps/X?exportToken=<jeton valide de l'attaquant>` fait opérer la session de la victime sous le compte de l'attaquant (fixation de session / login-CSRF : la victime crée ses données dans le compte de l'attaquant). Le jeton coexiste avec le rendu de contenu auteur (constat 1). Pas de `require=['exp']` dans le decode (`export_tokens.py:62`), ni de claim `nbf`/`aud`.

**Reproduction** : (1) ouvrir `/apps/<id>?exportToken=<access token OIDC de l'attaquant>` dans le navigateur d'une victime déjà connectée : les appels du shell partent avec le jeton de l'attaquant. (2) Lire les logs d'accès du shell pendant un export : la query string contient le jeton complet.

**Correctif** : lier le jeton à une route et une méthode (GET lecture seule, items/collections/configs de l'item exporté, `job_id` vérifié contre un job `running`) ou lui donner un scope lecture seule. Le transmettre par en-tête via Playwright (`extra_http_headers` / `add_init_script` écrivant `sessionStorage`) plutôt que par l'URL. Dans le shell, n'honorer `exportToken` que si `exportRender=1` et un marqueur propre au worker, et le retirer de l'URL (`history.replaceState`). Imposer `options={'require':['exp','iat']}`.

### 6. Clés d'API sans portée : une clé hérite de tous les privilèges de son créateur — Important — `differenciateur`

**Fichiers** : `core/app/apikeys/service.py:124-153` ; `core/app/apikeys/models.py` ; `core/app/auth/dependency.py:208-214`.

**Preuve** : `authenticate()` renvoie le `User` créateur sans filtre : ni scopes, ni mode lecture seule, ni limite par route/collection/IP, ni budget propre (le limiteur clé sur l'en-tête `Authorization` brut, donc par clé, mais avec les mêmes budgets que tout utilisateur). Une clé d'Administrateur est donc un administrateur complet pendant 365 jours ; la seule protection est `forbid_api_key`, qui l'empêche de créer d'autres clés. Les surfaces qui créent d'autres accès persistants restent ouvertes à une clé volée : webhooks sortants, jetons de soumission, `PipelineWebhookToken`, liens de partage, utilisateurs/rôles. ArcGIS (clés d'API à portée de privilèges et référents autorisés) et les jetons fins de GitHub/Stripe sont la référence.

**Reproduction** : créer une clé d'API avec un compte Administrateur et appeler `POST /v1/roles`, `POST /v1/webhooks` ou `POST /v1/users` : tout est accepté.

**Correctif** : ajouter `ApiKey.scopes` (liste de privilèges + lecture seule), `ApiKey.allowed_cidrs` et un budget propre. Dans `authenticate()`, intersecter les privilèges du créateur et les scopes, refuser les méthodes d'écriture en lecture seule. Rendre l'expiration par défaut courte (90 jours) et obligatoire.

### 7. Journal d'audit pauvre et mutable — Important — `differenciateur`

**Fichiers** : `core/app/audit/writer.py:6-31` ; `core/app/audit/models.py:15-32` ; `core/app/usage/routes.py:34`, `:93`.

**Preuve** : `write_audit` n'enregistre que tenant, acteur, action, objet et payload (`writer.py:6-31`). `AuditLog` (`models.py:15-32`) n'a ni adresse source, ni user-agent, ni request/trace id, ni hash chaîné. Les 158 appels `write_audit` tracent des écritures : aucune trace des refus `can()`/403 ni des échecs d'authentification (grep d'événements deny/login négatif). Les lectures de données ne sont pas auditées. Les migrations (0004, 0039, 0045, 0050, 0054) ne posent aucune restriction UPDATE/DELETE : le rôle applicatif peut réécrire l'historique. Les seules routes d'exposition sont `GET /usage/tasks` et `/usage/summary` : pas d'export CSV/JSON, pas de streaming SIEM ni syslog. Écrite dans la même transaction que l'action, l'entrée disparaît en cas de rollback. Esri (audit/logs ArcGIS Enterprise) et FME Flow couvrent ces cas.

**Reproduction** : lire `app/audit/models.py` et chercher un champ `ip` : absent. Faire un GET refusé (403) sur une collection privée : aucune ligne `audit_log` créée.

**Correctif** : ajouter `ip`, `user_agent`, `request_id` (middleware) et `result` (success|denied). Auditer les refus `can()`/`require_privilege` et les échecs d'authentification dans une transaction séparée. Rendre la table append-only (`REVOKE UPDATE, DELETE` pour le rôle applicatif, sauf procédure RGPD dédiée) avec chaîne de hash. Ajouter `GET /v1/audit/export` (privilège dédié) et un connecteur webhook/syslog.

## Constats Minor (NON VÉRIFIÉS : lus au code, ni reproduits ni confirmés par un second passage)

### 8. Upload présigné sans plafond de taille côté S3, quotas désactivés par défaut, miniatures non bornées — Minor — `securite` — non vérifié

**Fichiers** : `core/app/ingestion/storage.py:110-122` ; `core/app/ingestion/routes.py:80-92` ; `core/app/quotas/service.py:245-268` ; `core/app/items/routes.py:185`, `:209`.

**Preuve** : `generate_presigned_put_url` ne signe aucune limite de `Content-Length` : l'URL de 15 min accepte jusqu'à 5 Go. `CORE_UPLOAD_MAX_BYTES` n'est vérifié qu'à la lecture (`download_object`, `head_object`) et `enforce_storage_quota` s'exécute après le dépôt (`quotas/service.py:248`) et seulement à la création du job ; les objets orphelins restent jusqu'à l'expiration de 7 jours du bucket. `quotas_enabled()` est faux par défaut (`CORE_QUOTAS_ENABLED=false`). `upload_thumbnail` lit `file.file.read()` sans borne avant de tester la taille (`items/routes.py:185`) puis stocke et ressert le `content_type` fourni par le client tant qu'il commence par `image/` (ligne 209) sans `nosniff` : `image/svg+xml` est accepté tel quel (non exploitable en navigation directe car la route exige un bearer, mais fragile).

**Reproduction** : `POST /v1/uploads/presign` (rôle `data.manage`), puis `curl -T fichier_de_3Go` sur `uploadUrl` : l'objet est accepté sans job ni contrôle de quota.

**Correctif** : `generate_presigned_post` avec condition `content-length-range`, ou vérification côté cœur par webhook S3 / balayage borné d'orphelins. Activer des quotas par défaut sûrs en production. Lire la miniature par morceaux (comme `mapicons._read_bounded`), sniffer le type (PNG/JPEG/WebP uniquement), ajouter `X-Content-Type-Options: nosniff` et `Content-Disposition`.

### 9. Garde d'egress : NAT64 `64:ff9b::/96` considéré global et 6 copies divergentes — Minor — `dette` — non vérifié (mesure ponctuelle seulement)

**Fichiers** : `core/app/pipelines/egress.py:48-51` ; `alerts/egress.py:34-37` ; `harvest/egress.py:51-54` ; `copilot/egress.py:54-57` ; `search/egress.py:59-62` ; `geocoding/egress.py:32-34` ; `core/app/net_pin.py`.

**Preuve** : `_is_internal` est copié à l'identique dans 6 modules (le contrat de couches interdit l'import croisé ; `net_pin.py` ne partage que l'épinglage). Il repose sur `ipaddress.is_global` : mesuré, `64:ff9b::7f00:1` donne `is_global=True` (les adresses `::ffff:x.x.x.x` sont correctement refusées). Sur un hôte IPv6-seul avec passerelle NAT64, un DNS contrôlé par l'attaquant renvoyant un AAAA `64:ff9b::a9fe:a9fe` passe la garde et atteint 169.254.169.254. Toute correction doit être reportée à la main 6 fois (piège n°14 du dépôt). L'exploitation sur un déploiement NAT64 réel n'a pas été testée.

**Reproduction** : `python -c "import ipaddress;print(ipaddress.ip_address('64:ff9b::a9fe:a9fe').is_global)"` affiche `True`. Tester ensuite un `reader.connector.rest` avec un hôte dont l'AAAA est cette adresse, sur un déploiement NAT64.

**Correctif** : déplacer `is_internal_ip` dans un module feuille sans dépendance applicative (comme `net_pin.py`), importé par les 6 gardes ; y refuser explicitement `64:ff9b::/96`, `64:ff9b:1::/48`, `2002::/16` (6to4) en extrayant l'IPv4 embarquée avant test. Ajouter un test paramétré partagé.

### 10. Rate limiters en mémoire de process : soumission publique non partagée entre réplicas, repli local du limiteur Postgres — Minor — `parite` — non vérifié

**Fichiers** : `core/app/public_submit/service.py:48-82` ; `core/app/ratelimit/limiter.py:228-262` ; `core/app/main.py:337-343`.

**Preuve** : `HourlyLimiter` (`public_submit/service.py:48-82`) est un dict en mémoire : avec les réplicas HA (ARC-32) le budget de 100 requêtes/h/IP est multiplié par le nombre de réplicas, alors que le middleware partagé `PgRateLimiter` existe. Le middleware général échoue en ouvert vers le compteur mémoire après 5 s de panne Postgres (`limiter.py:228-262`), et seules 8 familles de routes sont limitées : `GET /v1/collections/*/items`, `/tiles`, `/stac` et `/dcat` anonymes, `/v1/items` et les routes WMS/WFS publiques n'ont aucun budget. Leur seul plafond est le `statement_timeout`.

**Reproduction** : 2 réplicas core avec `CORE_RATELIMIT_BACKEND=postgres`, 150 `POST /v1/public/submit/<jeton>` depuis une IP répartis sur les 2 réplicas : aucun 429 avant 200.

**Correctif** : brancher `HourlyLimiter` sur la table `rate_limit_counters` (fenêtre horaire). Ajouter un groupe `anon-read` (budget généreux par IP) pour les routes lisibles sans authentification.

### 11. Authentification : base interrogée avant validation du jeton, pas d'exigence `exp`, tenant unique par défaut — Minor — `dette` — non vérifié

**Fichiers** : `core/app/auth/dependency.py:205`, `:248-254` ; `core/app/sharing/share_links.py:62` ; `core/app/auth/export_tokens.py:48`, `:62`.

**Preuve** : `get_current_user` appelle `get_or_create_default_tenant(session)` (ligne 205) dès qu'un en-tête Bearer est présent, avant toute validation de jeton (clé `gsk_`, jeton d'export, OIDC) : chaque requête avec Bearer bidon coûte au moins un SELECT (et un INSERT au premier appel) sans budget (hors routes à groupe). `jwt.decode` est appelé sans `options={'require':['exp']}` (`dependency.py:248-254`, `share_links.py:62`, `export_tokens.py:62`) : un jeton signé sans `exp` n'expire jamais (exploitable seulement si le secret HS256 ou l'IdP en produit un). `is_export_token` (`export_tokens.py:48`) classe tout en-tête `alg=HS256` comme jeton d'export : les 3 secrets HS256 (export, partage, admin-tools) ne doivent jamais être égaux ; rien ne le vérifie au démarrage.

**Reproduction** : `curl -H 'Authorization: Bearer x' https://host/v1/items` en boucle : une requête SQL par appel avant le 401. Avec `CORE_EXPORT_TOKEN_SECRET` égal à `CORE_SHARE_LINK_TOKEN_SECRET`, vérifier que `typ` reste le seul garde-fou.

**Correctif** : valider d'abord la forme et la signature du jeton, puis résoudre le tenant (ou le mettre en cache mémoire). Ajouter `options={'require':['exp']}` à tous les `jwt.decode`. Au démarrage, refuser des secrets HS256 identiques entre fonctions (comparaison de hash).

### 12. Pas de MFA applicative ni de politique de session / rotation des clés — Minor — `differenciateur` — non vérifié

**Fichiers** : `core/app/auth/dependency.py:187-257` ; `core/app/apikeys/service.py:23-26` ; `core/app/auth/routes.py`.

**Preuve** : l'identité est entièrement déléguée à Keycloak : le cœur ne lit ni le claim `acr`/`amr` ni `auth_time`, donc il ne peut pas exiger une authentification forte pour les actions sensibles (purge de tenant, rotation du secret maître, création de clé d'API, export massif). `MAX_LIFETIME_DAYS=365` sans rotation guidée ni alerte d'expiration. Aucune politique de session (durée absolue, déconnexion globale, révocation de tous les jetons d'un utilisateur anonymisé hors clés d'API).

**Reproduction** : lire `dependency.py` : aucune lecture de `acr`/`amr` ; les routes `compliance.manage` et secrets acceptent un jeton OIDC de session standard.

**Correctif** : exiger un step-up (claim `acr` ou `auth_time` < 5 min) sur les actions à fort impact (`compliance.manage`, rotation des secrets, création de clé d'API, `admin.users.manage`), configurable. Notifications d'expiration de clé et durée par défaut de 90 jours.

## Avantages et différenciateurs

Socle solide, vérifié dans le code :
- Requêtes SQL paramétrées partout ; CQL2 borné.
- Sandbox DuckDB verrouillée : `getenv` absent, secrets masqués. Mesuré : aucune fuite d'environnement (piste écartée, voir ci-dessous).
- XML parsé avec `defusedxml` ; SVG assaini ; URLs présignées pour les fichiers.
- Rate limiter conscient du proxy ; aucun secret par défaut dans les compose.
- Garde d'egress SSRF présente sur pipelines, alertes, moissonnage, copilote, recherche et géocodage, avec épinglage DNS (`net_pin.py`).

Différenciateurs à construire face à ArcGIS Enterprise / FME Flow : clés d'API à portée (constat 6), audit riche, immuable et exportable vers un SIEM (constat 7), step-up MFA sur actions sensibles et politique de session (constat 12), CSP dont l'allowlist est validée par un admin (constat 3).

Pistes testées et écartées (pas des constats, aucune vulnérabilité observée) :
- SSRF via `xsi:schemaLocation` GML : aucune requête sortante observée.
- Fuite d'environnement via DuckDB : aucune fuite mesurée.
