# d18 — Performance et scalabilité

Audit du 2026-10-16. Méthode : lecture du code et micro-mesures locales (bases jetables supprimées, aucun fichier source modifié). Réserves : DuckDB mesuré sur disque local (pas de latence S3), machine WSL partagée. Le code est la preuve, pas les specs.

Synthèse : 3 Critical, 3 Important, 1 Minor (non vérifié). Les deux plus graves sont mesurés.

## Critical

### C1 — CDC wal2json v1 : une transaction = un message ; au-delà de 1 Go le slot se bloque et le WAL grossit sans borne
- Tag : bug
- Preuve : `core/app/cdc/consumer.py:220-222` démarre la réplication avec `options={"pretty-print":"0","include-pk":"1"}`, sans `format-version=2` : wal2json émet un document JSON par transaction. `core/app/cdc/main.py:171-176` fait `json.loads(payload)` du document entier. Relecture du code confirmée (consumer.py:220-222). Mesure sur base jetable (wal2json réel) : 200 000 insertions (4 colonnes) = 1 message de 63 466 697 octets (317 o/ligne). Une transaction de 2,4 M lignes échoue avec « out of memory / Cannot enlarge string buffer containing 1073741675 bytes ». `max_slot_wal_keep_size` = -1 sur le postgis de la stack : rétention du WAL illimitée. L'import (`core/app/ingestion/importer.py:296-416`) insère tout en une seule transaction.
- Reproduction : base wal2json, créer une table et un slot, INSERT 2,4 M lignes (~560 o) en une transaction, puis `pg_logical_slot_get_changes(slot,NULL,NULL,'pretty-print','0','include-pk','1')`. Plafond vers 3,4 M lignes à 317 o/ligne, ~300 k lignes pour des polygones à 100 sommets (~3 Ko EWKB hexa). Un UPDATE de masse tombe sous le même plafond.
- Correctif : `format-version=2` avec `include-transaction=false` (un message par changement) et adapter `decode_wal2json_message`. Poser `max_slot_wal_keep_size` dans le compose (10-20 Go) avec alerte sur le retard de slot. Dégradation : si une transaction dépasse le plafond, invalider la collection et la rebackfiller par snapshot au lieu de rejouer le même message en boucle.
- Fichiers : `core/app/cdc/consumer.py`, `core/app/cdc/main.py`, `core/app/ingestion/importer.py`, `docker-compose.yml`.

### C2 — Lecture du lac : `row_number()` sur tout l'historique à chaque requête, même avec snapshot (34 fois plus lent qu'un anti-join)
- Tag : differenciateur
- Preuve : `core/app/analytics/aggregate.py:571-577` construit `current AS (SELECT * FROM raw QUALIFY row_number() OVER (PARTITION BY pk ORDER BY ...) = 1)` (relu). `raw` est l'union du snapshot (déjà unique par pk, `snapshot.py:136-141`) et du delta brut : le fenêtrage ne sert qu'aux pk du delta. Ce CTE est consommé par `/aggregate`, `/profile`, `sql_sandbox`, les alertes (`alerts/jobs.py:198,382`), `reader.collection` (`pipelines/runtime.py:302-307`, aperçu compris) et le moteur de pipelines. Micro-mesure DuckDB (4 threads, 2 Go, snapshot + 1000 lignes de delta) : 10 M lignes, fenêtre 1,89 s contre anti-join 0,06 s ; 40 M lignes, fenêtre 8,23 s (RSS 2,1 Go, limite atteinte) contre 0,24 s. Extrapolation : ~20 s à 10^8, au bord du timeout de 30 s (`duckdb_conn.py:65`). Sans snapshot (défaut, `CORE_LAKE_SNAPSHOT_ENABLED=false`, `docker-compose.yml:562`), la fenêtre porte sur tout l'historique.
- Reproduction : parquet d'un snapshot de N lignes uniques + delta de 1000 lignes ; comparer `QUALIFY row_number() OVER (PARTITION BY id ORDER BY _lsn DESC, _seq DESC)=1` sur l'union avec `snapshot ANTI JOIN delta_pks UNION ALL delta dédupliqué`, puis `GROUP BY cat`. Script : scratchpad/m1.py.
- Correctif : dans `_dedup_cte`, avec snapshot : `(SELECT * FROM snap ANTI JOIN delta_pks USING(pk)) UNION ALL BY NAME (delta dédupliqué par fenêtre)`. Activer le snapshot par défaut (au moins au-delà de N fichiers). Pousser bbox et prédicats avant dédoublonnage quand c'est sûr (pk ou colonnes immuables).
- Fichiers : `core/app/analytics/aggregate.py`, `analytics/snapshot.py`, `pipelines/runtime.py`, `cdc/jobs.py`.

### C3 — Import de fichier : tout en mémoire puis dupliqué (pic 2,9 Go pour 281 Mo), worker limité à 2 Go
- Tag : bug
- Preuve : `core/app/ingestion/importer.py:216-277` (`_load_rows`) fait `list(parse_*(content))` sur le fichier entier en bytes, une 2e liste (force_2d, l.270-273), puis `importer.py:393-405` une 3e liste `params` de dicts avec le WKT. `parsers.py:158-183` : `json.loads` du texte complet. Limite d'upload 512 Mo (`ingestion/storage.py:154`) ; `docker-compose.yml:533` : `mem_limit: ${WORKER_MEM_LIMIT:-2g}` (relu). Mesure : GeoJSON 1 M points × 10 propriétés (281 Mo) : parse 16,9 s, RSS 2 566 Mo après parse, 2 931 Mo après params (27 s). Dans un worker à 2 Go : OOM kill. L'insertion n'est pas le goulot (64 k lignes/s en executemany comme en COPY).
- Reproduction : FeatureCollection de 1 M points (~281 Mo) via `POST /v1/uploads`, worker au défaut : OOM. Local : scratchpad/gen.py puis m3.py (`PYTHONPATH=core`).
- Correctif : import via DuckDB spatial (`ST_Read`/`read_parquet`/`read_csv`) ou ogr2ogr, en flux par lots de 10-50 k lignes (itérateur, jamais `list()`). Typage par échantillon. Refus précoce (413) selon taille × facteur d'expansion mesuré. À défaut, relever `WORKER_MEM_LIMIT` et documenter le plafond réel (~500 k points par Go).
- Fichiers : `core/app/ingestion/importer.py`, `parsers.py`, `storage.py`, `docker-compose.yml`.

## Important

### I1 — Tuiles : agrégation seulement à z ≤ 7, coût O(lignes de l'enveloppe), sans pré-agrégation ni cache serveur
- Tag : differenciateur
- Preuve : `core/app/features/tiles.py:441-444` : sonde d'agrégation tentée seulement si `0 < tile_agg_max_zoom() >= z` (défaut 7, `docker-compose.yml:367`). Au-delà, tuile brute `ORDER BY pk LIMIT 5000` (`tiles.py:106-122`) : seules les 5000 premières lignes par id, signalé par `X-Tile-Truncated` (`tiles.py:497-498`), affiché en badge dans `LayersPanel.tsx:391-400`. L'agrégation lit toute l'enveloppe sous `TILE_AGG_STATEMENT_TIMEOUT_MS` = 3 000 ms, 503 + Retry-After au dépassement (`tiles.py:451-464`). EXPLAIN ANALYZE sur 3 M points : tuile z0 = 1 250 ms (~0,42 µs/ligne, un worker) ; 3 s ≈ 7 M lignes. `docs/revue/2026-10-16-mesures-rev283-1e6.md` ne mesure que 10^6. Pas de cache serveur : seulement `Cache-Control max-age=300` (`tiles.py:487`).
- Reproduction : table de 10 M points, `GET /v1/collections/{id}/tiles/0/0/0.mvt` : 503 à chaque appel, 3 s de CPU Postgres brûlées par appel, accessible à un anonyme sur collection publique (rate limit seul). À z=9 sur 10^7 points : 5000 points affichés (plus petits id).
- Correctif : pré-agréger (cellules H3/quadkey par zoom bas, rafraîchies par CDC ou à l'import). Étendre l'échantillonnage à tous les zooms (grille agrégée ou échantillon uniforme par hash de pk, pas les 5000 premières lignes). Cache de tuiles serveur (clé = collection + version de table + z/x/y). Signalement visible côté widgets.
- Fichiers : `core/app/features/tiles.py`, `docker-compose.yml`, `shell/src/map/LayersPanel.tsx`.

### I2 — `/aggregate`, `/profile`, reader de pipeline : aucun cache ni limite de concurrence, 5 passes de footers Parquet par requête
- Tag : bug
- Preuve : `core/app/features/routes.py:435-480` : route `def` synchrone, `conn_factory()` ouvre un `duckdb.connect` neuf à chaque appel (`duckdb_conn.py:26-65`, 83 ms, 2 Go, 4 threads). Par appel : `_has_any_file` (glob S3), `latest_snapshot` (glob + `parquet_metadata`), `_has_seq_column` ×1-2 et `_lake_column_names` ×1-2 (`read_parquet(glob, union_by_name=true) LIMIT 0`, lit tous les footers, `aggregate.py:476-498,540-560`), la requête, puis `lake_as_of` (`aggregate.py:659-676`). Mesure locale avec 2 000 fichiers : `LIMIT 0` union_by_name = 0,128 s, `max(_ts)` = 0,081 s ; sur S3 chaque footer est une requête HTTP. Fichiers bruts jamais supprimés après snapshot (`cdc/jobs.py:131-148` ne purge que les anciens snapshots). Aucun Semaphore ni cache dans `app/analytics`/`features` ; `ratelimit/limiter.py:24-26` reconnaît 1 requête par widget ; le conteneur core n'a pas de `mem_limit`.
- Reproduction : collection à ~2 000 fichiers CDC bruts, dashboard de 8 widgets, 20 spectateurs : 160 connexions DuckDB concurrentes, chacune relisant 5 fois les footers.
- Correctif : cache résultat par (collection, corps haché, asOf/dernier flush CDC) à TTL court + single-flight. Cache par collection de la liste de fichiers/colonnes/`_seq` invalidé par version du lac. Semaphore (~cœurs/4) et `mem_limit` sur core. Purger/archiver les fichiers bruts couverts par le snapshot.
- Fichiers : `core/app/features/routes.py`, `analytics/aggregate.py`, `analytics/duckdb_conn.py`, `analytics/snapshot.py`, `docker-compose.yml`.

### I3 — Backfill CDC : `SELECT *` de toute la table en mémoire dans le thread de réplication
- Tag : bug
- Preuve : `core/app/cdc/backfill.py:127-160` exécute `SELECT * FROM public.<table>` avec `.mappings().all()`, normalise en dicts puis liste de `ChangeRow`, tout en mémoire. `core/app/cdc/main.py:228-241` l'appelle de façon synchrone dans `_on_message` (donc dans la boucle de lecture du slot, sans keepalive), puis `buffer.add` de toutes les lignes, flushées en un seul fichier (`buffer.py:34-44`, `FLUSH_MAX_ROWS=500` ne vaut qu'entre deux messages). Aucun `mem_limit` sur `cdc-worker` (seul `worker`, `docker-compose.yml:533`). Une collection de quelques millions de lignes retarde la réplication de toutes les autres et peut provoquer un OOM hôte.
- Reproduction : collection de 5 M lignes avant que le CDC la voie (ou redémarrage du cdc-worker sur base ancienne) : le premier message WAL sur la table déclenche le backfill complet en mémoire.
- Correctif : curseur serveur (`yield_per`/`stream_results`, lots de 10 k), un parquet par lot avec flush intermédiaire, dans un job procrastinate dédié plutôt que dans le handler WAL, avec keepalive. `mem_limit` sur cdc-worker.
- Fichiers : `core/app/cdc/backfill.py`, `main.py`, `buffer.py`, `docker-compose.yml`.

### I4 — Aperçu de pipeline : `reader.collection` matérialise toute la collection dédoublonnée en TEMP TABLE
- Tag : differenciateur
- Preuve : `core/app/pipelines/runtime.py:296-307` : `CREATE TEMP TABLE view AS {dedup_cte} SELECT <pk + toutes colonnes + geometry> FROM live`, sans filtre ni LIMIT. `preview_pipeline` (`runtime.py:1001-1091`) place cette matérialisation avant `_execute_transform_chain(..., stop_at=up_to)`, bornée seulement par un timer de 30 s (`_preview_timeout_s`, l.997-998) ; `IN_PREVIEW` n'est jamais consulté par `_materialize_reader`. Coût du constat C2 plus écriture de toutes les colonnes (memory_limit 2 Go, `max_temp_directory_size` 5 Go, `duckdb_conn.py:52-57`). À 10^7+ lignes l'aperçu expire systématiquement.
- Reproduction : pipeline `reader.collection` (10^7 lignes) → `transform.filter`, aperçu du nœud filter : 10^7 lignes matérialisées avant filtrage, timeout à 30 s.
- Correctif : en aperçu, échantillon borné (dernier snapshot limité à N lignes ou `USING SAMPLE`) et poussée des projections/prédicats dans le reader. Matérialisation complète réservée aux runs, avec projection des seules colonnes utilisées.
- Fichiers : `core/app/pipelines/runtime.py`, `core/app/analytics/aggregate.py`.

### I5 — Aucun index d'attribut, aucun ANALYZE après import, pas de `statement_timeout` sur GET /items
- Tag : parite
- Preuve : `core/app/collections/ddl.py:262-290` ne crée que `(tenant_id)` et le GiST de géométrie ; aucun autre `CREATE INDEX` sur les tables de collection, aucune API/UI pour en déclarer. `importer.py` n'exécute jamais `ANALYZE`. `features/repository.py:352` : `ORDER BY ... LIMIT :__l OFFSET :__o`, offset sans plafond (`routes.py:321`, `ge=0` seulement), CQL2 (`cql2.py`) et sortby libres. Seule la tuile pose un `statement_timeout` (`tiles.py:345-355`, `wms_routes.py:147`) ; `rls.py` n'en pose pas. Mesure sur 3 M lignes sans index : COUNT capé `cat='c7'` 98 ms ; `ORDER BY v DESC LIMIT 101` 148 ms ; même requête à OFFSET 2 000 000 : 665 ms ; `count(*)` sur `v>990` 105 ms. Acceptable à 3 M, linéaire : ~3 s à 10^8 sur une route anonyme pour les collections publiques.
- Reproduction : `GET /v1/collections/{id}/items?sortby=-v&offset=90000000&filter=<CQL2 coûteux>` sur 10^8 lignes ; aucune annulation côté serveur au-delà du timeout client.
- Correctif : `statement_timeout` transaction-local (5-10 s) dans `rls_scope` pour toute lecture publique/utilisateur ; plafonner l'offset (curseur au-delà de 10 000) ; `ANALYZE` après import/ajout massif ; API « index d'attribut » (`collections/{id}/indexes`, btree/trgm/BRIN en `CONCURRENTLY`) ; index composite `(tenant_id, pk)` ou partitionnement par tenant.
- Fichiers : `core/app/collections/ddl.py`, `features/repository.py`, `routes.py`, `rls.py`, `ingestion/importer.py`.

## Avantages et différenciateurs

- Insertion SQL saine : 64 k lignes/s en executemany comme en COPY, l'insertion n'est pas le goulot.
- Tri/filtre PostGIS sur 3 M lignes en 100-660 ms sans index d'attribut ; plans Seq Scan/top-N parallèles.
- Export en flux (CSV/GeoJSON) non limitant à ce volume.
- Architecture lac (CDC → GeoParquet + snapshot + DuckDB) : le correctif C2 est local (une CTE) et rapporte un facteur ~34 mesuré.
- Tuiles : sonde + agrégation + `statement_timeout` + 503/Retry-After déjà en place, il manque la pré-agrégation et le cache.
