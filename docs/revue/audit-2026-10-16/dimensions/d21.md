## Critical

### C1 — SLO latence API Features : regex de route périmée depuis SP-57b, l'alerte ne peut jamais se déclencher [bug]

- Preuve : `deploy/observability/grafana/provisioning/alerting/rules.yaml:17` filtre `http_route=~"/collections/.*/items.*"`. Les routeurs sont montés sous `v1_router = APIRouter(prefix="/v1")` (`core/app/main.py:416-417` et suivants) ; `features/routes.py:316` déclare `/collections/{collection_id}/items`, donc `http_route` vaut `/v1/collections/{collection_id}/items`. Un matcher `=~` Prometheus est ancré aux deux bouts : la série est vide, `histogram_quantile` renvoie NaN et `noDataState: OK` (`rules.yaml:29`) classe la règle « OK » en permanence. Faux vert depuis la migration `/v1`.
- Reproduction : servir du trafic sur `GET /v1/collections/x/items`, exécuter la requête de `rules.yaml:17` dans Grafana : vide. Avec `/v1/collections/.*/items.*` : non vide.
- Correctif : `http_route=~"/v1/collections/.*/items.*"`. Ajouter un test qui extrait les `http_route` des alertes et vérifie leur existence dans `app.routes` (piège n°14, jumelle oubliée après SP-57b). Vérifier aussi la règle Martin (ligne ~112) et les dashboards.

### C2 — Toutes les alertes SLO ont `noDataState: OK` : core, worker ou exporter arrêtés = aucune alerte [bug]

- Preuve : `rules.yaml:29`, `:56`, `:85`, `:112` (et `:141`). Si le core tombe ou si l'export OTLP casse, les séries disparaissent (taux de 5xx = division par série vide, backlog = `sum()` vide) : « no data » donc OK. La panne totale est le cas où l'alerte devrait sonner le plus fort. Aucune règle `absent()`/`up`, aucune sonde de `/health`.
- Reproduction : `docker compose stop core worker` avec le profil `observability` : après 5 min, toutes les règles restent à OK.
- Correctif : `noDataState: Alerting` pour les règles 5xx et backlog, ou règle `absent(http_server_duration_milliseconds_count)` for 5m en critical ; règle de fraîcheur des données du collecteur.

## Important

### I1 — Aucune alerte sur le retard CDC alors que la jauge `geostudio.cdc.lag_seconds` existe [parite]

- Preuve : `register_cdc_lag_gauge` (`core/app/observability.py:198`) est appelée par le cdc-worker (`cdc/main.py:134`). `grep cdc_lag|cdc.lag` dans `deploy/` et `docs/runbooks` : 0 résultat ; `dashboards/custom/jobs.json` n'a qu'un panneau (`geostudio_jobs_backlog`). Un worker vivant mais en retard, ou un slot de réplication qui gonfle le WAL, est invisible.
- Reproduction : `grep -rn cdc_lag deploy/` ne renvoie rien.
- Correctif : règle `slo-cdc-lag` (`max(geostudio_cdc_lag_seconds) > 300 for 10m`), panneau, entrée de runbook ; exposer la taille du slot (`pg_replication_slots`) via postgres-exporter.

### I2 — Le backlog de jobs ne compte que todo/doing : aucun signal sur les échecs ni la durée [parite]

- Preuve : `observability.py:175` `WHERE status IN ('todo','doing')` ; seul autre compteur métier : `geostudio.apps.runtime_executions` (`configs/routes.py:43`). Aucun compteur de runs de pipeline, imports, exports, livraisons d'alertes, moissonnages ; pas d'âge du plus ancien job. Seuil backlog > 50 « provisoire » (`rules.yaml:62`). Un job qui échoue en boucle ou reste bloqué en `doing` n'est pas détecté.
- Reproduction : faire échouer un import : `geostudio_jobs_backlog` ne bouge pas.
- Correctif : `geostudio.jobs.failed` (gauge par queue/task, 24 h), `geostudio.jobs.oldest_age_seconds`, histogramme `geostudio.job.duration` dans `otel_worker_middleware` (`observability.py:127`), `pipeline_runs{status}` depuis la table `pipeline_runs`.

### I3 — Les logs ne sont jamais exportés par OTLP : Loki ne reçoit rien de GeoStudio [bug]

- Preuve : `setup()` installe `TracerProvider` et `MeterProvider` avec exporteurs OTLP (`observability.py:94-95`) mais aucun `LoggerProvider`/`OTLPLogExporter` (grep dans `core/app` : 0 résultat). Logs uniquement sur stdout (l.103-107). Le pipeline logs d'`otelcol-config.yaml:81-84` et l'exporteur Loki sont câblés pour rien ; la corrélation `trace_id` n'est exploitable que via `docker logs`.
- Reproduction : profil `observability`, générer des erreurs core, Grafana > Explore > Loki : aucun flux `service_name=geostudio-core`.
- Correctif : `LoggingHandler` OTel (`opentelemetry.sdk._logs`) sur le logger racine quand l'endpoint est défini, ou receiver `filelog`/promtail ; provisionner la source Loki avec lien `trace_id` vers Tempo.

### I4 — L'export-worker n'exporte aucune télémétrie en compose (OTEL_* absent), contrairement à Helm [bug]

- Preuve : seules occurrences d'`OTEL_` dans `docker-compose.yml` : core (414-415), worker (669-670), cdc-worker (805-806). Le service `export-worker` (l.746+) n'a ni `OTEL_EXPORTER_OTLP_ENDPOINT` ni `OTEL_SERVICE_NAME` ; il importe `app.jobs`, donc `observability.setup()` tourne sans endpoint (rien n'est envoyé). Le chart Helm positionne `OTEL_SERVICE_NAME` pour l'export-worker (`export-worker.yaml:33`) : incohérence entre cibles. Les jobs les plus lourds (Chromium) sont les seuls sans trace.
- Reproduction : `docker compose --profile observability --profile export config | grep -c OTEL` : 3 services seulement (vérification partielle : 6 lignes `OTEL` au total dans le fichier).
- Correctif : ajouter les deux variables (`OTEL_SERVICE_NAME: geostudio-export-worker`) ; test de déployabilité exigeant `OTEL_*` sur tout service important `app.jobs` (piège n°2).

### I5 — Données d'otel-lgtm non persistées (ni compose ni Helm) [dette]

- Preuve : `docker-compose.yml:858-902` : seuls des fichiers de config sont montés, aucun volume sur `/data` (Prometheus, Loki, Tempo) alors que postgis/minio/backup ont des volumes nommés. Helm : strategy `Recreate`, zéro `volumeMounts`/PVC (`otel-lgtm.yaml:15-40`). Tout redémarrage efface métriques, traces, état des alertes ; fenêtres SLO glissantes et post-mortems impossibles.
- Reproduction : `docker compose up -d --force-recreate otel-lgtm` : historique antérieur vide.
- Correctif : volume nommé sur `/data`, PVC optionnel (`observability.persistence.size`), documenter la rétention.

### I6 — Alertes sans destinataire par défaut, aucun runbook d'astreinte [parite]

- Preuve : défaut compose `http://127.0.0.1:1/grafana-alert-webhook-not-configured` (`docker-compose.yml:880`) ; un seul contact point webhook (`contactpoints.yaml:9`), une seule politique (`policies.yaml:8`), pas d'e-mail/Slack. Le module `alerts` du cœur (e-mail/webhook) n'est pas réutilisé pour les incidents d'exploitation. 10 runbooks, aucun « que faire quand `slo-api-5xx-rate` sonne » ; pas d'annotation `runbook_url` ; seule mention : un paragraphe du runbook de restauration (`2026-07-24-restauration-sauvegardes.md:45`). Rien dans `GET /v1/instance/status` n'avertit.
- Reproduction : `.env.example` inchangé + profil `observability` : alertes en firing, webhook en échec, sans visibilité côté GeoStudio.
- Correctif : indicateur `alerting_destination_configured` dans `/v1/instance/status`, runbook par alerte (`runbook_url`), contact point e-mail (SMTP du cœur), option de routage vers les notifications in-app des admins.

### I7 — Aucune observabilité par tenant ni par fonctionnalité [differenciateur]

- Preuve : ressource OTel limitée à `service.name` (`observability.py:90-91`), sans `service.version`/`deployment.environment`/tenant ; `FastAPIInstrumentor.instrument_app` sans hook de requête (l.110-113) donc pas d'attribut `tenant_id`/user/item sur les spans ; aucun `request_id`/`X-Request-ID` (grep : 0). Dashboards purement techniques (core, jobs, martin, postgres, `core.json:20`). Pas de vue santé pipeline/moissonnage/alerte, ni quotas par tenant, ni coût DuckDB, alors que `pipeline_runs`, `audit_log`, usage et quotas existent.
- Reproduction : chercher dans Tempo les traces d'un tenant : impossible.
- Correctif : `service.version` et `deployment.environment` dans la Resource ; `server_request_hook` posant `tenant_id` + `X-Request-ID` renvoyé dans les erreurs RFC 7807 ; dashboards « Automatisation » (runs par statut, P95 par op, rejets) et « Tenants » (usage vs quotas) ; exemplars.

## Avantages et différenciateurs

- Existant solide : OTel natif sur core/worker/cdc-worker, profil `observability` packagé (`grafana/otel-lgtm`), 4 dashboards et 4-5 règles SLO provisionnés, jauges métier (backlog jobs, retard CDC), `GET /v1/instance/status`, logs JSON avec `trace_id`.
- Aucun de ces points n'est aujourd'hui un différenciateur face à ArcGIS Enterprise Monitor ou FME Flow : c'est de l'observabilité d'infrastructure générique.
- Le différenciateur potentiel est l'observabilité propre à la plateforme (runs de pipeline, qualité/rejets, moissonnages, alertes, quotas et usage par tenant), dont les données existent déjà en base (I2, I7).
