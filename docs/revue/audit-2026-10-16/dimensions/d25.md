# Dimension d25 — Chaîne d'approvisionnement et licences

Audit du 2026-10-16. Lecture du code uniquement, aucun test exécuté, aucun fichier source modifié.
Limite : l'état réel des tags GHCR et des CVE n'a pas été interrogé.

## Synthèse

Le socle est solide : actions GitHub épinglées par SHA, signature cosign keyless par digest, vérification des signatures avant la production du compose épinglé, `pip-audit` strict, `npm audit` avec liste d'exceptions justifiées. Les trous portent sur la reproductibilité des images secondaires, l'absence de contrôle automatique des licences, les écosystèmes non surveillés (Rust, images des compose) et des scans purement informatifs.

Comptage : 0 Critical, 6 Important (vérifiés), 2 Minor (non vérifiés).

## Constats Important

### 1. L'image export-worker est construite sans lockfile : dépendances flottantes, hors pip-audit
- Sévérité : Important. Tag : `securite`. Statut : vérifié.
- Fichiers : `deploy/export-worker/Dockerfile:18-19`, `core/Dockerfile:51`, `.github/workflows/_build-and-push.yml:62-64`, `.github/workflows/ci.yml:251`.
- Preuve : `core/Dockerfile:51` fait `uv export --frozen` à partir de `uv.lock`. `deploy/export-worker/Dockerfile:18-19` ne copie que `pyproject.toml` (`COPY pyproject.toml ./` puis `uv pip install --system --no-cache -r pyproject.toml`). Le contexte de build est `./core`, mais `uv.lock` n'est jamais copié. Les bornes de `pyproject` sont de type `>=` : chaque rebuild résout les dernières versions. L'image exécute Chromium sur du contenu utilisateur. `pip-audit` (`ci.yml:251`) audite l'environnement verrouillé, pas ce qui est installé dans cette image. Le commentaire du Dockerfile core (j03-018) décrit ce défaut comme corrigé pour core seulement.
- Reproduction : construire l'image à deux dates différentes ; `pip list` diffère alors que `uv.lock` n'a pas bougé.
- Correctif : copier `uv.lock`, faire `uv export --frozen --no-dev --no-hashes -o /tmp/r.txt && uv pip install -r /tmp/r.txt` comme pour core. Idéalement, installer un groupe d'extras réduit (playwright et le strict nécessaire) plutôt que les ~100 dépendances de core.

### 2. Aucun contrôle automatique des licences (GPL/AGPL/LGPL) Python, npm ou Rust
- Sévérité : Important. Tag : `securite`. Statut : vérifié.
- Fichiers : `.github/workflows/ci.yml`, `core/pyproject.toml`, `shell/package.json`, `desktop-etl/src-tauri/Cargo.toml`.
- Preuve : aucune occurrence de `pip-licenses`, `license-checker`, `cargo-deny` ou `deny.toml` dans `.github/`, `core/pyproject.toml`, `shell/package.json` ou `desktop-etl` (grep négatif). Les licences ne sont vérifiées qu'à la main (commentaires `vérifiée sur PyPI` dans `pyproject.toml`), et `test_deployability.py` ne garde que le cas mc/MinIO. Le projet affirme Apache-2.0 et diffuse des images publiques. Il embarque des paquets LGPL (pymssql, psycopg, par ex. `pyproject.toml:69`) et des bundles PyInstaller (sidecar desktop). Une dépendance transitive GPL ou AGPL ajoutée par une montée de version passerait sans alerte. Les SBOM existent mais aucune règle ne les lit.
- Reproduction : ajouter une dépendance GPL-3.0 à `pyproject.toml` ; aucun job CI n'échoue.
- Correctif : job CI de licences : `pip-licenses --fail-on='GPL;AGPL'` avec allowlist LGPL documentée, `license-checker --failOn` pour npm, `cargo deny check licenses` pour desktop-etl. Garder les exceptions dans un fichier versionné, comme `check-npm-audit.mjs`.

### 3. Dependabot et audits ignorent le sidecar Rust, desktop-etl/e2e, les images des compose et le chart Helm
- Sévérité : Important. Tag : `securite`. Statut : vérifié.
- Fichiers : `.github/dependabot.yml:18-72`, `desktop-etl/src-tauri/Cargo.toml`, `desktop-etl/e2e/package.json`, `docker-compose.yml:49,116,830,859,914,951,1062`, `docker-compose.prod.yml:350,360`, `deploy/helm/geostudio/values.yaml:178,183`.
- Preuve : `dependabot.yml` ne déclare que `uv` (/core), `npm` (/shell), `github-actions` et `docker` sur 9 répertoires (Dockerfile uniquement). Aucune entrée `cargo` (desktop-etl/src-tauri, qui contient un `Cargo.lock`) ni `npm` pour desktop-etl/e2e. L'écosystème `docker` ne lit pas les `image:` des compose ni des values Helm. Ces images ne sont jamais mises à jour automatiquement : edoburu/pgbouncer:1.22.1-p0, maplibre/martin:v0.18.0, gis-ops/valhalla:3.5.1, grafana/otel-lgtm:0.11.4, postgres-exporter, keycloak:24.0.5, traefik, tecnativa/docker-socket-proxy:0.3.0, tailscale:v1.102.3. Aucun `cargo audit` dans le CI (les workflows desktop-etl ne contiennent que `cargo install`).
- Reproduction : lire `dependabot.yml` ; aucune entrée cargo ni docker-compose.
- Correctif : ajouter les écosystèmes `cargo` (/desktop-etl/src-tauri), `npm` (/desktop-etl/e2e) et `docker-compose` pour les deux compose ; ajouter `cargo audit` ou `cargo deny check advisories` au CI ; pour Helm, un `docker` sur le chart ou centraliser les tags dans un seul fichier.

### 4. Scans de vulnérabilités d'image uniquement informatifs, et absents du canal edge
- Sévérité : Important. Tag : `securite`. Statut : vérifié.
- Fichiers : `.github/workflows/_build-and-push.yml:160-175,199-205`, `.github/workflows/publish-edge.yml:45`, `.github/workflows/release.yml:219`.
- Preuve : Trivy tourne avec `continue-on-error: true` et `exit-code: "0"` (`_build-and-push.yml:167-175`) : la publication n'est jamais bloquée, même sur une CVE CRITICAL corrigeable. L'étape SBOM est aussi `continue-on-error`, et l'attestation est sautée silencieusement si le fichier est absent (ligne 212). `publish-edge.yml:45` fixe `run_scans: false`, ce qui supprime scan, SBOM et attestation. Or `edge` est l'image tirée par les déploiements Proxmox/OCI à chaque merge sur main. Une image sans attestation SBOM peut être publiée et signée.
- Reproduction : publier une release dont l'image de base contient une CVE critique corrigeable ; le workflow reste vert et pin-digests produit le compose.
- Correctif : Trivy bloquant sur CRITICAL avec `--ignore-unfixed` et un `.trivyignore` daté ; attestation SBOM obligatoire (échec si le fichier est absent) pour les releases ; au moins SBOM + attestation pour edge, ou un scan Trivy de l'image core à chaque merge.

### 5. Reproductibilité : images de base sans digest, `pip install uv` et `pip` non épinglés, build MinIO depuis un tag git mutable
- Sévérité : Important. Tag : `securite`. Statut : vérifié.
- Fichiers : `core/Dockerfile:1,16`, `deploy/export-worker/Dockerfile:9,13`, `deploy/minio/Dockerfile:12,26,32`, `deploy/titiler/Dockerfile:19-21`, `deploy/postgis/Dockerfile:10`, `shell/Dockerfile:1,18`, `deploy/backup/Dockerfile:2`.
- Preuve : toutes les images de base utilisent des tags flottants (python:3.12-slim, node:22-slim, nginx:1.27-alpine, postgres:16-bookworm, alpine:3.20, golang:1.24-bookworm, debian:bookworm-slim), aucune ne porte de `@sha256:`. `RUN pip install --no-cache-dir uv` (`core/Dockerfile:16`, export-worker:13) installe sans version l'outil qui produit toute l'installation. `deploy/titiler/Dockerfile:20` fait `pip install -U pip`. `deploy/minio/Dockerfile:26` fait `git clone --branch ${MINIO_RELEASE}` : un tag git est déplaçable, et un binaire AGPL de stockage est construit depuis une référence non vérifiée. Le digest n'est figé qu'après coup par `pin_compose_digests.py` sur le résultat du build : la construction elle-même n'est pas reproductible.
- Reproduction : reconstruire la même révision à deux dates ; le digest change sans modification de code.
- Correctif : épingler les `FROM` par digest (Dependabot docker les met à jour), `pip install uv==X.Y.Z`, `git clone` puis `git checkout <sha>` vérifié pour MinIO. Option : `SOURCE_DATE_EPOCH`.

### 6. Le binaire `mc` est téléchargé sans vérification, et l'image appexport-standalone installe ses paquets sans version
- Sévérité : Important. Tag : `securite`. Statut : vérifié.
- Fichiers : `deploy/backup/Dockerfile:20-23`, `deploy/appexport-standalone/Dockerfile:34`.
- Preuve : `deploy/backup/Dockerfile:21` fait `curl -fsSL .../mc.linux-${TARGETARCH}.${MC_RELEASE} -o /usr/local/bin/mc && chmod +x`, sans sha256sum, cosign ni GPG ; seul `mc --version` est exécuté. Ce binaire tourne dans le conteneur de sauvegarde, qui détient les identifiants S3 et la clé age. `deploy/appexport-standalone/Dockerfile:34` fait `pip install --no-cache-dir fastapi 'uvicorn[standard]' pydantic duckdb sqlalchemy` sans version ni lockfile. Cette image est livrée aux clients dans les exports autoportés, n'est pas couverte par `pip-audit`, et sa résolution diffère de celle du cœur.
- Reproduction : rebuild de l'image standalone ; une nouvelle majeure de pydantic ou sqlalchemy change le comportement sans changement de dépôt.
- Correctif : `ARG MC_SHA256_amd64/arm64` et `echo "$sha  /usr/local/bin/mc" | sha256sum -c -`. Pour standalone, générer un requirements verrouillé depuis `uv.lock` et l'installer avec `--require-hashes`.

## Constat bug (Important)

### 7. Compose de production : repli `:-latest` si GEOSTUDIO_VERSION est absente
- Sévérité : Important. Tag : `bug`. Statut : vérifié.
- Fichiers : `docker-compose.prod.yml:22,30,80,166,254,271,278,282,286,383`.
- Preuve : les 10 images `ghcr.io/tlenenao` utilisent `${GEOSTUDIO_VERSION:-latest}`. Sans variable définie, le déploiement tire `latest`, mutable et sans digest. L'épinglage (`docker-compose.digests.yml`) n'est produit que comme artefact CI optionnel (`release.yml:261-284`) ; rien n'oblige le déploiement à l'utiliser, et les tests de déployabilité ne vérifient pas l'absence de repli latest. Le chart Helm est correct sur ce point (`tag: ""` = appVersion).
- Reproduction : `docker compose -f docker-compose.prod.yml config | grep image:` sans GEOSTUDIO_VERSION ; toutes les images pointent vers `:latest`.
- Correctif : `${GEOSTUDIO_VERSION:?GEOSTUDIO_VERSION requis}` et consommer par défaut `docker-compose.digests.yml` ; ajouter un test de déployabilité interdisant `latest`.

## Avantages et différenciateurs

- Actions GitHub épinglées par SHA.
- Signature cosign keyless par digest en CI, avec vérification des signatures publiées (`verify-published`) avant la production du compose épinglé (`docker-compose.digests.yml`).
- `pip-audit` strict sur l'environnement verrouillé ; `npm audit` filtré par une liste d'exceptions justifiées et datées.
- SBOM et attestations produits pour les releases ; image MinIO reconstruite depuis les sources AGPL.
- Différenciateur potentiel face à ArcGIS et FME : publier la procédure de vérification côté consommateur (constat 8) ferait de la chaîne signée un argument produit.
