# Dimension d12 : ETL, orchestration

Audit du 2026-10-16. Méthode : lecture du code (aucun test exécuté, aucun fichier source édité). Les reproductions sont des scénarios déduits de la lecture du code, **non rejoués**. Les numéros de ligne sont ceux relevés pendant l'audit.

Bilan : 9 constats vérifiés (tous Important), 4 constats Minor **non vérifiés**.

## Constats vérifiés

### 1. Important, tag `bug` : annulation inopérante hors writers collection/dataset ; un run `cancel_requested` peut finir `succeeded`

- **Fichiers** : `core/app/pipelines/collection_writer.py`, `runtime.py`, `repository.py`, `jobs.py`.
- **Preuve** : `should_cancel` n'est consulté qu'à `collection_writer.py:487` (après chaque lot). `runtime.py:1521-1560` : `_write_export` et `_write_file` ne reçoivent pas `should_cancel`. La chaîne `_execute_transform_chain` (`runtime.py:~1490`) et les readers ne l'appellent jamais. Aucun `conn.interrupt()` côté run : seul `preview_pipeline` (`runtime.py:~1034`) interrompt DuckDB sur délai. Les writers externes (postgres, email, ftp…) reçoivent `**extra` sans le lire. `repository.py:263-275` : `mark_succeeded` écrase le statut sans condition, donc `cancel_requested` devient `succeeded` si le run n'atteint jamais une boucle de lot.
- **Reproduction** : pipeline `reader.connector.rest` (ou `httpCall` lent) vers `writer.export` (ou writer externe). Lancer, puis `POST /v1/pipelines/{id}/runs/{run}/cancel` (200, `cancel_requested`). Le run continue jusqu'au bout, finit `succeeded`, effets externes produits, aucune trace de l'annulation.
- **Correctif** : (1) vérifier `should_cancel` entre chaque nœud de `_execute_transform_chain` et avant/après chaque writer ; (2) thread de surveillance appelant `conn.interrupt()` sur `cancel_requested` (comme le timer de preview) ; (3) `mark_succeeded`/`mark_failed` en UPDATE conditionnel préservant `cancel_requested` vers `cancelled` ; (4) timeout dur de run configurable.

### 2. Important, tag `bug` : `defer()` non gardé après commit, run `queued` orphelin qui bloque le pipeline ~60 min

- **Fichiers** : `core/app/pipelines/service.py`, `jobs.py`, `repository.py`, `core/app/webhooks/triggers.py`.
- **Preuve** : `service.py:124-125` `session.commit(); defer_task(run.id, …)` sans try/except (idem `service.py:193-194` pour la reprise). Si procrastinate/Postgres lève, le run reste `queued`. `create_run_unless_active` (`repository.py:66-107`) le tient pour actif tant que `created_at` a moins de 60 min (`repository.py:19, 87`) : tout nouveau déclenchement reçoit 409 ; seul `reclaim_stuck_runs` (`repository.py:355-388`, seuil unique 60 min) le clôt. Dans le balayage cron, `jobs.py:488` (`run_pipeline_task.defer(...)`) et `jobs.py:448` (reprises en retard) ne sont pas dans un try : une exception avorte la boucle, prive les autres pipelines dus du tick, et laisse le run déjà commité `queued`. Jumelle du piège n°14, appliquée seulement aux retries (`jobs.py:164-169`). Concerne REST, MCP, webhook, cron, déclencheur fichier.
- **Reproduction** : rendre `defer` indisponible (couper la connexion procrastinate) pendant `POST /v1/pipelines/{id}/run` : 500, run `queued` en base. Rétablir le service, relancer : 409 « déjà en cours » pendant ~1 h.
- **Correctif** : encadrer chaque `defer` (en cas d'échec, marquer le run `failed`, ou balayage dédié qui re-defer les `queued` > 2-5 min sans job procrastinate) ; try/except par pipeline dans le balayage ; seuil de péremption `queued` distinct (court) de celui de `running`.

### 3. Important, tag `bug` : run « périmé » clos à 60 min alors qu'il tourne encore (deux runs concurrents), ni heartbeat ni reprise sur crash worker

- **Fichiers** : `core/app/pipelines/repository.py`, `jobs.py`.
- **Preuve** : `repository.py:355-388` `reclaim_stuck_runs` passe en `failed` tout run `running` dont `started_at` a plus de 60 min (constante en dur `repository.py:19`, non configurable alors que `app/job_timeouts.py` offre `CORE_EXPORT_RUNNING_TIMEOUT_MINUTES` aux exports) ; le commentaire `ponytail: pas de heartbeat` (l.363) avoue le plafond. Ensuite `create_run_unless_active` ignore les runs périmés (l.87-97) et le cron (`list_due_pipelines`, l.464-481) re-planifie : le premier thread continue d'écrire (`writer.collection` replace, `httpCall`, writers externes) en même temps que le second ; `mark_succeeded` (l.271) fait « primer la fin réelle ». Un worker tué (OOM, redéploiement) laisse le run `running` 60 min puis `failed` sans appliquer la politique `retry` (`jobs.py:382-431` ne s'exécute que dans le processus vivant).
- **Reproduction** : pipeline de plus d'une heure (gros import + `httpCall` paginé) avec cron fréquent : au tick suivant le seuil, run #1 passe `failed` en base et run #2 démarre alors que #1 tourne encore.
- **Correctif** : heartbeat (`heartbeat_at` mis à jour par le callback de progression ou toutes les 30 s) et réclamation sur heartbeat périmé, pas sur durée absolue ; seuil configurable par pipeline ; sur reclaim d'un run dont `retry` n'est pas épuisé, appliquer `_schedule_retry`.

### 4. Important, tag `parite` : déclencheur fichier S3, le run ne reçoit ni la clé ni l'etag du fichier déclencheur

- **Fichiers** : `core/app/webhooks/triggers.py`, `core/app/pipelines/service.py`, `core/app/outbox/models.py`.
- **Preuve** : `triggers.py:152-158` appelle `run_pipeline_service(session, user=owner, item_id=…, defer_task=…, actor_kind="file_trigger")` sans `params`. `object_key` n'est stocké que dans `FileTriggerSeen` (`outbox/models.py:88-95`) et n'est lu par aucun code du pipeline (grep : uniquement `webhooks/triggers.py` et `outbox/models.py`). Un fichier = un run, mais le run ignore lequel. Sondage fixé à 5 min (`webhooks/jobs.py:213`) et un run actif fait `break` (`triggers.py:161-163`) : un fichier par run, un par tick de 5 min au mieux.
- **Reproduction** : file-trigger sur `s3://bucket/in/`, déposer `a.csv` et `b.csv` : deux runs (en série, ≥ 5 min d'écart si un run est actif), aucun `{{param.*}}` ni contexte ne porte `in/a.csv`.
- **Correctif** : passer `params={"trigger.objectKey":…, "trigger.etag":…, "trigger.bucket":…}` (paramètres réservés déclarés par le pipeline) consommables par `reader.file`/`reader.blob` ; intervalle de sondage configurable par trigger ; option « un run par lot de fichiers ».

### 5. Important, tag `parite` : reprise manuelle et retry automatique refusés aux writers `append`, alors que les écritures collection/dataset sont transactionnelles (et `append` est le défaut)

- **Fichiers** : `core/app/configs/schemas.py`, `core/app/pipelines/service.py`, `jobs.py`, `core/app/db.py`, `collection_writer.py`.
- **Preuve** : `schemas.py:~465-480` `append_writers()` classe `writer.collection`/`writer.dataset` en mode `append` (défaut `params.get("mode","append")`) comme « non rejouables » ; `schemas.py:~441-447` rejette en 422 `retry.max > 0` avec un tel writer ; `service.py:~153-163` refuse la reprise manuelle (409). Or tout le run s'exécute dans UNE session : `jobs.py:316-371` `with request_scoped_session(factory)` ; `db.py:205-220` commit unique en sortie, rollback sur exception ; `collection_writer.py` ne contient aucun `commit` (grep vide) et `runtime.py:1496-1500` le dit (« transaction du run annulée à l'échec »). Un échec annule toutes les lignes ajoutées : rejouer ne duplique rien. Seuls les writers externes (`EXTERNAL_EFFECT_WRITER_OPS`) sont réellement non rejouables. Un pipeline en config par défaut n'a donc ni retry auto ni « Reprendre » (checkpoints non écrits car `payload.retry is None`, `jobs.py:327-338`).
- **Reproduction** : `reader.connector.rest` vers `writer.collection` (mode omis) avec `retry {max:3}` : PUT config 422 ; run échoué : `POST /pipelines/runs/{id}/retry` : 409 « n'est pas idempotent ».
- **Correctif** : retirer `writer.collection/dataset` mode append de `append_writers()` (garder les writers à effet externe), vérifier par test que l'échec ne laisse aucune ligne ; écrire les checkpoints même sans `retry` (coût disque borné par la rétention).

### 6. Important, tag `differenciateur` : planification sans fuseau horaire, résolution silencieuse de 5 min, aucun circuit-breaker

- **Fichiers** : `core/app/configs/schemas.py`, `core/app/pipelines/repository.py`, `jobs.py`, `core/app/configs/pipeline_validation.py`.
- **Preuve** : `schemas.py:347-360` `PipelineRefreshPolicy` = `{enabled, cron}`, sans `timezone` ; croniter évalué en UTC (`repository.py:457,482`) : `0 8 * * *` = 08:00 UTC, décalé de 1-2 h selon l'heure d'été à Paris. Balayage `*/5` (`jobs.py:433`) : un cron `* * * * *` ou `*/2` est accepté (`pipeline_validation.py:106-110` ne vérifie que 5 champs) mais s'exécute au mieux toutes les 5 min. Pas de politique de rattrapage (une seule exécution après panne), pas de fenêtre, pas de « suspendre après N échecs » (alors que `outbox/delivery.py:28-105` l'a pour les webhooks). Propriétaire supprimé/anonymisé : `_acting_user` lève `ValueError` (`jobs.py:322, 59-62`), le run échoue à chaque tick indéfiniment, notification envoyée à un propriétaire inexistant. `_notify(status="success")` (`jobs.py:377`) notifie CHAQUE run planifié réussi.
- **Reproduction** : pipeline planifié `*/5`, propriétaire anonymisé (RGPD Art. 17) : un run `failed` toutes les 5 min, sans fin, sans alerte à un administrateur.
- **Correctif** : champ `timezone` IANA (croniter + zoneinfo) ; refus 422 des crons plus fins que le pas du balayage (ou balayage 1 min) ; `missedPolicy: skip|runOnce|backfill` ; suspension automatique + notification des admins après N échecs consécutifs ; exécution sous compte de service ou transfert de propriété ; notification de succès opt-in.

### 7. Important, tag `differenciateur` : webhook entrant, un déclenchement pendant un run actif est perdu (409), sans file, coalescence ni idempotence ; jeton sans expiration ni portée

- **Fichiers** : `core/app/pipelines/service.py`, `routes.py`, `repository.py`.
- **Preuve** : `service.py:~105-110` (dans `run_pipeline_service`) `PipelineRunActive` donne `HTTPException 409` ; `routes.py:341-363` `/trigger` n'a ni en-tête `Idempotency-Key`, ni mise en attente (aucun statut « pending trigger »). Un événement externe (CI, capteur) reçu pendant un run est rejeté : source non rafraîchie jusqu'au prochain déclenchement. Les jetons (`repository.py:491-504`, `create_webhook_token_service`) n'ont ni expiration, ni rotation, ni limitation de paramètres, ni signature HMAC/horodatage (bearer statique) ; seul `last_used_at` est tracé.
- **Reproduction** : deux `POST /v1/pipelines/{id}/trigger` espacés de quelques secondes, run long : le 2e reçoit 409 et son événement n'est jamais rejoué.
- **Correctif** : option `onBusy: reject|queueOne|coalesce` par pipeline (un seul trigger en attente, rejoué à la fin du run) ; `Idempotency-Key` ; expiration/rotation de jeton ; HMAC optionnel (`X-Signature` + horodatage anti-rejeu).

### 8. Important, tag `bug` : quarantaine, rejets accumulés en mémoire sans plafond, aucun seuil d'échec, aucune rétention ni ré-injection

- **Fichiers** : `core/app/pipelines/collection_writer.py`, `repository.py`.
- **Preuve** : `collection_writer.py:398-409` `rejects: list[tuple]` grossit pendant TOUTE la boucle de lots (l.~414-488) et n'est vidé qu'après (l.490-491 `_store_rejects`) : une source massivement invalide (10^7 lignes) charge tous les rejets en RAM du worker (OOM probable, run zombie 60 min). Aucun paramètre `maxRejects`/ratio (grep `maxReject|rejectThreshold` : vide) : un run dont 90 % des lignes sont rejetées finit `succeeded_with_rejects` (`repository.py:268-270`). `<cible>__rejected` (l.124-214) croît sans purge ; `source_row` omet géométrie et champs sensibles (l.404-409), donc impossible de ré-injecter les lignes corrigées.
- **Reproduction** : CSV de 5 M lignes dont la colonne clé est vide avec `rejectWhenFalse` : tous les rejets restent en mémoire jusqu'à la fin du dernier lot.
- **Correctif** : vider `rejects` à chaque lot (INSERT par lot) ; `maxRejects`/`maxRejectRatio` entraînant l'échec du run ; rétention (N jours / N runs) sur la quarantaine ; identifiant source stable + géométrie WKT dans un champ à droits propres pour « Rejouer les rejets ».

### 9. Important, tag `differenciateur` : lineage au niveau item seulement, détecté par nom de clé, non branché sur les suppressions

- **Fichiers** : `core/app/lineage/service.py`, `routes.py`, `core/app/mcp/tools/lineage.py`.
- **Preuve** : `service.py:33-50` `REF_KEYS` (14 noms de clé) : toute référence portée autrement (nom de collection dans du SQL/CEL, `secret_name` des connecteurs, colonnes) est invisible. Aucune notion de run : on ignore quel run/version a alimenté une collection et quand. Graphe reconstruit entièrement à chaque appel (`service.py:78-112` : tous les items + configs courantes du tenant, O(tenant) par requête REST ou MCP). Seuls consommateurs de `service.py` : `lineage/routes.py:62` et `mcp/tools/lineage.py:28` ; ni la suppression d'item/collection ni celle de secret ne consultent l'impact (grep `from app.lineage` : `main.py`, routes et MCP).
- **Reproduction** : supprimer une collection lue par un pipeline via `reader.connector.postgres` + SQL nommant la table : aucun avertissement « utilisée par … » côté cœur ; `/impact` ne la voit pas.
- **Correctif** : table d'arêtes matérialisée à l'écriture de config (item vers item, item vers secret, op vers colonnes lues/écrites issues du compilateur) ; `dataset_lineage_run(run_id, writer_node, collection_id, rows_in/out)` alimentée par `run_pipeline` ; garde `impact` (409 avec liste) sur DELETE d'item/collection/secret ; vue column-level.

## Constats Minor, non vérifiés

Ces quatre points proviennent de la lecture du code mais n'ont pas fait l'objet de la vérification croisée.

### M1. Minor, tag `dette` (non vérifié) : aucune rétention des `pipeline_runs`

- **Preuve** : seule suppression de `PipelineRun` : `compliance/purge.py:233` (purge de tenant entier). Aucune tâche périodique ne borne la table (`jobs.py:433-488` ne purge que les checkpoints). Chaque run stocke `node_stats` JSON (`repository.py:406`) et une ligne `audit_log` (`jobs.py:472-481`) : un cron `*/5` produit ~105 000 runs/an. `get_latest_runs_for_items` (`repository.py:157-177`) fait un `row_number()` sur tous les runs des pipelines candidats à chaque balayage.
- **Reproduction** : pipeline `*/5` pendant 6 mois : ~50 000 lignes, le balayage fenêtre sur l'ensemble.
- **Correctif** : purge périodique (90 jours ou 500 derniers runs par pipeline, en gardant les échecs récents) ou requête `DISTINCT ON`/LATERAL indexée `(pipeline_item_id, created_at desc)`.

### M2. Minor, tag `dette` (non vérifié) : checkpoints de reprise sur disque local du worker

- **Preuve** : `checkpoints.py:17-18` (`ponytail: disque LOCAL du worker`) ; Helm `worker.yaml:54-57` monte `/scratch` en `emptyDir` (sizeLimit 5Gi, `values.yaml:~156`) alors que `docker-compose.yml:9,642-690` utilise un volume nommé persistant. Une reprise sur un autre pod/nœud, ou après reschedule, ne trouve aucun fichier et rejoue tout (`jobs.py:117-127` ne pose `resumable` que si `checkpoints.exists` côté worker courant), sans que l'UI sache pourquoi. Le `manifest.json` n'est pas partagé entre `core` (API qui propose « Reprendre ») et worker.
- **Reproduction** : déploiement Helm, run échoué avec retry, pod worker recréé avant la reprise : la reprise repart du nœud 1 sans message, `resumable` incohérent.
- **Correctif** : PVC pour `/scratch` (RWO + worker unique) ou Parquet de checkpoint sur S3 avec manifest en base ; message explicite « points de reprise indisponibles, rejeu complet ».

### M3. Minor, tag `polish` (non vérifié) : annulation, état et nettoyage incomplets

- **Preuve** : `jobs.py:378-379` `except PipelineCancelledError: tracker.mark_cancelled()` : ni `_notify` (échecs et succès notifient, `jobs.py:377,399`), ni `checkpoints.discard`/`_clear_resumable` (répertoire de reprise conservé 24 h). `routes.py:188` n'autorise l'annulation que de `queued|running|retrying` alors que `_ACTIVE_STATUSES` (`repository.py:50`) et `mark_running` (l.189) traitent aussi `pending` (jamais créé par le code actuel, état mort). `list_due_pipelines` (l.464) ignore `pending` alors que `create_run_unless_active` le compte actif. `request_cancel` sur un run `retrying` ne purge pas le point de reprise.
- **Reproduction** : annuler un run avec politique retry : aucune notification, `checkpoints/<tenant>/<run>` persiste jusqu'à la purge à 24 h.
- **Correctif** : notifier `cancelled`, discard des checkpoints à l'annulation, supprimer l'état `pending` ou l'aligner partout.

### M4. Minor, tag `dette` (non vérifié) : livraison des webhooks sortants

- **Preuve** : `delivery.py:28-35,94-105` backoff 30 s x 2^n ; avec un seul événement, 5 tentatives tiennent en ≈ 7,5 min, puis `_disable` (l.118-137) marque TOUS les événements `pending` de la destination `failed`. Une panne de récepteur de quelques minutes perd définitivement des `pipeline.run.finished` (seul rejeu manuel unitaire, `routes.py:255`). La signature (l.49-50, 82) porte le corps seul : pas d'en-tête de timestamp signé pour borner le rejeu. Un événement poison (4xx permanent) est retenté toutes les heures sans maximum par événement et reste `pending` hors purge (l.231-240).
- **Reproduction** : récepteur HTTP arrêté 10 minutes : webhook désactivé, événements en file passés `failed`.
- **Correctif** : seuil de désactivation en durée (ex. 24 h d'échecs continus), bascule en `failed` par événement après N tentatives, replay en lot à la réactivation, en-tête `X-GeoStudio-Timestamp` inclus dans le HMAC.

## Avantages et différenciateurs

Points observés dans le code qui servent de base (à ne pas casser en corrigeant ce qui précède) :

- **Transaction unique par run** pour les writers collection/dataset (`jobs.py:316-371`, `db.py:205-220`) : un échec annule toute l'écriture, ce qui rend le retry sûr (levier du constat 5).
- **Quarantaine `<cible>__rejected`** et statut `succeeded_with_rejects` (`collection_writer.py:124-214`, `repository.py:268-270`) : comportement proche des « rejected features » de FME, absent de la plupart des concurrents open-source.
- **Retry et reprise par nœud** avec checkpoints Parquet (`checkpoints.py`, `jobs.py:382-431`) : reprise partielle, pas seulement relance complète.
- **Déclencheurs multiples** dans un même modèle : cron, webhook entrant avec jetons, déclencheur fichier S3, REST, MCP ; outbox de webhooks sortants signés avec désactivation automatique de destination (`outbox/delivery.py`).
- **Lineage exposé aussi en MCP** (`mcp/tools/lineage.py`) : exploitable par un agent IA ; le constat 9 montre la marge pour en faire un vrai différenciateur column-level face à FME/ArcGIS.
- **Verrou de run actif par pipeline** (`create_run_unless_active`) : évite par défaut les exécutions concurrentes (à fiabiliser, constats 2 et 3).
