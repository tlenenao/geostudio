# d24 — SDK, extensions, ouverture aux tiers

Audit du 2026-10-16, lecture seule, sans exécution de tests. Périmètre : SDK de widgets Web Components, registre d'extensions, CSP, documentation développeur.

Bilan : 10 constats (5 Important vérifiés, 4 Minor non vérifiés, plus 1 Minor-structurel inclus dans ces 4). Les deux plus graves : les extensions ne se chargent pas sur les surfaces publiques ou embarquées, et la frontière `permissions.collections` est contournable alors que la doc l'annonce comme « une vraie frontière serveur ».

Le cadre de confiance (pas de sandbox, pas d'intégrité, pas de signature, CSP à l'échelle de l'instance) est assumé dans l'ADR 0013 et `SECURITY.md` : il n'est remonté qu'en différenciateur, sauf pour l'absence de contre-mesure de contenu (constat 4).

Statut de vérification : les constats 1 à 5 sont vérifiés dans le code. Les constats 6 à 9 (Minor) sont **non vérifiés**.

---

## Important

### 1. Les widgets d'extension ne s'affichent jamais sur les pages publiques, embed et sites (« Widget inconnu ») — tag : bug

Preuve :
- Seuls `AppRuntimePage` et `AppBuilderPage` (et `staticExport/entry.tsx`) appellent `useActiveExtensions` + `registerExtensionWidget` (`shell/src/pages/AppRuntimePage.tsx:54-60`).
- `shell/src/pages/EmbedPage.tsx:67`, `shell/src/pages/SitePublicPage.tsx:56`, `shell/src/pages/PublicItemPage.tsx:54` (et `DatasetPage`) montent `<AppRenderer mode="runtime">` sans aucune occurrence de `xtension` (grep = 0).
- Le registre étant vide pour ces types, `shell/src/builder/WidgetHost.tsx:59-66` renvoie le placeholder `widgetHost.unknownWidget`.
- `GET /extensions` accepte pourtant un appel anonyme (`core/app/extensions/routes.py:124`, `get_current_user_optional`) : le cœur est prêt, seul le shell est incomplet.
- Impact : SDK d'embedding GAP-19 et portails SP-13, soit exactement les surfaces ouvertes aux tiers.

Reproduction : enregistrer une extension, la placer dans une app, partager l'app via `/embed/:token` ou la publier dans un site `/sites/:slug`. Le widget affiche « Widget inconnu : <id> ». Il fonctionne sur `/apps/:pk`.

Correctif : extraire un hook `useRegisterExtensions()` (déjà dupliqué dans `AppBuilderPage` et `AppRuntimePage`) et l'appeler dans `AppRenderer`, ou dans les 3 pages publiques, avant le rendu. Ajouter un test E2E d'embed avec le widget de référence `examples/external-widget`.

### 2. La frontière `permissions.collections` est contournable via la prop `dataSourceId` — tag : securite

Preuve :
- `shell/src/builder/WidgetHost.tsx:57-58` calcule `dsId = item.props.dataSourceId` puis `data = states[dsId]` ; `shell/src/builder/wc/WcHost.tsx:25` l'assigne à `el.data`, quel que soit le manifeste.
- Le validateur ne parcourt que les props que le manifeste déclare de type `dataSource` (`core/app/configs/extension_permissions.py:54-62`). Une config portant `props.dataSourceId` vers une source hors liste est acceptée.
- `source is None → continue` (l. 60) laisse passer toute référence non résolue ; la valeur d'une prop dataSource peut être une expression liée, résolue par `resolveExprBindings` après validation.
- La doc (`docs/guides/2026-07-13-ecrire-un-widget-web-component.md:42-47`) présente pourtant cela comme « une vraie frontière serveur ».

Reproduction : manifeste `{permissions:{collections:["a"]}, props:[{name:"src",type:"dataSource"}]}` ; config avec widget=ext, `props:{dataSourceId:"ds_b"}` où `ds_b.layer="b"`. PUT config : 200, et le widget lit les données de b dans `el.data`.

Correctif : dans `validate_extension_permissions`, vérifier aussi `props.dataSourceId` (clé réservée du host) et rejeter les sources non résolues ou les expressions pour les extensions restreintes. Côté host, ne passer `data` qu'aux extensions dont la prop dataSource déclarée est la source. Réécrire la doc : confort d'autorat, pas une frontière, puisque le code tiers peut appeler l'API avec la session.

### 3. La CSP enforcing bloque tout connect-src/img-src vers l'origine de l'extension — tag : bug

Preuve :
- `core/app/security/service.py:131-135` : `compute_csp_allowlist` renvoie `connect_hosts=set(tile_hosts)` et `img_hosts=set(tile_hosts)` ; les hôtes d'extension ne vont que dans `script_hosts`.
- `core/app/security/traefik_render.py:22-23,41-50` : `default-src 'self'`, ni `font-src`, ni `media-src`, ni `frame-src`.
- Une extension qui charge un JSON, une API tierce, une image, une police ou des tuiles est bloquée par le navigateur.
- La doc (`docs/guides/2026-07-13-ecrire-un-widget-web-component.md:106-111`) affirme que « votre code reste libre de faire ses propres requêtes réseau, dans la limite de ce que le token autorise ».

Reproduction : extension qui fait `fetch('https://api.exemple.org/x')` ou charge `<img src=https://cdn.exemple.org/a.png>` avec `CORE_CSP_MODE=enforce` : violation connect-src/img-src, requête bloquée.

Correctif : ajouter au manifeste des champs déclaratifs `connectHosts`/`imgHosts` (https uniquement, validés comme `module_url`), les agréger dans `compute_csp_allowlist` pour les extensions activées, mettre la doc à jour. Au minimum, ajouter l'origine du module à connect-src et img-src.

### 4. Aucun garde d'intégrité sur le code tiers (SRI, pinning, signature) — tag : securite

Preuve :
- `moduleUrl` = n'importe quelle URL https (regex `^https://[^\s]+$`, `core/app/extensions/schemas.py:141`).
- Le shell fait `import(url)` brut (`shell/src/builder/extensions/moduleCache.ts:5-8`). Ni hash, ni digest épinglé, ni signature.
- Le commentaire de `core/app/security/traefik_render.py:30-41` reconnaît que la CSP « ne protège PAS contre un fichier malveillant substitué sur l'origine déclarée ».
- Le code exécuté a les droits DOM complets du shell : accès à la session OIDC et à toutes les API du cœur.
- L'ADR 0013 et `SECURITY.md` assument la CSP à l'échelle de l'instance (l'origine d'un tenant est autorisée pour tous). Ce constat porte sur l'absence de contre-mesure de contenu, qu'une ouverture aux tiers exigerait.

Reproduction : enregistrer une extension valide, puis remplacer `widget.js` côté hébergeur : le shell exécute le nouveau code sans contrôle. Non rejoué sur stack réelle ; constat par lecture du code.

Correctif : ajouter `integrity` (sha384) au manifeste, vérifié avant exécution (fetch + hash puis import d'un Blob URL, ou `<script type=module integrity>`), avec restriction de script-src à ce hash. À plus long terme, iframe sandbox + postMessage (RPC typé) pour les extensions non approuvées.

### 5. Contrat DOM minimal et sans version — tag : differenciateur

Preuve :
- `shell/src/builder/wc/WcHost.tsx:21-28` n'assigne que `props`, `data`, `user`, `navigate`.
- `WidgetContext` (`shell/src/builder/registry.ts:9-21`) porte `variables`, `theme`, `breakpoint`, `mode`, `pages`, `bus`, fournis par `WidgetHost.tsx:89-102`, mais non transmis aux extensions.
- Un widget tiers ne peut ni lire/écrire une variable d'app, ni déclencher un cross-filter (`setFilter`), ni connaître le mode edit/export ou le thème.
- `ExtensionCreate` (`core/app/extensions/schemas.py:161-170`) n'a aucun champ `sdkVersion`/`contractVersion` : impossible de faire évoluer le contrat sans casser l'existant.
- Seuls canaux : `CustomEvent` déclarés (sortants) et méthodes déclarées (entrantes). Principal écart face aux widgets personnalisés d'ArcGIS Experience Builder.

Reproduction : écrire un widget qui lit une variable `region` ou pose un filtre cross-dataset : aucune API disponible.

Correctif : contrat v1 versionné (`sdkVersion` au manifeste) ; ajouter à l'élément `variables`, `theme`, `mode`, `breakpoint`, `setVariable(name,value)`, `setFilter(datasetId,filter)`, `query(datasetId,spec)` (via `ItemClient` et `can()`), plus un événement `gs:ready`. Publier les types dans un paquet `@geostudio/widget-sdk`.

### 6. L'UI d'administration ne peut enregistrer qu'un squelette — tag : parite

Preuve :
- `shell/src/pages/AdminExtensionsPage.tsx:25-37` : `RegisterForm` n'a que 4 champs (id, tag, label, moduleUrl) et envoie `defaultSize:{w:2,h:2}` en dur.
- `ExtensionCreateInput` (`shell/src/api/types.ts:1417-1423`) n'expose pas props/events/actions/permissions.
- Une extension créée depuis l'UI n'a aucune prop éditable ni événement ou action câblable. Le manifeste complet exige un `POST /extensions` manuel. Aucun PATCH n'est appelé par l'UI. La doc renvoie à l'API sans exemple curl ni auth.
- Aucun outil MCP d'extension (grep `core/app/mcp` : uniquement la validation dans `tools/configs.py`).

Reproduction : `/admin/extensions`, enregistrer le widget de référence ; dans le builder, le panneau de props est vide et aucun événement n'est disponible.

Correctif : import de manifeste JSON dans `RegisterForm` (validé par `ExtensionCreate`), éditeur d'extension existante (PATCH), outils MCP d'enregistrement.

## Minor (non vérifiés)

### 7. Échec de chargement de module mis en cache définitivement — tag : bug (non vérifié)

`shell/src/builder/extensions/moduleCache.ts:12-17` stocke la promesse avant son issue (`cache.set(url,p)`) et ne la retire jamais en cas de rejet ; `LazyWcHost.tsx:28-40` réutilise la promesse rejetée. Une panne réseau transitoire rend le widget « Extension indisponible » jusqu'à F5. Pas de vérification `customElements.get(tag)` après chargement : un module sans `define` donne un élément inerte sans erreur.

Reproduction : couper le réseau pendant le premier import, le rétablir, remonter le widget.

Correctif : `p.catch(() => cache.delete(url))` ; après import, vérifier `customElements.get(manifest.tag)` (sinon `whenDefined` avec délai) et lever une erreur lisible ; message de diagnostic pour les administrateurs.

### 8. Doc développeur contradictoire avec le code — tag : polish (non vérifié)

Preuve (`docs/guides/2026-07-13-ecrire-un-widget-web-component.md:15-19,53-56,85-90`, `examples/external-widget/manifest.json:5`) :
1. Manifeste d'exemple avec `moduleUrl: "widget.js"` alors que `ModuleUrl` exige `^https://` (`schemas.py:141`) : 422.
2. `data` décrit comme « variables, contexte » alors que le host n'y met que l'état de `props.dataSourceId` (`WcHost.tsx:25`).
3. Variables `--gs-*` non listées ; le fond du thème d'app n'atteint pas un shadow DOM sans héritage explicite.
4. Aucun typage de `DataSourceState` ni du format des événements.

Reproduction : `curl -X POST /v1/extensions -d @examples/external-widget/manifest.json` : 422 sur `moduleUrl`.

Correctif : URL https absolue dans l'exemple (ou chemin relatif résolu contre l'origine du manifeste), corriger la description de `data`, lister les `--gs-*` et `DataSourceState`, ajouter un exemple curl et un gabarit (Vite + Lit + types).

### 9. Catalogue d'extensions jamais rafraîchi — tag : dette (non vérifié)

`shell/src/builder/registry.ts:48-53` : Map global, `registerWidget` écrase avec un `console.warn`, pas de `unregisterWidget` ; `AppBuilderPage.tsx:150-159` et `AppRuntimePage.tsx:54-60` n'enregistrent qu'au chargement ; cache de modules indexé par URL (`moduleCache.ts:12`). Une extension désactivée reste utilisable dans la session ouverte ; un changement de `moduleUrl` ou une nouvelle version de la même URL n'est pas rechargé.

Reproduction : ouvrir le builder, désactiver l'extension dans un autre onglet : elle reste dans la palette jusqu'à F5.

Correctif : `unregisterWidget` + réconciliation avec la liste active ; versionner l'URL (`?v=updated_at` ou hash d'intégrité).

### 10. Pas d'écosystème tiers (gouvernance, signature, marketplace) — tag : differenciateur (non vérifié)

`core/app/extensions/models.py:198-220` : PK (id, tenant_id), aucun champ version, éditeur, hash, changelog ni statut de revue ; `routes.py:32-65` sans catalogue inter-tenants ; l'ADR 0013 reconnaît le SDK comme non ouvert aux tiers. ArcGIS Marketplace/Experience Builder et FME Hub reposent sur un paquet versionné et signé ; ici, une extension est une ligne de config pointant vers une URL. Constat structurel, sans reproduction.

Correctif : paquet d'extension (manifeste + hash + semver + éditeur), signature (cosign/minisign) vérifiée à l'enregistrement, statut « approuvée » pour la CSP, export/import entre instances.

## Avantages et différenciateurs

- SDK à base de Web Components standard (Lit + pont React interne) : pas de dépendance à un framework imposé aux auteurs tiers.
- Contrat déclaratif : le manifeste décrit props, événements, actions et permissions, ce qui rend les extensions compatibles avec le builder no-code et la génération IA.
- Validation serveur des permissions de collections à l'écriture de config (à renforcer, constat 2).
- Cadre de confiance explicite et documenté (ADR 0013, `SECURITY.md`) : pas de sandbox, d'intégrité ni de signature, CSP à l'échelle de l'instance, limite assumée plutôt que cachée. À traiter comme différenciateur (honnêteté du modèle de menace) tant que le SDK n'est pas ouvert aux tiers.
- `GET /extensions` déjà accessible en anonyme : le cœur est prêt pour les surfaces publiques, seul le shell reste à câbler (constat 1).
- Un widget de référence (`examples/external-widget`) et un guide d'écriture existent, ce qui est une base de documentation que n'ont pas toujours les concurrents.
- Opportunité : un contrat v1 versionné, des paquets signés et un statut « approuvée » donneraient une valeur de différenciation face à ArcGIS Experience Builder et à FME Hub.
