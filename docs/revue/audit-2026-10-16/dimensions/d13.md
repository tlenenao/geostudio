# d13 — ETL : qualité de données

Audit en lecture seule (2026-10-16). Aucun test lancé. 5 constats vérifiés dans le code, 2 Minor non vérifiés (marqués comme tels).

## Synthèse

Le couple `transform.detectChanges` puis `writer.collection` en upsert ne peut pas synchroniser de données réelles (D13-01). La validation reste mince : non-null et unicité seulement, sans validité géométrique ni seuil de qualité. Les colonnes de sortie ne sont pas gardées contre les collisions de noms. La quarantaine existe et fonctionne.

## Constats

### D13-01 — Critical — bug — detectChanges ne projette que clés + statut

- Fichiers : `core/app/pipelines/compiler.py:684-715`, `core/tests/test_pipeline_runtime.py:2982-2985`, `core/app/pipelines/ops/schemas.py:82-90`
- Preuve : `_compile_detect_changes` retourne `SELECT {key_select}, ({status_expr}) AS statut FROM input t FULL OUTER JOIN join o ON ...`. Seules les clés et le statut sortent (relu aux lignes 709-714). Le test `test_pipeline_runtime.py:2985` verrouille ce comportement (`set(rows[0].keys()) == {'id','status'}`). La description de `WriterCollectionParams.statusColumn` promet que l'upsert écrit inserted/updated et ignore unchanged.
- Reproduction : `reader.collection(A)` → `transform.detectChanges(withCollectionId=B, keyColumns=[id], statusColumn=st)` → `writer.collection(mode=upsert, statusColumn=st, keyColumns=[id])`. Les lignes inserted n'ont que `id`, la géométrie est NULL. Les lignes deleted n'ont aucune donnée.
- Correctif : émettre `t.*` plus le statut. Pour les deleted, reprendre `o.*` par COALESCE sur les colonnes communes. Mettre à jour le test. Option : `emit: all|changedOnly` et sorties séparées par statut (ports FME Inserted/Updated/Deleted/Unchanged).

### D13-02 — Important — bug — clé NULL mal classée, doublons en fan-out silencieux

- Fichiers : `core/app/pipelines/compiler.py:696-710`
- Preuve : le statut se décide sur `t.<keyColumns[0]> IS NULL` puis `o.<keyColumns[0]> IS NULL`. Une clé NULL ne matche jamais. Une ligne « avant » à clé NULL reçoit 'inserted' au lieu de 'deleted'. Seule la 1re clé d'un jeu composite est testée. Aucune détection de doublon : un doublon côté t ou o multiplie les lignes.
- Reproduction : avant {id:NULL,v:1}, après {} : statut 'inserted' (attendu 'deleted'). Deux lignes id=1 de chaque côté : 4 lignes de sortie, statuts arbitraires.
- Correctif : colonne sentinelle `__present` via sous-requête au lieu de tester la clé. Option `onDuplicateKey: fail|first|reject` avec contrôle `GROUP BY clé HAVING COUNT(*)>1`. `IS NOT DISTINCT FROM` pour les NULL si voulu.

### D13-03 — Important — parité — aucun validateur ni réparateur de géométrie

- Fichiers : `core/app/pipelines/ops/contracts.py`, `core/app/features/validation.py:44-145`, `core/app/pipelines/collection_writer.py:455-466`
- Preuve : aucune occurrence de ST_IsValid/ST_MakeValid/GeometryValidator/Repair dans `ops/*.py` ni `compiler.py`. `validate_feature` (l.134-145) ne vérifie que le type de géométrie, jamais la validité topologique.
- Reproduction : polygone « nœud papillon » importé puis `writer.collection` : accepté. `transform.intersection` sur cette couche échoue (GEOS) ou donne un résultat faux.
- Correctif : op `transform.validateGeometry` (isValid, reason via ST_IsValidReason, `repair` via ST_MakeValid) branchable sur `rejectWhenFalse`. Règle optionnelle `geometry_invalid` dans `write_rows`. Parité FME GeometryValidator et ArcGIS Check/Repair Geometry.

### D13-04 — Important — parité — validateAttributes très pauvre

- Fichiers : `core/app/pipelines/compiler.py:637-652`, `core/app/pipelines/ops/schemas.py:596-615`
- Preuve : seuls `nonNullColumns` et `uniqueColumns` existent. Le non-null est un `IS NOT NULL` simple (chaîne vide ou blanche acceptée). L'unicité utilise `COUNT(*) OVER (PARTITION BY ...) = 1` : les NULL sont comptés comme une seule valeur, donc toutes les lignes à clé NULL sont non uniques (sémantique SQL UNIQUE non respectée). Un seul booléen agrège toutes les colonnes, la règle en échec n'est pas identifiable.
- Reproduction : `name=''` passe nonNull. Trois lignes `code` NULL avec `uniqueColumns=[code]` : toutes `false`.
- Correctif : liste de `rules` typées {column, kind: notNull|notBlank|regex|range|enum|length|expression(CEL), resultColumn?, severity}. Colonne `__errors` (LIST) pour que la quarantaine porte le motif. Paramètre `ignoreNulls`. Réutiliser `_effective_domain` des collections.

### D13-05 — Important — sécurité (intégrité) — collision de colonnes de sortie non gardée

- Fichiers : `core/tests/test_pipeline_fme_review_guards.py:75-77`, `core/app/pipelines/ops/schemas.py:596-615`, `core/app/pipelines/compiler.py:643-650`
- Preuve : la garde `no_op_output_param_accepts_geometry` exempte explicitement (BASE_UNGUARDED) `validateAttributes.nonNullResultColumn`/`uniqueResultColumn` et `detectChanges.statusColumn`. Aucun validateur de nom sur ces modèles. `SELECT *, (...) AS "geometry"` produit deux colonnes `geometry`.
- Reproduction : `validateAttributes {nonNullColumns:['a'], nonNullResultColumn:'geometry'}` accepté à l'écriture (422 attendu), échec à l'exécution seulement. `nonNullResultColumn == uniqueResultColumn` et `statusColumn ∈ keyColumns` passent aussi.
- Correctif : `model_validator` commun (nom ≠ geometry/vide, résultats distincts, statusColumn ∉ keyColumns), retirer les 3 entrées de BASE_UNGUARDED, idéalement contrôle contre les colonnes amont.

### D13-06 — Important — différenciateur — aucun seuil de qualité

- Fichiers : `core/app/pipelines/collection_writer.py:90-122`, `core/app/pipelines/collection_writer.py:486-495`, `core/app/pipelines/repository.py:268-270`, `core/app/pipelines/ops/schemas.py:98-104`
- Preuve : `WriterCollectionParams` n'a que `onInvalid` et `rejectWhenFalse`. `mark_succeeded` (repository.py:268-270) passe en `succeeded_with_rejects` dès qu'un nœud a des rejets, même à 100 %. `quality_report` ne porte que null/distinct/min/max.
- Reproduction : colonne obligatoire vide : 100 % en quarantaine, 0 écrit, run non en échec ; alertes et webhooks ne le distinguent pas.
- Correctif : `qualityGate: {maxRejectRate, minRows, maxNullRate}` évalué avant le commit final, échec propre (rollback) ou statut `failed_quality`. Taux de rejet dans l'événement outbox.

### D13-07 — Minor — dette — quarantaine sans géométrie, rejets en mémoire (NON VÉRIFIÉ)

- Fichiers : `core/app/pipelines/collection_writer.py:399-409`, `:486-487`, `:195-214`
- Preuve (rapportée, non revérifiée) : `reject()` exclut `geometry` des lignes en quarantaine ; `rejects` est une liste vidée une seule fois après la boucle (`_store_rejects`) ; `seen` croît sans borne.
- Reproduction : 5 M de lignes dont 50 % de clés NULL : mémoire proportionnelle aux rejets, rien persisté si le run échoue à 90 %.
- Correctif : flush par lot dans la transaction du lot, géométrie en WKT sous la même RLS, plafond `maxStoredRejects` avec compte total.

### D13-08 — Minor — différenciateur — rapport qualité limité au writer (NON VÉRIFIÉ)

- Fichiers : `core/app/pipelines/collection_writer.py:90-122`, `:369`, `core/app/pipelines/runtime.py:1192-1207`
- Preuve (rapportée, non revérifiée) : `quality_report` appelé une seule fois (l.369), 50 colonnes max ; pas de nœud de profilage ni de contrat de schéma ; `mapSchema` complète par NULL sans alerte ; pas d'historique de qualité par run.
- Correctif : ops `transform.profile` et `transform.assertSchema` (fail|warn), AlertRule « dérive de qualité », historique par run.

## Avantages et différenciateurs

- Quarantaine `<cible>__rejected` fonctionnelle avec statut `succeeded_with_rejects` et détail `rejects_by_rule` dans `node_stats`.
- `quality_report` (null/distinct/min/max) à l'écriture.
- `detectChanges` utilise `IS DISTINCT FROM` pour comparer les attributs (NULL-safe sur les valeurs).
- Opportunité : un `qualityGate` natif serait un différenciateur net face à FME et ArcGIS ; un `detectChanges` à sorties séparées par statut donnerait la parité ChangeDetector.
