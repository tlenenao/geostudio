## Important

### 1. Six gardes d'egress SSRF copiées-collées — tag `dette`

**Preuve.** Six modules reproduisent le même schéma de garde (`_allowlist` / `_is_internal`) : `core/app/alerts/egress.py:29-37`, `copilot/egress.py:49-57`, `geocoding/egress.py:27-34`, `harvest/egress.py:46-54`, `pipelines/egress.py:43-51`, `search/egress.py:54-62`. Chacun porte la même ligne `not ip.is_global or ip.is_multicast or getattr(ip, 'is_site_local', False)` et le même commentaire j06-003. Seuls l'env var d'allowlist, le défaut et le client (requests/httpx) varient. La docstring de `alerts/egress.py` assume la « duplication délibérée ». `app/net_pin.py` factorise déjà la partie épinglage IP. Le correctif j06-003 a dû être répliqué 6 fois ; les copies sont identiques aujourd'hui, la prochaine dérive est inévitable.

**Reproduction.** `diff core/app/alerts/egress.py core/app/geocoding/egress.py` : seuls l'env var, le défaut d'allowlist et le client diffèrent. `grep -n 'def _is_internal' -A5 core/app/*/egress.py` : corps identiques.

**Correctif.** Extraire `app/egress_guard.py` avec `assert_public_host(url, allowlist_env, default=...)` et `is_internal(ip)`, sous le contrat de couches. Chaque domaine ne garde que son env var et son client. Un test paramétré unique (IPv4 CGNAT, fec0::/10, multicast, DNS multi-A) exécuté sur toutes les entrées.

Or `app/jobs/common.py:30-33` importe `app.items.models`, `app.users.models` et `app.notifications`, alors que `app/items/repository.py:24` et `app/collections/repository.py:10` (couches basses) importent `app.jobs.after_commit` : cycle de paquets items → jobs → items/notifications que le linter ne voit pas. `app/pipelines/service.py:23` importe aussi `jobs.common`.

### 3. mypy --strict ne couvre que 7 chemins, le périmètre large est non bloquant — tag `dette`

**Preuve.** `.github/workflows/ci.yml:118` : `mypy --strict app/auth app/secrets app/analytics app/copilot app/admin_tools app/roles app/net_pin.py`. `ci.yml:134-135` : étape « Mypy (périmètre large, non bloquant) » → `uv run mypy app/ || true`. **Correctif.** Mesurer le nombre d'erreurs de `mypy app/`, rendre le job bloquant avec un baseline (mypy-baseline ou `--exclude` par paquet), puis étendre le périmètre strict d'un paquet par SP, en commençant par features, collections, items et pipelines/runtime.

### 4. Pièce jointe : le PUT S3 du widget Formulaire ignore le statut de la réponse — tag `bug`

**Preuve.** `shell/src/builder/widgets/form.tsx:306` : `await fetch(uploadUrl, { method: "PUT", body: file, headers: { "Content-Type": file.type } });` sans test de `res.ok`, puis `client.confirmAttachmentUpload` (l. 307-312). Une 403 SignatureDoesNotMatch ou une 5xx S3 est silencieuse ; l'erreur n'apparaît qu'au confirm (`core/app/attachments/routes.py:226`, `head_object`) avec un message sans rapport avec la cause. Les autres sites de PUT vérifient `.ok` (`api/domains/exportsIngestion.ts:89-90`, `shell/Tileset3DUploadButton.tsx:110-111`). Au passage : le `Content-Type` du PUT est `file.type` brut alors que le presign a été signé avec `contentType` (repli `application/octet-stream`) ; pour un fichier sans type, l'en-tête diffère de la valeur signée.

**Reproduction.** Mocker le PUT présigné en 403 dans un E2E de pièce jointe : le code enchaîne sur `confirmAttachmentUpload` au lieu d'afficher un échec de téléversement.

**Correctif.** Remplacer le `fetch` brut par `client.uploadToPresignedUrl(uploadUrl, file)` (lève sur `!res.ok`) avec le `contentType` signé. Test vitest « PUT 403 → pas de confirm ».

### 5. Export autoporté : le mini-serveur « miroir » n'a pas la parité de filtrage de l'API du cœur — tag `parite`

**Preuve.** `core/app/appexport/miniserver/main.py:105-111` : `list_items` n'accepte que limit/offset/bbox ; `select_features` (`miniserver/items.py:76-90`) ne construit que bbox et geomIntersects, ORDER BY pk fixe. Le cœur expose `sortby`, `datetime`, `crs`, `bbox-crs`, `cursor`, `filter`/`filter-lang`/`filter-crs` et les filtres d'attribut (`core/app/features/routes.py:317-332`). FastAPI ignore les paramètres inconnus : une app exportée qui envoie un filtre, un tri ou un CQL reçoit silencieusement des données non filtrées. Le docstring de `miniserver/items.py:2` revendique pourtant « miroir de app.features.repository ».

**Reproduction.** Dans une app « Autoportée » exportée : `GET /v1/collections/{id}/items?sortby=-nom&limit=5` renvoie l'ordre par PK ; `?filter=...` renvoie tout.

**Correctif.** Soit répondre 400 sur tout paramètre non supporté (échec au moins visible), soit extraire la grammaire de filtre (cf. constat 6) dans un module pur partagé cœur + mini-serveur et brancher sortby/datetime/filter. Ajouter un test de parité contractuel cœur↔miniserveur sur un snapshot commun.
