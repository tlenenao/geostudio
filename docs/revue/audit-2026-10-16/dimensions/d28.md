# d28 — Performance perçue

Audit en lecture seule du code shell, aucun test lancé. Le découpage par route est réel : la charge JS/CSS initiale est de 631 Ko brut pour un seuil de 640 Ko. Les faiblesses sont ailleurs : poids des chunks de route, absence de préchargement, perte de contenu à chaque changement de requête, tableau client limité à 100 lignes. LCP et gzip non mesurés (le `dist/` présent est possiblement antérieur au code courant).

## Important

### 1. Le chunk MapView embarque deck.gl et loaders.gl 3D-Tiles même pour une carte 2D simple
- Tag : polish — Vérifié
- Preuve : `shell/src/map/mapDeckTerrain.ts:2-7` importe statiquement maplibre-gl, `@deck.gl/mapbox`, aggregation-layers (Heatmap/Hexagon), layers (Column), geo-layers (Tile3DLayer) et `@loaders.gl/3d-tiles`. `shell/src/map/MapView.tsx:40` importe ce module en statique. `dist/.vite/manifest.json` : `assets/MapView-*.js` = 1 180 336 octets (en plus de vendor-map, 933 Ko). Le commentaire de `shell/vite.config.ts` reconnaît que deck.gl est laissé au chunking automatique.
- Reproduction : ouvrir `/maps/:id` avec une seule couche vectorielle, réseau bridé 4G lente ; le chunk de 1,18 Mo est téléchargé et évalué avant le premier rendu.
- Correctif : dans `mapDeckTerrain.ts`, charger les couches par `import()` dynamique (loader mémoïsé, `await` avant création de la couche), y compris `MapboxOverlay`. Vérifier avec `check-bundle-size` et le manifeste que MapView passe nettement sous 300 Ko.

### 2. Aucun préchargement des chunks lourds : cascade page, MapView, vendor-map
- Tag : differenciateur — Vérifié
- Preuve : les 55 `lazy()` ne se déclenchent qu'au rendu ; recherche de prefetch/modulepreload/onMouseEnter+import dans `shell/src` hors tests : 0 résultat. MapEditorPage (8,8 Ko) a pour imports dynamiques MapView et AddressSearch : trois allers-retours en série (page, MapView, vendor-map ~2,1 Mo). Idem SqlLabPage (444 Ko) et PipelineBuilderPage (213 Ko). Repli = `<LoadingState/>` (`shell/src/shell/routes.tsx:252, :389, :408`).
- Reproduction : depuis `/`, cliquer une carte en 4G émulée ; spinner pendant toute la cascade. `e2e/journeys/t03/vitals.spec.ts` mesure ce parcours mais n'est pas lancé en CI.
- Correctif : helper `prefetchRoute(kind)` appelé sur `onMouseEnter`/`onFocus` des liens du catalogue et d'`ItemCard`, et en `requestIdleCallback` après le premier rendu ; remplacer le spinner par un squelette de page.

### 3. Catalogue : chaque frappe, filtre ou page remplace la liste par un spinner
- Tag : polish — Vérifié
- Preuve : `shell/src/api/domains/items.hooks.ts:17-21` : `useQuery({queryKey:["items", params], ...})` sans `placeholderData`. Seuls `notifications.hooks.ts:11` et `extensionsAdminTools.hooks.ts:91` utilisent `keepPreviousData`. `shell/src/pages/CatalogPage.tsx:359` : `query.isLoading && <LoadingState/>` ; la liste (`:429`) disparaît dès que la clé change.
- Reproduction : taper dans la recherche ou cliquer « page suivante » : grille, spinner, grille.
- Correctif : `placeholderData: keepPreviousData` dans `useItems` et `useItemFacets` ; atténuer la grille via `isPlaceholderData` (opacité, `aria-busy`). Idem listes admin paginées.

### 4. Widgets de données : tout changement de filtre ou de cross-filter remet les widgets en chargement
- Tag : differenciateur — Vérifié
- Preuve : `shell/src/builder/DataContext.tsx:93-105` : `useQueries` avec `queryKey ["datasource", s.id, merged.query]` (filtres, temps, emprise, cross-filter inclus), sans `placeholderData` ; `loading: r.isLoading` (`DataContext.tsx` ~l.123). `shell/src/builder/widgets/data.tsx:116` et `:308` : `if (!data || data.loading) return <LoadingState/>` remplace tout le widget.
- Reproduction : dashboard avec tableau et graphique reliés par cross-filter ; clic sur une catégorie : spinner au lieu d'une mise à jour en place. Idem au déplacement de carte avec un dataset sensible à l'emprise.
- Correctif : `placeholderData: (prev) => prev`, exposer `isFetching` avec un indicateur discret ; réserver `LoadingState` au premier chargement.

### 5. Widget tableau : tri et pagination côté client sur les 100 premières lignes
- Tag : parite — Vérifié
- Preuve : `shell/src/api/domains/datasets.ts:103-107` : `buildFeaturesUrl` n'ajoute ni limit, ni offset, ni sortby ; le cœur a `limit` par défaut (`core/app/features/routes.py`, paramètre `limit` ~l.88, défaut 100 d'après l'audit). `data.tsx:324-334` : tri local de `data.records` puis découpe par `pageSize` (10). Le message `widgetData.truncated` signale sans corriger. Le widget liste (`data.tsx` ~145) rend toutes les lignes sans virtualisation.
- Reproduction : lier le tableau à une collection de plus de 100 entités, trier par colonne : l'ordre n'est global que sur 100 entités ; pied « tronqué ».
- Correctif : passer `limit=pageSize`, `offset`, `sortby` dans la requête (clé comprise), utiliser `data.total` pour le nombre de pages ; avec le constat 4 la pagination reste fluide. Virtualiser si `pageSize` est grand.
