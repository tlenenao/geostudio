## Important

### I1 — Un worker tué laisse le `lock` procrastinate : compaction et snapshot CDC ne repartent plus
- **Tag** : bug — **Vérifié**
- **Preuve** : `app/cdc/jobs.py:49, 55, 154` posent `lock="cdc_compaction"` / `lock="run_snapshot_cycle"`. Le schéma procrastinate crée l'index unique `procrastinate_jobs_lock_idx_v1 ON (lock) WHERE status='doing'` (schema.sql:101-102) et `fetch_job` écarte tout job dont le lock est tenu par un `doing` (schema.sql:224-235). `get_stalled_jobs` n'est appelé que par `scripts/healthcheck_worker_stalled.py:30`, qui ne fait que faire échouer la sonde. Aucun `retry_stalled_jobs` dans le dépôt ; aucun autoheal dans le compose.
- **Reproduction** : lancer `run_compaction_cycle_task`, `kill -9` du worker (ou OOM, `mem_limit` 2g). La ligne reste `doing` avec son lock ; tous les cycles suivants restent `todo`. Le lac accumule de petits fichiers sans alerte, la sonde passe seulement `unhealthy`.
- **Correctif** : au démarrage du worker et périodiquement, récupérer les jobs `doing` dont le worker est absent (`get_stalled_jobs()` puis `retry_job_by_id_async`), ou libérer le `lock` de ces tâches idempotentes avec `queueing_lock`. Ajouter un redémarrage sur `unhealthy` ou une alerte Grafana.

### I2 — Aucun timeout d'exécution sur les jobs synchrones
- **Tag** : bug — **Vérifié**
- **Preuve** : `pipelines/repository.py:356-380` (`reclaim_stuck_runs`), l'ingestion (`reclaim_stuck_jobs`) et `export/repository.py:~140` ne font que passer la ligne en `failed`/`error` après 60 min (`app/job_timeouts.py:8`, `DEFAULT_RUNNING_RECLAIM_MINUTES = 60`). Le job procrastinate reste `doing`, son thread garde un des slots `-c ${CORE_WORKER_CONCURRENCY:-4}` (`docker-compose.yml:545`). Aucun `wait_for`, `signal.alarm` ni `timeout=` sur le corps des jobs dans `app/pipelines/jobs.py` et `app/ingestion/tasks.py`.
- **Reproduction** : 4 `reader.connector.*` ou imports GDAL bloqués (socket sans timeout, requête DuckDB infinie). Les 4 slots sont pris, les files `etl`/`ingestion` ne progressent plus, alors que l'UI affiche « failed : périmé ». Worker `unhealthy`, sans redémarrage.
- **Correctif** : corps lourds dans un sous-processus avec échéance dure (kill), ou timeouts DuckDB/HTTP/`statement_timeout` par nœud ; la réclamation du statut doit aussi annuler le job ; redémarrage automatique si la sonde stalled échoue.

### I3 — Run de pipeline vivant > 60 min déclaré périmé : double exécution possible
- **Tag** : bug — **Vérifié**
- **Preuve** : `pipelines/repository.py:356-380` : `reclaim_stuck_runs` passe en `failed` tout run `running` dont `started_at` dépasse 60 min (commentaire « pas de heartbeat »). `repository.py:66-100` : `create_run_unless_active` ignore les runs plus vieux que `stale_minutes`=60. `pipelines/jobs.py:456` puis `460-488` : le même balayage réclame puis crée aussitôt le run planifié suivant. `mark_succeeded` (`repository.py:263-275`) est inconditionnel et écrase le statut.
- **Reproduction** : pipeline cron dont le run légitime dure 75 min. À 60 min : marqué `failed`, webhook « run finished » émis, nouveau run créé ; deux `writer.collection` écrivent la même cible. À la fin du premier, `mark_succeeded` repasse `succeeded` et un second événement de fin part.
- **Correctif** : heartbeat (`last_progress_at` mis à jour par `append_node_stat` et un thread périodique), réclamation ancrée dessus ; `mark_succeeded`/`mark_failed` conditionnels sur le statut lu ; seuil configurable.

### I4 — Defer perdu après création d'un run de pipeline : blocage 409 pendant 60 min
- **Tag** : bug — **Vérifié**
- **Preuve** : `pipelines/service.py:113-118` (`session.commit()` puis `defer_task(...)` sans try/except). Le balayage (`pipelines/jobs.py:445-449`) ne re-défère que les `retrying` en retard (`requeue_overdue_retries`), jamais les `queued`. Les jumelles quality (`quality/jobs.py:67-70`, `stale_pending_ids`) et geocode (`geocoding/jobs.py:141-150`) le font. `create_run_unless_active` renvoie 409 tant que le run `queued` a moins de 60 min.
- **Reproduction** : couper la base ou le pool procrastinate entre `commit` et `.defer()` : 500, ligne `queued` orpheline ; tous les « Exécuter » (REST, MCP, webhook, cron) répondent 409 pendant 60 min, puis le run est clos en erreur sans avoir tourné.
- **Correctif** : dans `run_pipeline_sweep_task`, re-déférer les `queued` de plus de ~2 min ; try/except autour du `defer` des routes. Jumelles à traiter dans le même geste : `export/routes.py:68`, `appexport/routes.py:60`, `raster/routes.py:78`, `terrain3d/routes.py:52`, `tileset3d/routes.py:86`, `dataexport/routes.py:30`.

### I5 — Alertes : defer perdu, évaluation `pending` reprise après 60 min, boucle abandonnée à la première exception
- **Tag** : bug — **Vérifié**
- **Preuve** : `alerts/jobs.py:595-612` : `evaluate_alert_task.defer` sans try/except dans la boucle, après `create_evaluation` et `commit` ; une exception arrête le balayage pour les règles suivantes. `alerts/repository.py:18` (`_PENDING_RECLAIM_MINUTES = 60`), `list_due_rules` (~178-185) et `alerts/service.py:62-66` : une évaluation `pending` n'est replanifiée qu'après 60 min (quality : 5 min), et par nouvelle ligne, sans re-defer.
- **Reproduction** : coupure de quelques secondes pendant le balayage : la règle X reste `pending`, la règle Y suivante n'est pas traitée. La transition d'état (seul déclencheur de notification) est retardée d'au moins 60 min.
- **Correctif** : try/except par règle avec log ; re-déférer les `pending` de plus de ~5 min ; garder 60 min uniquement pour `running`.

### I6 — Webhooks sortants : désactivation après 5 échecs, événements en attente détruits
- **Tag** : différenciateur — **Vérifié**
- **Preuve** : `webhooks/delivery.py:28` `MAX_CONSECUTIVE_FAILURES = 5` ; l.98-104 chaque échec incrémente `hook.consecutive_failures`, à 5 `_disable` passe tous les événements `pending` de la destination en `failed` (l.133-140). `deliver_due` (l.200-225) livre 10 événements par lot : 5 événements et un récepteur indisponible 10 s suffisent. Seul un replay manuel par événement existe (`webhooks/routes.py:255-290`, exige la destination déjà réactivée) ; pas de replay en masse.
- **Reproduction** : destination avec 6 événements `pending`, récepteur en 503 une minute. Au premier balayage, 5 échecs : destination désactivée, événements `failed`, notification. Réactiver puis rejouer à la main chaque événement ; la garantie « au moins une fois » de l'ADR 0027 est perdue.
- **Correctif** : compter les échecs par fenêtre de temps (au plus +1 par tick), désactiver après N heures sans succès, conserver les `pending` (statut `paused`) et les rejouer à la réactivation, ajouter `POST /webhooks/{id}/replay-failed`.

## Minor (non vérifiés)

### M1 — Moissonnage : re-defer à chaque tick d'un job non pris (rafales après panne) — NON VÉRIFIÉ
- **Tag** : bug
- **Preuve** : `harvest/jobs.py:58-68` : `run_harvest_task.defer` par source due, sans `queueing_lock` ni `lock`. `harvest/repository.py:~345-380` n'exclut qu'une source `running` ; `mark_running` (~172-200) ne vérifie pas l'échéance.
- **Reproduction** : worker `harvest` arrêté 2 h : 8 ticks de 15 min déposent 8 jobs par source ; au redémarrage, chaque source est moissonnée jusqu'à 8 fois d'affilée (egress multiplié).
- **Correctif** : `queueing_lock=f"harvest:{source_id}"` via `.configure(...)`, ou `mark_running` vérifie que la source est toujours due.

### M2 — Ingestion : collection committée avant `mark_done` — NON VÉRIFIÉ
- **Tag** : bug
- **Preuve** : `ingestion/tasks.py:178-196` : `run_import` commit (collection, table, lignes), puis `_delete_source`, puis `mark_done` dans une autre session ; toute exception entre les deux passe par `except Exception` (l.213-221) → `mark_error` + notification d'échec. `run_append` (l.158-170) a la même fenêtre.
- **Reproduction** : tuer le worker juste après le commit : job « error / timed out » alors que la collection existe ; relancer l'import crée un doublon.
- **Correctif** : `mark_done` dans la même transaction que la création, ou enregistrer `collection_id` avant le commit final pour que le balayage conclue `done`.

### M3 — Embedding : vecteur périmé jamais rafraîchi — NON VÉRIFIÉ
- **Tag** : dette
- **Preuve** : `items/jobs.py:57-66` : `sweep_missing_embeddings_task` ne sélectionne que `embedding IS NULL`, lot de 100 plus récents (risque de famine des plus anciens). `embed_item_task` (l.27-43) avale toute exception. L'enqueue (`items/repository.py:~74-85`) ne capture que `ProcrastinateException`.
- **Reproduction** : modifier le titre d'un item déjà indexé alors que la file est indisponible : la recherche sémantique garde l'ancien vecteur, aucun balayage ne le corrige.
- **Correctif** : colonne `embedding_updated_at` (ou hash du texte), sélection `embedding IS NULL OR embedding_updated_at < updated_at`, pagination par curseur.

## Avantages et différenciateurs

- Ni ArcGIS ni FME ne proposent de reprise automatique unifiée, de timeout par job ni de garantie « un seul run par pipeline ». Le cœur possède déjà presque toutes les briques (balayages par type de job, `create_run_unless_active`, outbox de webhooks) ; il manque un superviseur commun (heartbeat + re-defer + timeout) pour en faire un argument produit.
- Outbox de webhooks rejouable (ADR 0027) : réel différenciateur face aux automatisations sortantes de FME Flow, à condition de corriger I6.
- Migrations Alembic récentes (0070, 0071, 0072, 0054, 0030, 0039) : `downgrade` corrects et idempotents, tête unique 0081.
- Balayages de reprise présents pour quality, geocode, ingestion, export, appexport, raster et 3D ; quality/geocode fournissent le patron à reporter sur pipelines, alertes et exports.
