## Méthode

Huit cartographes ont inventorié indépendamment les fonctionnalités du dépôt,
chacun sur une tranche du code (shell, cœur, builder, cartographie,
fédération, automatisation, infrastructure, administration). Pour **chaque**
ligne, une preuve `chemin:ligne` vérifiée dans le code source est obligatoire
— jamais une affirmation tirée de `CLAUDE.md`, d'une spec ou d'un plan, qui
sont des récits d'intention et non une source de vérité. Les huit fragments
ont ensuite été consolidés en une matrice unique de **304 lignes**
(`.superpowers/sdd/sp42-matrice.jsonl`), vérifiée mécaniquement (schéma,
preuves non vides, notes obligatoires présentes pour tout état non `livre`)
puis par un réviseur indépendant qui a rejoué 8 arbitrages de désaccord entre
fragments et échantillonné 15 preuves au hasard. Ce document est un **rendu**
de cette matrice, pas une nouvelle collecte : le JSONL source n'est pas
modifié par ce rendu.

**Regroupement d'affichage.** La matrice distingue 65 domaines — un par
angle de cartographie, trop fin pour un document lisible. Ils sont
regroupés ici, pour l'affichage seulement, en **10 familles** (Catalogue,
Cartes, Données, Apps & sites, Automatisation, Analytique, Fédération,
Administration, Infrastructure, SDK & extensibilité). Chaque section
rappelle la liste des domaines de cartographie qu'elle regroupe, et la
colonne « Domaine » de chaque tableau conserve le libellé d'origine du
cartographe — aucune information n'est perdue par le regroupement, qui vit
entièrement dans le script de rendu, jamais dans les données sources.

## Les cinq états

| État | Signification |
|---|---|
| **livré** | La fonctionnalité fonctionne de bout en bout sur au moins une surface, avec preuve de test. |
| **partiel** | Une partie fonctionne réellement ; ce qui manque est décrit par la note (obligatoire). |
| **inerte** | Le code existe, est testé, est mergé dans `dev` — **mais rien ne l'atteint** : aucune route ne le monte, aucun bouton ne l'appelle, aucun consommateur réel ne l'exerce en dehors de ses propres tests. Ce n'est pas la même chose qu'un défaut fonctionnel : le code est correct dans l'absolu, il est simplement inaccessible depuis un usage normal du produit. **C'est la trouvaille la plus significative de cette revue** — 13 lignes, détaillées ci-dessous et reprises dans `docs/revue/2026-09-04-analyse-gaps.md`. |
| **prévu** | Décidé (arbitrage §8 de la feuille de route, ou décision actée en session) mais aucun code n'existe encore. |
| **absent** | Ni décidé ni codé — trou constaté par la revue, pas nécessairement une intention du produit. |

## Comment lire les notes

Chaque fonctionnalité porte six critères notés de 0 à 10 par les cartographes
qui l'ont inventoriée, en s'appuyant sur le code lu et sur les trouvailles de
la revue (sécurité, tests, gaps) — **ce sont des jugements d'agents, pas des
mesures**. Aucun des six n'est calculé automatiquement ; deux cartographes
raisonnables peuvent diverger d'un point sur une même ligne. La **note
globale** est la moyenne arrondie à deux décimales de ces six critères.

| Critère | Ce qu'il évalue |
|---|---|
| **utilité** | La fonctionnalité répond-elle à un vrai besoin produit, pour un usage réel du dépôt ? |
| **qualité du code** | Lisibilité, séparation des responsabilités, absence de duplication ou de raccourci fragile. |
| **sécurité** | Autorisation, RLS, garde d'egress, validation d'entrée — absence de trouvaille de la revue. |
| **tests** | Couverture réelle (unitaire/intégration/E2E), pas seulement leur présence déclarée. |
| **complétude** | La fonctionnalité fait-elle ce qu'elle promet de bout en bout, ou reste-t-il un bout non fait ? |
| **découvrabilité** | Un utilisateur ou un agent peut-il *trouver* la fonctionnalité depuis un usage normal du produit ? |

**Ancrages communs aux six critères** (l'échelle est la même partout, seul
l'objet noté change) :

| Plage | Signification |
|---|---|
| **0-3** | Problématique — absent, cassé, non testé, ou risque de sécurité réel identifié par la revue. |
| **4-6** | Moyen — fonctionne mais incomplet, fragile, peu découvrable ou insuffisamment testé. |
| **7-8** | Bon — solide et testé, réserves mineures seulement. |
| **9-10** | Excellent — aucune réserve identifiée sur ce critère par la revue. |

Dans les tableaux ci-dessous, la colonne **Note** porte la note globale
(mise en **gras** sous 5/10, pour repérer les points faibles d'un coup
d'œil) ; le détail des six critères et, si elle existe, une **suggestion**
concrète d'amélioration figurent dans la ligne de détail sous le libellé de
la fonctionnalité, à la suite de la note qualitative du cartographe quand
elle existe.


## Limite de l'exercice

**Cette matrice est une photo datée, pas l'état courant du dépôt.** Elle
décrit le dépôt tel qu'observé au commit `87eb55ad`. Depuis, `HEAD` a
sensiblement avancé — une session concurrente et 41 commits de correctifs
produits par SP-42 lui-même se sont ajoutés — et une partie des défauts que
cette matrice reflète a déjà été corrigée par ces commits ultérieurs. Ne pas
lire ce document comme une déclaration sur ce que le dépôt sait faire
aujourd'hui : c'est un instantané qui a servi de matière première à
l'analyse des manques (`analyse-gaps.md`) et au backlog (`backlog.md`), et il
se périme au même rythme que tout inventaire figé sur un dépôt qui continue
d'avancer.

## Surfaces manquantes

### MCP (12)

- **[Automatisation] Consulter l'historique des exécutions d'un pipeline** — Un agent MCP peut créer/lancer/expliquer un pipeline mais ne peut pas consulter l'historique de ses exécutions passées — jumelle de lecture manquante pour un agent qui diagnostiquerait un échec.
- **[Automatisation] Inspecter les couches d'un GeoPackage/Shapefile avant de choisir laquelle importer** — Aucun outil MCP n'expose l'inspection ni le déclenchement d'un import de fichier — un agent ne peut pas piloter l'ingestion de données de bout en bout.
- **[Catalogue/Items] Historique de versions et rollback d'une config** — Aucun outil MCP restore_config : un agent qui vient de casser une config par une écriture malheureuse ne peut pas revenir en arrière sans repasser par l'UI.
- **[Catalogue/Items] Publier / dépublier un item** — Aucun outil MCP ne bascule isPublished directement — seul un PATCH générique existerait à construire à la main, sans garde dédiée côté agent.
- **[Collections] Lire le schéma d'une collection (champs + pièces jointes)** — Un agent qui construit un formulaire ou une requête via create_form_app/run_analytics_query n'a aucun moyen de découvrir d'abord les champs disponibles d'une collection (pas de get_collection_schema).
- **[Collections] Lister/rechercher les collections (recherche hybride)** — search_catalog (MCP) ne cherche jamais les collections, seulement les items (docstring explicite "items only") — aucun outil MCP ne peut découvrir une collection par recherche sémantique.
- **[Features (OGC API)] Créer/modifier/supprimer une entité (OGC Part 4)** — Aucun outil MCP en écriture sur les entités (query_features est la seule opération MCP, en lecture) ; un agent IA ne peut pas créer/modifier/supprimer de feature.
- **[Features (OGC API)] Filtrer les features par intersection géométrique exacte (ST_Intersects)** — query_features (MCP) ne relaie pas geom_intersects alors que le produit en dépend directement (cross-filter carte, SP-14n).
- **[Recherche] Recherche hybride des collections (même mécanisme RRF que les items)** — La recherche fonctionne au niveau repository mais n'a aucun consommateur : ni le shell (ItemClient sans paramètre q), ni le MCP (search_catalog exclut explicitement les collections).
