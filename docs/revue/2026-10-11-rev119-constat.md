# Constat REV-119 / GAP-25 — couche sémantique (Task F1, 2026-10-11)

Question : un dataset porte-t-il des métriques CEL nommées, versionnées, réutilisables par plusieurs widgets/requêtes ?

## Constat (vérifié dans le code, pas dans les récits)

- `DatasetPayload` (`core/app/configs/schemas.py:185-196`) ne porte que `columns: dict[str, DatasetColumnMeta]` (`:159-163` : label/description/format, pas d'expression), `timeField`, `reactsToExtent`, `crossFilterLinks`, `sourcePipelineId`. Aucun champ `metrics`.
- Une mesure est définie à chaque requête : `AggregateMeasure` (`core/app/analytics/aggregate.py:31-38`, field/agg/label/p), sans résolution par nom.
- Les « métriques » du pipeline (`core/app/pipelines/ops/schemas.py:44`, `metrics: dict[str, str]`) sont locales à un nœud `transform.aggregate`, pas au dataset.
- Les colonnes calculées CEL vivent dans la config du widget (`shell/src/builder/widgets/data.tsx:254`, contexte `computedColumn`), donc redéfinies par widget.
- Versionnement : la config du dataset est versionnée en bloc (`configs.current_version`, `core/app/configs/models.py:27`), mais il n'existe aucune métrique à versionner.
- La spec/plan GAP-25 (`docs/superpowers/specs/2026-09-06-gap25-couche-semantique-design.md`, plan homonyme) décrivent `Collection.metrics: list[NamedMetric]` ; `grep NamedMetric|metricName` sur `core/` et `shell/src` = 0 occurrence : jamais implémenté. A28 (feuille de route §8) promettait « métriques nommées CEL » sur le dataset : non livré.

## Cas retenu : Cas 2 (non couvert)

## Deux options v1 minimales

**Option A — métriques nommées sur `DatasetPayload`** : `metrics: dict[str, DatasetMetric]` (`{expr CEL | field+agg, label, format}`), résolues par `metricName` dans widgets/requête visuelle ; versionnées gratuitement avec la config du dataset.
- Pour : aligne A28, un seul lieu de définition par dataset, historique/rollback déjà là, MCP lit le dataset. Coût ~5.
- Contre : champ de schéma + validation CEL à l'écriture + résolution côté widget (cel-js) ET côté `aggregate` (SQL) à garder équivalents ; un changement de métrique modifie silencieusement tous les widgets consommateurs.

**Option B — `Collection.metrics` côté serveur (plan GAP-25 existant)** : catalogue par collection, résolu dans `run_collection_aggregate` (REST+MCP), autofill dans le wizard.
- Pour : plan/spec déjà écrits, un seul chemin d'exécution (SQL), partagé entre tous les datasets d'une même collection. Coût ~5-8.
- Contre : hors dataset (A28 dit dataset), migration Alembic, ne couvre pas les widgets calculant côté client ni les datasets ArcGIS (sans collection), spéculatif (aucun cas d'usage remonté).

## Recommandation

Option A, limitée à `field+agg` (pas de CEL libre en v1, donc un seul moteur d'évaluation : `AggregateMeasure`), si un cas d'usage réel apparaît ; sinon laisser REV-119 `ouvert` explicitement différé (le gap est jugé le plus spéculatif de la revue, spec du 2026-09-06). Les métriques partagées ENTRE datasets restent un manque distinct, à ouvrir en REV-325 après A.
